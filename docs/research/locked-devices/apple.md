# Baton on Apple platforms: what is technically possible when the device is LOCKED

Research date: 2026-10-14. Scope: macOS (Apple silicon and Intel) and iOS/iPadOS, current releases (macOS 27 / iOS 27 era).

Requirement under test: handing work off must keep working when the devices are locked, because the person will not leave the previous device unlocked.

Nothing in this report was executed on hardware. In the tables, the word Works means documented or credibly reported, and an [INFER] tag after it means the evidence is indirect. Anything without evidence is marked UNKNOWN and has an exact test in section C.

---------------------------------------------------------------------------------------------------

## Bottom line

1. **macOS, locked but awake: the background part of Baton very probably keeps working.** No Apple document says a locked session suspends its processes, and two indirect sources point the other way: a forum report from a CI-Mac administrator whose logged-in, locked Macs have `loginwindow` frontmost while the apps in the session sit in the Running Background state (Q1), and Chrome Remote Desktop's design, whose host process lives on in a user session that has been switched out to the login window (Q1, Q9). This is [INFER], not [DOC]; test T1 settles it. Two things do stop it: system sleep (forced sleep cannot be prevented, assertions are suggestions, and the user-idle assertions have no effect in Dark Wake) and a restart with FileVault (no third-party code runs until credentials are supplied; Apple silicon on macOS 26+ can be unlocked over SSH).
2. **macOS LAN access needs a one-time user grant for a LaunchAgent.** Local Network privacy (macOS 15+) exempts launchd daemons and root programs but explicitly not launchd agents, and sending UDP (which includes QUIC replies) and making outgoing TCP connections need the grant. Relay traffic over the internet does not (Q1).
3. **Capturing a window or the display, and injecting input, on a locked Mac is not documented as supported by anything Apple publishes.** Apple DTS only says it would expect ScreenCaptureKit to work in a locked GUI session and warns of special-case restrictions in the unlock UI; ScreenCaptureKit is unavailable before login; a sleeping display cannot be captured; Apple DTS says there is no native way to run XCUITest, which relies on the Accessibility API and an activated target app, on a locked session (Q6, Q7). Every shipping product found works around this with a privacy mode (blank the physical display, block local input, lock when the session ends), which presupposes that the Mac is unlocked first (Q10).
4. **Virtual displays are SPI only.** Apple DTS: there is no public API, only an SPI that several apps use (Q9). Chrome Remote Desktop's lock-like curtain uses the private `login.framework` function `SACSwitchToLoginWindow`, and it fails on Macs without a physical display (Q1, Q9).
5. **iOS/iPadOS locked: the app is suspended and Wi-Fi may be dropped.** The only dependable path to a locked iPhone is an APNs alert push (optionally rewritten by a Notification Service Extension in about 30 seconds); a tap then needs an unlock. There is no background pasteboard read. Default Class C file protection and Keychain `AfterFirstUnlock` keep the inbox usable while locked but not before the first unlock after a reboot (Q13-Q15).
6. **Design consequence [INFER].** Direction matters. A locked device can usually be a receiver (queue, store, notify), but it cannot reliably be a source that is polled on demand: a suspended iPhone cannot read its clipboard or serve files at all, and a locked Mac's clipboard-read and window-capture behaviour is unverified. So favour push-before-lock (the source encrypts and uploads or hands off while the person is using it) over pull-while-locked, and treat live streaming and remote control of a locked device as unproven until tests T9-T12, T19 pass (section E).

### 0.2 State definitions used in the tables

- macOS locked  = a user is logged in, the lock screen (or a password-protected screen saver) is showing, the system is awake. The display may be on or may have turned itself off.
- macOS asleep  = system sleep (idle sleep, lid closed, Apple menu Sleep), not Dark Wake.
- iOS locked    = screen locked and Baton's app is not in the foreground (suspended, unless a background mode or task is running it). Applies to iPadOS too.

## B. Answers to Q1-Q17

### Q1. macOS: LaunchAgent and network when locked, display sleep, system sleep, lid closed, Power Nap, App Nap, assertions, WoL, Sleep Proxy, wake from the internet

**One-line answer:** a locked screen and a sleeping display are not documented to stop a LaunchAgent, and indirect evidence says they do not; system sleep does stop it. IOPM assertions can hold the system awake but are suggestions, and lid close, Apple-menu sleep, low battery and thermal emergencies override them. LaunchAgents (unlike daemons) need the per-user Local Network grant.

1. LaunchAgent session and liveness
   - [DOC, archived] Launchd agent session types: Aqua (GUI agent, "Has access to all GUI services; much like a login item."), StandardIO, Background, and LoginWindow ("Runs in the loginwindow context"). A daemon "is not allowed to connect to the window server". Frameworks above CoreServices (ApplicationServices, Carbon, AppKit) need a GUI per-session bootstrap namespace. The note says a GUI session is created when a user logs in through the GUI, a process connected to the window server does not survive a normal logout, and an agent may need to know whether its GUI login session is active (using the console). https://developer.apple.com/library/archive/technotes/tn2083/_index.html
   - [REPORT, Developer Forums, original poster, not Apple] A CI-Mac administrator says the Macs are logged in but the lock screen is active, so the foreground process is `com.apple.loginwindow`, and UI tests fail to activate the app under test (the failure message ends in the state Running Background). This shows apps in a locked session in a background state, not suspended or killed, but the poster does not say what else keeps running. https://developer.apple.com/forums/thread/840965
   - [REPORT, source code, Chromium main branch, fetched 2026-10-14] Chrome Remote Desktop's macOS curtain mode is the best evidence that a user session keeps running while the console shows the login window. The code comment says: "When curtain mode is in effect on Mac, the host process runs in the user's switched-out session, but launchd will also run an instance at the console login screen." The same file rejects the root (login screen) instance with the error code LOGIN_SCREEN_NOT_SUPPORTED, installs a Carbon `kEventSystemUserSessionActivated` handler that disconnects the client when the session is switched back in, and switches the console with `base::mac::SwitchToLoginWindow()`. https://chromium.googlesource.com/chromium/src/+/refs/heads/main/remoting/host/curtain_mode_mac.cc
   - [REPORT, source code, PRIVATE] `SwitchToLoginWindow()` loads the private framework `/System/Library/PrivateFrameworks/login.framework/Versions/A/login` with `dlopen` and calls the function `SACSwitchToLoginWindow` found with `dlsym`. The same file has `SACScreenLockEnabled`, and a comment lists other possibly useful private functions: `SACLockScreenImmediate()`, `SACScreenSaverIsRunning()`, `SACScreenSaverStartNow()`, `SACScreenSaverStopNow()`. No comment in the file calls them private or undocumented; the PrivateFrameworks path is the indication. https://chromium.googlesource.com/chromium/src/+/refs/heads/main/base/mac/login_util.cc
   - [REPORT, source code] The same Chromium file says that on a Mac with no physical monitor the switch to the login window "will fail silently" (the comment cites rdar://42733382), so the host then disconnects the client. The 2020 version (M80) ran `CGSession -suspend` instead (the `CGSession` binary in the User menu extra), per the file shown by the fetch tool. https://chromium.googlesource.com/chromium/src/+/80.0.3987.116/remoting/host/curtain_mode_mac.cc
   - [DOC] `NSWorkspace.sessionDidResignActiveNotification` is "A notification that the workspace posts before a user session switches out." The page adds that if an app launches in an inactive session, the workspace sends the notification after `willFinishLaunching` and before `didFinishLaunching`, so apps are expected to run in sessions that are not on the console. It must be registered on `NSWorkspace.shared.notificationCenter`. https://developer.apple.com/documentation/appkit/nsworkspace/sessiondidresignactivenotification
   - [INFER] A locked but logged-in session is not suspended. No Apple page states this in so many words, and a switched-out session (what Chrome Remote Desktop uses) is not identical to the lock screen. Test T1.

2. Network from the agent (Local Network privacy, macOS 15 and later)
   - [DOC] macOS keeps separate local network privacy state for each user account. It automatically allows daemons started by `launchd`, programs running as root, and command-line tools run from Terminal or over SSH. Then: "The exception for `launchd` daemons doesn't apply to `launchd` agents." Device managers cannot configure it with MDM. https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy
   - [DOC] A local network is a network on a broadcast-capable interface (Wi-Fi, Ethernet, not cellular or VPN); traffic to local addresses, all multicast addresses and the IPv4 broadcast address is local network traffic. Operations that need the grant: making an outgoing TCP connection (yes), sending a UDP unicast (yes), sending multicast or broadcast (yes), connecting a UDP socket (yes), receiving UDP multicast (yes), Bonjour register, browse and resolve (yes), resolving `.local`. Operations that do not: listening for and accepting incoming TCP connections, and receiving an incoming UDP unicast. https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy
   - [INFER] QUIC is UDP, so even a listener-only agent that replies to a LAN peer is "sending a UDP unicast" and needs the grant. Connections that go through a relay on the internet are not local network traffic, so they need no grant. TN3179 describes the privilege by address and interface type; I did not find a statement about relays, so confirm with T2.
   - [DOC] For a `launchd` agent that is not installed with `SMAppService`, set `AssociatedBundleIdentifiers` in the plist so that macOS knows the responsible code (the app) and records the user's choice for the whole app. There is no API to show the alert (FB8711182); connecting a UDP socket to a local address triggers it without generating traffic. macOS fails to display the alert when a very short-lived process performs a local network operation, for example a `launchd` agent that exits immediately when the operation fails (FB16131937). https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy
   - [DOC] macOS 15.5 added the user defaults `AllowedEthernetLocalNetworkAddresses` and `AllowedWiFiLocalNetworkAddresses` (domain `com.apple.network.local-network`, array of CIDR strings, set with `sudo`, restart required) that make listed networks non-local for every program; TN3179 says this is aimed at site administrators and CI systems. macOS 27.2 adds add and remove buttons in System Settings > Privacy & Security > Local Network to reset a program's state. https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy
   - [DOC] Denial shows up as `NWPath.UnsatisfiedReason.localNetworkDenied` for an `NWConnection` TCP connection, or `kDNSServiceErr_PolicyDenied` for Bonjour. TN3179 recommends signing with an Apple-issued identity so that the privilege tracks the program reliably. https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy
   - [INFER] The first local network operation should happen while the user is present (onboarding), not as first background use; the alert cannot be answered on a locked unattended Mac. Test T2.
   - [DOC] macOS 27: `launchd` refuses property lists that carry the quarantine extended attribute, so an installer must create or clean them itself. https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes

3. Display sleep versus system sleep
   - [DOC] Separate options exist in Apple's Mac user guide: on laptops "Prevent automatic sleeping on power adapter when the display is off" (Battery > Options); on desktops "Prevent automatic sleeping when the display is off" (Energy Saver). https://support.apple.com/bn-in/guide/mac-help/set-sleep-and-wake-settings-mchle41a6ccd/14.0/mac/14.0
   - [REPORT, vendor doc] HCL BigFix Remote Control: if a Mac sits at the lock screen for 5 to 10 minutes with no input and no sessions, a later connection shows a black screen and the controller cannot take control; the documented fix is the Energy Saver option that prevents sleeping when the display is off. https://help.hcl-software.com/bigfix/10.0/lifecycle/Lifecycle/Remote_Control/RC_Admin_Guide/rcadmmaclocked.html
   - [REPORT, forum] A TidBITS poster with an M1 Mac mini found TeamViewer access became consistent after he enabled "Prevent Automatic Sleeping When the Display is Off" (an overnight backup had been putting the Mac to sleep). Anecdote. https://talk.tidbits.com/t/wake-on-lan-with-apple-silicon/33183
   - [DOC] `CGDisplayIsAsleep`: "A sleeping display is still considered to be a part of global display (desktop) space, but it is not drawable." https://developer.apple.com/documentation/coregraphics/cgdisplayisasleep(_:)

4. IOPM assertions and caffeinate (Apple open-source header, exact text from the header)
   - [DOC] `kIOPMAssertPreventUserIdleSystemSleep`: "The system may still sleep for lid close, Apple menu, low battery, or other sleep reasons." and "This assertion has no effect if the system is in Dark Wake." https://raw.githubusercontent.com/apple-oss-distributions/IOKitUser/main/pwr_mgt.subproj/IOPMLib.h
   - [DOC] `kIOPMAssertPreventUserIdleDisplaySleep`: "If the display is already off, this assertion does not light up the display." It points to `IOPMAssertionDeclareUserActivity` for turning the display on. Also "While the display is prevented from dimming, the system cannot go into idle sleep." and "This assertion has no effect if the system is in Dark Wake." https://raw.githubusercontent.com/apple-oss-distributions/IOKitUser/main/pwr_mgt.subproj/IOPMLib.h
   - [DOC] `kIOPMAssertNetworkClientActive`: "This assertion keeps the system awake in dark or full wake, as long as the system is on AC power." On battery it can prevent idle sleep; "This assertion provides CPU, disk, and network connectivity." Also: "IOKit power assertions are suggestions and OS X may not honor them under battery, thermal, or user circumstances." and "If the network is no longer available, this assertion may stop working and allow the system to go to sleep." It is the only one of the three whose header says it works in Dark Wake. https://raw.githubusercontent.com/apple-oss-distributions/IOKitUser/main/pwr_mgt.subproj/IOPMLib.h
   - [DOC] `IOPMDeclareNetworkClientActivity` wraps that assertion with a timeout equal to the system sleep timer: on AC it prevents idle sleep and demand sleep, on battery only idle sleep. The header says: "If your remote clients require access to the framebuffer or the GPU, then this isn't the appropriate call for you." It then points to `IOPMAssertionDeclareUserActivity` with `kIOPMUserActiveRemote`. https://raw.githubusercontent.com/apple-oss-distributions/IOKitUser/main/pwr_mgt.subproj/IOPMLib.h
   - [DOC] `IOPMAssertionDeclareUserActivity`: "This causes the display to power on and postpone display sleep, up to the user's display sleep Energy Saver settings." Any process may call it without special privileges ("No special privileges are necessary to make this call - any process may call this API."). To hold the display longer, the header suggests `kIOPMAssertPreventUserIdleDisplaySleep`. https://raw.githubusercontent.com/apple-oss-distributions/IOKitUser/main/pwr_mgt.subproj/IOPMLib.h
   - [REPORT, mirror of Apple's man page] `caffeinate`: `-s` "Create an assertion to prevent the system from sleeping." and, as a separate sentence, "This assertion is valid only when system is running on AC power."; `-i` creates an assertion to prevent idle sleep; `-d` one to prevent display sleep; `-u` "Create an assertion to declare that user is active." with "If the display is off, this option turns the display on and prevents the display from going into idle sleep." (5 second default timeout without `-t`). https://sudo.is/docs/macos/man_caffeinate.html
   - CONFLICT: the same Apple header says `kIOPMAssertionTypePreventSystemSleep` ("PreventSystemSleep") was "Deprecated in 10.9. This assertion is not supported in any OS X releases." and "This assertion is deprecated. Do not use it.", while the `caffeinate -s` man page describes a system-sleep assertion honoured on AC only. Which assertion `caffeinate -s` really takes on macOS 26/27 is [UNKNOWN] (T3). Do not rely on `-s`; use `PreventUserIdleSystemSleep` plus `NetworkClientActive` and check `pmset -g assertions`.
   - [DOC] `ProcessInfo.beginActivity(options:reason:)` options include idleDisplaySleepDisabled, idleSystemSleepDisabled, userInitiated, userInitiatedAllowingIdleSystemSleep, background, latencyCritical. https://developer.apple.com/documentation/foundation/processinfo/activityoptions

5. Forced sleep cannot be prevented
   - [DOC, archived, 2014] Technical Q&A QA1340 distinguishes idle sleep from forced sleep (closing a laptop lid, choosing Sleep from the Apple menu, a thermal emergency or low battery). It says: "it is not possible to prevent forced sleep, only delay it." If an app does not acknowledge the will-sleep message, sleep is delayed by 30 seconds; `kIOMessageCanSystemSleep` is not sent for forced sleep. https://developer.apple.com/library/archive/qa/qa1340/_index.html
   - [INFER] A lid close on a MacBook without the closed-display conditions, or a low battery, will end Baton's availability whatever assertions it holds; the app should detect the will-sleep message and tell peers it is going away.

6. App Nap
   - [DOC, archived] The App Nap page says "Generally, an app is a candidate for App Nap if:" it isn't the foreground app, hasn't recently updated content in the visible portion of a window, isn't audible, hasn't taken any IOKit power management or NSProcessInfo assertions, and isn't using OpenGL. An app is taken out of App Nap when it comes to the foreground or receives an XPC message or an Apple event. The page does not say whether UI-less LaunchAgents are napped. https://developer.apple.com/library/content/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/AppNap.html
   - [INFER] Holding a ProcessInfo activity or an IOPM assertion while a peer session is connected removes the candidacy; test T1 covers an agent with and without one.

7. Power Nap, Wake for network access, pmset
   - [DOC] Mac user guide (the macOS 14.0 edition of the page; the current edition was not fetched), Wake for network access: lets the Mac "wake briefly so users can access shared services (if applicable)". 8. Sleep Proxy, Wake-on-LAN, wake from the internet
   - [REPORT, by the Sleep Proxy author, Lion-era page] A low-power always-on device on the same LAN segment ("like an AirPort base station or Apple TV") answers for the sleeping Mac and wakes it when "the proxy sees an incoming IP UDP packet" or an "incoming IP TCP connection request for a Bonjour-advertised service on the sleeping machine". Pinging does not wake it. The Mac needs Bonjour-advertised services and "Wake for network access"; a laptop "needs both (a) to be connected to AC power and (b) to have a display available". Ethernet: "Sleep Proxy wakeup is supported on all Macs connected via Ethernet." Wi-Fi: "supposed to be supported when associated with compatible Wi-Fi base station", with reports of it not working reliably. https://stuartcheshire.org/sleepproxy/
   - [REPORT, third-party project documentation, weak] The Desomnia project documents that Apple's proxies cap a registration lease at 24 hours and wake the host when the lease expires. I could not confirm this in an Apple source. https://desomnia.readthedocs.io/en/stable/modules/network/sleepproxy/apple.html
   - [REPORT, forum] Wake-on-LAN on Apple silicon is unresolved. In a TidBITS thread the original poster relays that TeamViewer support said Apple silicon Macs do not reliably support third-party Wake-on-LAN while sleeping; another poster's M2 Mac Studio shows `womp 1` but he does not say whether it wakes; nobody tested Ethernet against Wi-Fi. https://talk.tidbits.com/t/wake-on-lan-with-apple-silicon/33183 . Apple forum 656687 is Intel-only (2018 MacBook Pro, Catalina), has no Apple answer, and one poster merely points at `DNSServiceSleepKeepalive` in `dns_sd.h`. https://developer.apple.com/forums/thread/656687
   - [REPORT, source code] `DNSServiceSleepKeepalive(sdRef, flags, fd, timeout, callback, context)` is declared in `dns_sd.h` without documentation; a lead only, semantics UNKNOWN. https://raw.githubusercontent.com/apple-oss-distributions/mDNSResponder/main/mDNSShared/dns_sd.h
   - [UNKNOWN] Wake from the internet: no mechanism available to third parties was found. Deep sleep (`standby`, `autopoweroff`) may defeat LAN wake after some hours; T4.
   - [INFER] Any wake scheme needs a second always-on device on the same LAN (a Sleep Proxy such as an Apple TV, or a Baton helper sending a magic packet); a relay alone cannot wake a Mac.

### Q2. After a FileVault restart: what runs pre-login, Apple silicon vs Intel

**One-line answer:** nothing third-party runs until FileVault credentials are supplied. Apple silicon with macOS 26 or later can be unlocked over SSH if Remote Login is on and a network connection is available. After that the Mac proceeds to a normal login and user LaunchAgents start.

- [REPORT, Apple DTS, forum 758542, July 2024] "When you boot a machine with FileVault enabled, it boots to pre-boot environment that will not load any third-party code." A footnote says: "Historically that used to be EFI. These days it's a cut-down version of macOS. Regardless, there's no third-party code." https://developer.apple.com/forums/thread/758542
- [REPORT, Apple DTS, forum 758542, same thread as above] After pre-boot "the system boots for real. That ends up starting loginwindow", which tries to acquire the `system.login.console` right; Apple's own mechanisms detect that the user has entered credentials into FileVault and use them to complete the login without showing UI. DTS also says that pre-login agents are ordinary launchd agents that you enable or disable by adding or removing the plist in `/Library/LaunchAgents` or with `launchctl enable` and `disable`, and (as relayed by the fetch tool) that `SMAppService` is not an option for them because it only supports agents in `~/Library/LaunchAgents`; re-read the thread before relying on that last point. https://developer.apple.com/forums/thread/758542
- [DOC] "After a user turns on FileVault on a Mac, their credentials are required during the boot process." On Apple silicon the internal volume is always encrypted; "FileVault on a Mac with Apple silicon is implemented using Data Protection Class C with a volume key." https://support.apple.com/guide/security/sec4c6dc1b6e
- [DOC] "FileVault can be unlocked over SSH after a restart if Remote Login is turned on and a network connection is available." Scope given: Apple silicon, macOS 26 or later. The pages do not distinguish Wi-Fi from Ethernet and do not say what happens after the unlock. https://support.apple.com/guide/security/sec8447f5049 and https://support.apple.com/guide/deployment/dep82064ec40
- [REPORT, single-user blog] A short account of remote FileVault unlock on Tahoe says limited SSH runs at pre-boot; Ethernet worked reliably and Wi-Fi did not; intended for the same network or a VPN. https://deepakness.com/raw/remote-filevault-unlock-macos-tahoe/
- CONFLICT (different OS generations, not necessarily a contradiction): a Jamf community thread dated 2024-07-31 (Sonoma) has one poster say the FileVault unlock screen "has no network connectivity" and another say macOS "isn't fully running" until someone unlocks locally. Apple's macOS 26 documentation above describes SSH unlock. https://community.jamf.com/general-discussions-2/file-vault-mac-os-sonoma-33828
- [REPORT, Apple DTS (Quinn), forum 724955] An Endpoint Security developer reports that on FileVault Macs daemons and system extensions start after the first user login and after some LaunchAgents; Quinn answers that expecting daemons to start before agents is "not a valid expectation in general", because launchd is launch-on-demand and the root of much of that demand is the loginwindow session. https://developer.apple.com/forums/thread/724955 . Forum 745343 has only the question (a LaunchDaemon that runs only after login on macOS 14.2.1), without an Apple answer. https://developer.apple.com/forums/thread/745343
- [REPORT, vendor docs] Parsec's separate login-screen installer (a LaunchAgent in `/Library/LaunchAgents`) requires that FileVault be disabled and that the host use a hardwired Ethernet connection. https://support.parsec.app/hc/en-us/articles/32381618319124-Access-Login-Screen-on-macOS . Level's macOS remote control does not support a Mac that is powered off or "sitting at the pre-boot FileVault unlock screen, where the agent isn't running yet". https://docs.level.io/en/articles/15486697-macos-remote-control . A Sunshine user reports login items only start after login and used automatic login as a workaround. https://github.com/orgs/LizardByte/discussions/777 . A TeamViewer community answer says the FileVault boot screen is not the real macOS login and recommends `sudo fdesetup authrestart` for remote reboots (community advice, not on Apple's page). https://community.teamviewer.com/English/discussion/comment/152119/
- [INFER] A LaunchDaemon or LoginWindow-session agent lives on the encrypted volume and cannot run earlier. After a power loss or update restart a FileVault Mac is unreachable by Baton until a person (or SSH-unlock tooling) supplies the password. After the FileVault credentials are reused the desktop is logged in and unlocked, so a LoginWindow-session agent would live only briefly. Test T5.
- [UNKNOWN] Intel specifics: apart from DTS's footnote that pre-boot was historically EFI, and SSH unlock being documented only for Apple silicon, nothing was found for Intel Macs with or without a T2 chip. `fdesetup authrestart` (authenticated restart) is mentioned only in community posts here.

### Q3. NSPasteboard from a LaunchAgent while locked; pasteboard privacy prompts; Universal Clipboard with a locked Mac

**One-line answer:** no documented gate on writes. Reads are the target of a new macOS pasteboard privacy alert whose enforcement on shipping 27.x is not documented, and an alert on a locked, unattended Mac cannot be answered. Universal Clipboard has no macOS API and no documented lock behaviour.

- [DOC] The general pasteboard "automatically participates with the Universal Clipboard feature" and there is no macOS API for interacting with it: the NSPasteboard page says "There is no macOS API for interacting with this feature." https://developer.apple.com/documentation/appkit/nspasteboard
- [DOC] AppKit updates, April 2025: "Prepare your app for an upcoming feature in macOS that alerts a person using a device when your app programmatically reads the general pasteboard." and "The system shows the alert only if the pasteboard access wasn't a result of someone's input on a UI element that the system considers paste-related." New `detect` methods read patterns without notifying; `accessBehavior` reports whether access is always allowed, never allowed, or prompts; preview with `defaults write <bundle id> EnablePasteboardPrivacyDeveloperPreview -bool yes`. https://developer.apple.com/documentation/updates/appkit
- [DOC] `accessBehavior`: "The user can customize this behavior per-app in System Settings for any app that has triggered a pasteboard access alert in the past." https://developer.apple.com/documentation/appkit/nspasteboard
- [DOC] macOS 27.2 beta 4 notes, AppKit > Deprecations: "The EnablePasteboardPrivacyDeveloperPreview user default has been removed." (186955507). Neither these notes nor the macOS 27 notes say whether the alert is now on by default. https://developer.apple.com/documentation/macos-release-notes/macos-27_2-release-notes
- [REPORT, blog comments] Michael Tsai's post on the preview records a Felix Schwarz update (September 2025) that the feature seemed absent in macOS 26 unless enabled with the defaults key, and comments dated 2026-09-21/22 that the key is deprecated and no longer does anything, with one developer, running with SIP and AMFI disabled, doubting that the alert is enabled at all. Enforcement on macOS 27.0 and 27.1 is therefore [UNKNOWN] (T6). https://mjtsai.com/blog/2025/05/12/pasteboard-privacy-preview-in-macos-15-4
- Unrelated: the macOS 26.4 Terminal paste warning (ClickFix protection) is a Terminal feature, not this API. https://mjtsai.com/blog/?p=51478
- [INFER] The documented alert covers programmatic reads. Writes (`setString`) and an inbound phone-to-Mac flow are not described as gated, and polling `changeCount` is not described as a content read. A pull model that reads the Mac's clipboard on demand while the Mac is locked is the risky case: if an alert appears, nobody can answer it.
- [UNKNOWN] Whether NSPasteboard writes and `changeCount` polling from a LaunchAgent work while the screen is locked: no source. T6.
- [UNKNOWN] Universal Clipboard with a locked Mac. Apple's Handoff security page describes Handoff and Universal Clipboard (BLE advertisements, AES-256-GCM, payload protected and transferred in the same way as an iMessage) and has no statement about locked devices. https://support.apple.com/guide/security/handoff-security-secf78dbe639/web . One AppleVis user wrote that they have seen it fail if one of the devices is locked (undated, not specific to the Mac). https://applevis.com/comment/65068

### Q5. File reads while locked (TCC, FileVault, iCloud placeholders)

- [DOC] Data Protection classes. Class C (Protected Until First User Authentication) is the same as Class A "except that the decrypted class key isn't removed from memory when the device is locked or the user logged out." It is the default for third-party app data; on Mac it uses a volume key that stays accessible as long as the volume is mounted. Class A on macOS: shortly after the last user is logged out, the decrypted class key is discarded. Apple silicon Macs do not support Class D (No Protection). https://support.apple.com/guide/security/secb010e978a
- [INFER] A locked but logged-in Mac keeps files readable and writable for the user's processes. Test T8.
- [UNKNOWN] TCC: no source says grants change, or prompts are answerable, when the screen is locked. Grants persist by app identity (INFER); a prompt triggered while locked cannot be answered until unlock.
- [DOC] macOS 27: a process without a bundle ID cannot be granted Files & Folders access to other teams' app or group containers (known issue 184660124; workaround Full Disk Access); accesses to other teams' containers no longer prompt and are denied by default (161835690); apps can no longer access the local TCC database directly (90775556). A bare LaunchAgent helper should therefore live inside the app bundle and have a bundle identifier. https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes
- [UNKNOWN] iCloud Drive placeholders (dataless files): on-demand download while locked: no source. T8.

### Q11. Continuity (Handoff, Universal Clipboard, AirDrop, iPhone Mirroring): the bar to beat

**One-line answer:** Apple documents nothing about Handoff, Universal Clipboard or AirDrop toward a locked Mac, except that an AirDrop receiver must be awake. The one Apple feature built around a locked device is iPhone Mirroring. Its security model (a hardware-backed Mac identity pinned on the iPhone, an authentication choice enforced by the Secure Enclave, a time-boxed remote unlock, visible indicators on the locked iPhone) is the bar for any Baton feature that acts on a locked device.

1. Handoff
   - [DOC] Apple Platform Security: "the two devices establish a Bluetooth Low Energy (BLE) 4.2 pairing out-of-band using APNs." Each device generates "a symmetric 256-bit AES key", stored in the keychain, and "This key can encrypt and authenticate the BLE advertisements"; the advertisements use AES-256 in GCM mode with replay protection (paraphrase). The payload: "The activity payload is protected and transferred in the same way as an iMessage." For web pages: "the system advertises the domain name of the webpage in the encrypted Handoff advertisement bytes." and "When launched, the native app receives the full URL and the title of the webpage." https://support.apple.com/guide/security/handoff-security-secf78dbe639/web
   - [DOC] The same page states only a proximity condition (Handoff works "when a user's iOS, iPadOS, and macOS devices are near each other.") and, as read through the fetch tool, makes no statement about unlock state, screen state or locked devices. https://support.apple.com/guide/security/handoff-security-secf78dbe639/web
2. Universal Clipboard
   - [DOC] Same Platform Security page: "Content is protected in the same way as other Handoff data"; it is shared by default "unless the app developer chooses to disallow sharing"; and "Apps have access to clipboard data regardless of whether the user has pasted the clipboard into the app." https://support.apple.com/guide/security/handoff-security-secf78dbe639/web
   - [DOC] Mac User Guide (macOS 11-era page): Universal Clipboard works "When Handoff is on", so Handoff must be enabled; the page does not say whether the Mac must be unlocked, and says nothing about a locked or sleeping Mac. https://support.apple.com/en-asia/guide/mac-help/mchl732d3c0a/11.0/mac
   - [DOC] There is no macOS API for it (Q3). On iOS the general pasteboard "automatically transfers its contents to nearby devices that use the same iCloud account", with `localOnly` and `expirationDate` options (Q14). https://developer.apple.com/documentation/uikit/uipasteboard
3. Handoff requirements, current Mac User Guide
   - [DOC] "Both devices have Wi-Fi and Bluetooth turned on."; "You're signed in to the same Apple Account on both devices."; "Your devices must be within 10 metres (30 feet) of one another."; the app must support Handoff. The page does not mention a Mac being locked, asleep or at the login window. https://support.apple.com/en-in/guide/mac-help/mchl732d3c0a
4. AirDrop
   - [DOC] Discovery: "the sending device emits an AirDrop signal over BLE that includes the user's AirDrop short identity hash." Then "The Wi-Fi radio is used to communicate directly between devices". Receivers are listed as "Other Apple devices that are awake, in close proximity, and have AirDrop turned on" (awake is required; unlocked is not mentioned). The page does not address screen-on, unlocked or locked states. https://support.apple.com/guide/security/airdrop-security-sec2261183f4/web
5. iPhone Mirroring: the security model (the only first-party flow built around a locked device)
   - [DOC] Preconditions: "Your iPhone is locked and near your Mac." (it may also be charging and in StandBy); "Your iPhone and Mac are signed in to the same Apple Account using two-factor authentication."; "Your iPhone is using iOS 18 or later and is set up to use a passcode."; macOS 15 or later; the Mac must be Apple silicon or have the T2 chip; "Your Mac is not sharing its internet connection or using AirPlay or Sidecar."; "iPhone Mirroring can be used with only one Mac and one iPhone at a time."; "iPhone Mirroring is currently unavailable in the European Union." https://support.apple.com/en-lb/120421 and https://support.apple.com/120421 (the macOS 15, T2 and one-pairing lines appear only in the plain 120421 version of the page as fetched).
   - [DOC] Setup and identity: the Mac user enters the iPhone passcode on the iPhone; "the current cryptographic identity for the Mac is recorded."; "The private key for this identity is protected in the Secure Enclave."; the identity is pinned, so "if it changes, notifications aren't forwarded to the Mac." Identities are exchanged over a local peer-to-peer protocol and protected with end-to-end encrypted keys in iCloud (paraphrase of the fetch tool's summary). https://support.apple.com/guide/security/sec6ab47ebfc
   - [DOC] Session start: the remote unlock uses the same protocol as Apple Watch unlocking an iPhone (paraphrase), and is started by launching the iPhone Mirroring app on the Mac. At setup the user chose between 'Automatically authenticate' and 'Ask every time' (the labels); the Mac's Secure Enclave enforces the choice. Then "the Mac connects to the iPhone using a local wireless peer-to-peer connection." and the Mac "unlocks the iPhone keybag to enable remote access for the duration of the remote session." Also: "Secure ranging isn't required for iPhone Mirroring." https://support.apple.com/guide/security/sec6ab47ebfc
   - CONFLICT (minor, between Apple pages): the authentication prompt is described three ways. The Platform Security page: the Mac password or Touch ID if supported. Apple Support 120421: "iPhone Mirroring always asks you to authenticate before mirroring," with the Mac login password, Touch ID or Apple Watch (the list is paraphrase). The Mac User Guide: "Receive a prompt for Touch ID, Face ID, or your iPhone passcode each time you use iPhone Mirroring." https://support.apple.com/en-om/guide/mac-help/mchl444d53a6
   - [DOC] During the session: "Your iPhone stays locked, so no one else can access it or use it to see what you're doing."; "While mirroring, your iPhone says that it's in use and identifies the Mac using it."; the Platform Security page says users see a persistent notification on the iPhone's Lock Screen; "iPhone Mirroring automatically pauses the connection after periods of inactivity."; "To stop mirroring your iPhone, quit the iPhone Mirroring app or unlock your iPhone."; "Access to the iPhone camera and mic is not available in iPhone Mirroring, including for Face ID or phone calls."; drag and drop, Universal Clipboard and AirDrop are supported (paraphrase). The Personal Safety guide adds that using the iPhone directly ends the session (paraphrase). https://support.apple.com/en-lb/120421 , https://support.apple.com/guide/personal-safety/ips70daa1bcf/web
   - [DOC] Afterwards: "A banner is shown the first time the iPhone is unlocked after a session has ended."; Settings > General > AirPlay & Continuity > iPhone Mirroring shows which Mac, when and for how long; access can be revoked from the iPhone (including Safety Check) or from the Mac. Revoking "resets iPhone Mirroring" (Personal Safety guide). https://support.apple.com/guide/security/sec6ab47ebfc , https://support.apple.com/guide/personal-safety/ips70daa1bcf/web
   - [DOC] Notifications: "Your Mac automatically receives notifications and Live Activities from your iPhone." That happens whether or not iPhone Mirroring is in use or the iPhone is nearby, as long as it is on (paraphrase). https://support.apple.com/en-lb/120421
   - [UNKNOWN] Whether the Mac must be unlocked to start iPhone Mirroring: as read through the fetch tool, Apple Support 120421 and the Personal Safety guide both say they do not state it, and the Mac User Guide page says nothing about a locked or sleeping Mac. The Platform Security page, as summarised, does not describe encryption of the mirrored screen stream either.
6. The bar to beat [INFER from the items above]
   - Proximity-triggered or one-tap start, no manual pairing per transfer, end-to-end encrypted.
   - A hardware-backed device identity pinned by the other side; a changed identity stops the flow.
   - The device that is controlled stays locked, grants a time-boxed session only after the controlling device authenticates (with a user choice between automatic and ask every time), and shows a persistent indicator naming the controlling device plus a history of past sessions.
   - iPhone Mirroring is the reverse of Baton's main case (a locked phone and an in-use Mac). Apple's keybag unlock is a first-party mechanism; I found no public API that lets a third-party app unlock or drive a locked iPhone.
   - [UNKNOWN] Handoff, Universal Clipboard and AirDrop toward a locked Mac (T15).

### Q12. Lock / sleep detection APIs and notifications (public? stable?)

**One-line answer:** sleep and wake are covered by documented macOS APIs (the `IORegisterForSystemPower` header lists availability from macOS 10.0, and the `NSWorkspace` screen-sleep notification is listed from macOS 10.6); that they behave the same on macOS 26 and 27 for a LaunchAgent was not tested here (T14). Screen lock and unlock on macOS are signalled, as far as I found, only by undocumented distributed notification names that Chromium, Electron and Hammerspoon use; the only documented signal tied to a session is the fast-user-switching pair. iOS has no public lock-state API, only protected-data availability signals. The full list is in section D.

1. Undocumented lock notifications (macOS)
   - [REPORT, source code] Chromium `ui/base/idle/idle_mac.mm`, at commit d4afc97b7 (its date was not verified; the file carries a 2012 copyright header): a `MacScreenMonitor` observes `com.apple.screensaver.didstart`, `com.apple.screensaver.didstop`, `com.apple.screenIsLocked` and `com.apple.screenIsUnlocked` on `NSDistributedNotificationCenter`, and reports the session as locked if the screensaver is running or the screen-lock flag is set. https://chromium.googlesource.com/chromium/src/+/d4afc97b7/ui/base/idle/idle_mac.mm
   - [REPORT, source code, fetched raw 2026-10-14] Electron (`main` branch) observes `com.apple.screenIsLocked` and `com.apple.screenIsUnlocked` on the distributed center and emits `lock-screen` and `unlock-screen`; it also observes `NSWorkspaceSessionDidBecomeActiveNotification` and `NSWorkspaceSessionDidResignActiveNotification` on the shared workspace center and emits `user-did-become-active` and `user-did-resign-active`. https://raw.githubusercontent.com/electron/electron/main/shell/browser/api/electron_api_power_monitor_mac.mm
   - [REPORT, source code, fetched raw 2026-10-14] Hammerspoon (`master`) `libcaffeinate_watcher.m` observes the lock pair plus `com.apple.screensaver.didstart`, `com.apple.screensaver.willstop`, `com.apple.screensaver.didstop` on the distributed center, and `NSWorkspaceDidWakeNotification`, `WillSleep`, `WillPowerOff`, `ScreensDidSleep`, `ScreensDidWake`, `SessionDidResignActive`, `SessionDidBecomeActive` on the workspace center. Its comment: "It is crucial to use the shared workspace notification center here." https://raw.githubusercontent.com/hammerspoon/hammerspoon/master/extensions/caffeinate/libcaffeinate_watcher.m
   - [INFER] The names are not in Apple's documentation (I found no Apple page for them). Electron `main` and Hammerspoon `master`, both fetched on 2026-10-14, still use them, and the Chromium file above shows long use (2012 header; its commit date was not verified). That shows long use, not that they fire on macOS 26 or 27: I found no report either way. Nobody guarantees them. Treat as best effort and pair with a poll (below). T14.
2. Documented macOS notifications and their rules
   - [DOC] `NSWorkspace.willSleepNotification`: "A notification that the workspace posts before the device goes to sleep." and "An observer of this message can delay sleep for up to 30 seconds while handling this notification." https://developer.apple.com/documentation/appkit/nsworkspace/willsleepnotification
   - [DOC] `NSWorkspace.didWakeNotification`: "A notification that the workspace posts when the device wakes from sleep." https://developer.apple.com/documentation/appkit/nsworkspace/didwakenotification
   - [DOC] `NSWorkspace.screensDidSleepNotification`: "A notification that the workspace posts when the device’s screen goes to sleep." (macOS 10.6 and later). It also says: "If you use a different notification center to register, you won’t receive the notification." The same rule is on the will-sleep and did-wake pages. https://developer.apple.com/documentation/appkit/nsworkspace/screensdidsleepnotification
   - [DOC] `NSWorkspace.sessionDidResignActiveNotification` and its counterpart are about user sessions switching out and in (fast user switching), not about the screen lock (Q1 item 1). https://developer.apple.com/documentation/appkit/nsworkspace/sessiondidresignactivenotification
   - [REPORT, source code only] `screensDidWake` and `willPowerOff` NSWorkspace notifications are used by Hammerspoon; I did not fetch their documentation pages, so their [DOC] status is unverified. https://raw.githubusercontent.com/hammerspoon/hammerspoon/master/extensions/caffeinate/libcaffeinate_watcher.m
3. IOKit power messages
   - [DOC, header] `IORegisterForSystemPower` "Does not provide system shutdown and restart notifications." ### Q13. iOS/iPadOS: background execution limits, BGTaskScheduler, audio/VoIP/location tricks and App Store risk, APNs background/VoIP/NSE/time-sensitive, Multipeer/Bonjour in background

**One-line answer:** a locked iPhone or iPad moves Baton to the background, suspends it shortly after, and may drop Wi-Fi. The only documented way to reach a locked device is an APNs push (an alert push, optionally rewritten by a Notification Service Extension in about 30 seconds). LAN-first transport to a locked phone is not dependable.

1. Lock, suspension and Wi-Fi
   - [DOC] When the app moves to the background, "That method has five seconds to perform any tasks and return. Shortly after that method returns, the system puts your app into the suspended state." `beginBackgroundTask` extends this, but "If you don’t end your tasks in a timely manner, the system terminates your app." It cannot be called from an app extension; use `ProcessInfo.performExpiringActivity(withReason:using:)` there. https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time
   - [DOC] "Typically, an app is in a suspended state when it’s in the background." https://developer.apple.com/documentation/xcode/configuring-background-execution-modes
   - [REPORT, Apple DTS (Quinn), forum 844516; the original poster's Linux-based device is wired to an iPhone by USB-C Ethernet and loses data about 30 seconds after the lock, and Quinn answers by comparing it to the Wi-Fi behaviour] "If you lock the screen, your app moves to the background and shortly thereafter gets suspended, meaning that it's unable to perform networking." And separately: "If the device sleeps, the system disassociates from Wi-Fi." On Wi-Fi power: "For Wi-Fi, an iOS device with WWAN will shut down the Wi-Fi interface to save power, relying on WWAN for push notifications. OTOH, if the device doesn't have WWAN, it'll attempt to stay associated with Wi-Fi for these admins tasks." For Ethernet Quinn writes: "I would expect this to work the same way on Ethernet, but I must admit that I've never tested this." https://developer.apple.com/forums/thread/844516
   - [REPORT, Developer Forums post on the Wi-Fi lifecycle, forum 734361; the author is not shown in the fetched text] Lists circumstances where iOS leaves a Wi-Fi network: "Device sleep, which typically happens shortly after screen lock" and "After 30 minutes of not having a Wi-Fi app active"; says the details are not documented; for cellular it says "On modern iPhones [1] the WWAN lifecycle is quite simple: The system tries hard to keep the interface up as much as possible." A footnote says: "The behaviour of Wi-Fi apps is one of the places where I'm least confident about the accuracy of this post." https://developer.apple.com/forums/thread/734361
   - [REPORT, Apple DTS (Kevin Elliott), forum 783777, about Local Push Connectivity dropping on a locked phone] Asked whether Wi-Fi-only locked devices are the problem scenario: "Yes, that's the scenario that tends to have the most problems." and "Having an active cellular radio tends to mask these issues by hiding WiFi issues." He also mentions one iOS 16 issue: a device disassociating at lock from an access point whose information elements mark it as a battery-powered hotspot (paraphrase). The original poster (not Apple) reproduced drops only with the phone locked and unplugged. https://developer.apple.com/forums/thread/783777
   - [REPORT, forum 772637] Apple DTS (Quinn): "I suggested it here because I suspect that’s what’s happening. AFAIK NWListener doesn’t have any sort of 15 minutes limit on its background viability, so there’s something else causing this failure." About `UIRequiresPersistentWiFi` he writes: "That’s not what that property is about. Rather, it’s supposed to prevent the system from disassociating from Wi-Fi." The original poster (not Apple) later wrote that a CoreLocation problem stopped location updates and the app went to sleep. That is an anecdote that location updates kept the app running, not an Apple statement. https://developer.apple.com/forums/thread/772637
   - [INFER] A locked phone has no listener, may have no Wi-Fi association and has a suspended process. LAN-first transport to it works only while the device is awake and Baton is in the foreground, or while some background mode keeps it running.
2. BGTaskScheduler and other background time
   - [DOC] `BGAppRefreshTask`: "The system decides the best time to launch your background task, and provides your app up to 30 seconds of background runtime." `BGProcessingTask` is for work "such as overnight when the device charges", at a time the system chooses. https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app
   - [DOC] `BGContinuedProcessingTask` "starts in the foreground", your app "needs to run the task only in response to someone’s action, such as tapping a button.", the system shows progress through a system interface where the person can cancel, and "The system cancels any running tasks if a person closes the app in the app switcher, but the app doesn’t receive an indication of cancellation in that case." The pages I read do not show the task's introduction version. https://developer.apple.com/documentation/backgroundtasks/performing-long-running-tasks-on-ios-and-ipados
   - [DOC] Background modes: `audio`, `location`, `voip`, `external-accessory`, `bluetooth-central`, `bluetooth-peripheral`, `screen-capture` (iOS, iPadOS, visionOS), `fetch`, `remote-notification`, `processing`, `nearby-interaction`, `push-to-talk`. The `screen-capture` row: "The app captures and streams screen content while in the background." Also: "Use background execution modes sparingly because overuse can negatively impact device performance and battery life." https://developer.apple.com/documentation/xcode/configuring-background-execution-modes
3. Pushes
   - [DOC] Background push (`content-available: 1`, `apns-push-type: background`, `apns-priority: 5`): "the system doesn’t guarantee their delivery" and "don’t try to send more than two or three per hour." The system holds only the newest one and "If something force quits or kills the app, the system discards the held notification." After delivery "Your app has 30 seconds to perform any tasks and call the provided completion handler." https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app
   - [DOC] Notification Service Extension: the `didReceive(_:withContentHandler:)` method "has only about 30 seconds to modify the payload and call the provided completion handler."; "If you fail to call the completion handler from either method, the system displays the original contents of the notification."; the payload must include `mutable-content` with the value 1 and an `alert` dictionary with title, subtitle or body. It is not run if alerts are disabled or the payload only plays a sound or sets a badge. An example in the page decrypts an encrypted payload. https://developer.apple.com/documentation/usernotifications/modifying-content-in-newly-delivered-notifications
   - [DOC] VoIP push: "If you are unable to support CallKit in your app, you cannot use PushKit to handle push notifications." It also says: "If you need to do work in response to an incoming notification, for example to decrypt content, use a notification service extension to perform that work." Apps built with the iOS 13 SDK or later must use CallKit for VoIP calls. https://developer.apple.com/documentation/pushkit/responding-to-voip-notifications-from-pushkit
   - [DOC] Interruption levels: `timeSensitive` is described as "The system presents the notification immediately, lights up the screen, can play a sound, and breaks through system notification controls."; `passive` adds to the list "without lighting up the screen or playing a sound". Whether `timeSensitive` overrides a hidden-preview or locked-screen setting, and the entitlement or review needed, were not checked [UNKNOWN]. https://developer.apple.com/documentation/usernotifications/unnotificationinterruptionlevel
   - [REPORT, Apple DTS (Kevin Elliott), forum 760711] Paraphrase of his reply: Apple has never formally documented what should launch before first unlock; the broad behaviour is that, outside a few specific components such as VoIP apps and Notification Service Extensions, the system tries to avoid launching anything before first unlock, with exceptions in both directions. He adds: "Don't try to fix/change ANY of these issues unless you're in the foreground." An Apple Frameworks engineer in the same thread confirmed one such behaviour as a bug (FB14562763). If an app cannot operate before first unlock, he says there are only two options (paraphrase): block normal operation until the data is accessible, or call `exit()` or `abort`, and tell the user in either case. https://developer.apple.com/forums/thread/760711
4. App Store risk of keep-alive tricks (audio, VoIP, location)
   - [DOC] App Review Guideline 2.5.4: "Multitasking apps may only use background services for their intended purposes: VoIP, audio playback, location, task completion, local notifications, etc." 2.5.1 says apps "should use APIs and frameworks for their intended purposes"; 2.4.2 says apps "may not run unrelated background processes"; 4.5.4 says "Push Notifications must not be required for the app to function". https://developer.apple.com/app-store/review/guidelines/
   - [INFER] Using audio, VoIP or location only to keep a socket alive is outside the intended-purposes wording; Apple's decisions are not documented, so treat it as a rejection risk and as a battery cost the person will notice. Guideline 4.5.4 means Baton must still function (foreground or manual sync) without push.
5. Multipeer, Bonjour, Wi-Fi Aware, Local Push, Bluetooth
   - [DOC] Multipeer Connectivity: "If the app moves into the background, the framework stops advertising and browsing and disconnects any open sessions." https://developer.apple.com/documentation/multipeerconnectivity
   - [DOC] TN3179, iOS: "If an iOS app is in the background and performs a local network operation while its Local Network privilege is undetermined, the system denies that operation without presenting the local network alert." The system does not record that decision; a later foreground operation shows the alert as if it were the first. App extensions "share the Local Network privilege state of their container app", and extension types assumed to run in the background are denied the same way. Packet tunnel, app proxy and DNS proxy provider extensions "have local network access regardless of the Local Network privilege state of their container app". On iOS, sending or receiving multicast or broadcast needs the `com.apple.developer.networking.multicast` entitlement, as does working with arbitrary Bonjour service types or browsing all service types; sending a UDP unicast and receiving an incoming UDP unicast do not. https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy
   - [INFER] The first LAN operation must happen with the app in the foreground during onboarding; a Notification Service Extension that tries to reach a Mac on the LAN first would be denied.
   - [DOC] Wi-Fi Aware (iOS and iPadOS 26 and later): "Your app may connect to paired Wi-Fi Aware devices whenever it’s running, in both foreground and background states." The page adds that the app may get runtime through the platform's existing mechanisms, for example BackgroundTasks (paraphrase). It describes pairing with Wi-Fi Aware certified accessories; whether a Mac or PC can be such a peer is not stated. https://developer.apple.com/documentation/wifiaware
   - [REPORT, Apple DTS (Quinn), forum 787570] Quinn writes: "WiFiAware works like any other networking API in this respect. Connections operate fine in the background as long as your app is executing." A suspended app loses its connections; idle connections are closed after an undocumented timeout, currently a few minutes; there is no state restoration equivalent (paraphrase of the rest). https://developer.apple.com/forums/thread/787570
   - [DOC] Local Push Connectivity: "Local Push Connectivity is appropriate for use cases where an iOS device operates on a local, restricted network that doesn’t have access to APNs." The extension "functions like a local network replacement for APNs; use it primarily to send small messages and alerts to users", is launched when the device joins a matching Wi-Fi SSID, needs the `app-push-provider` value of the `com.apple.developer.networking.networkextension` entitlement requested from Apple, and Apple says to "limit your functionality within the push provider extension to delivering local notifications and CallKit alerts to users". [INFER] It is meant for restricted networks, not for a consumer LAN channel, so entitlement approval is doubtful. https://developer.apple.com/documentation/networkextension/local-push-connectivity
   - [INFER, unverified] A `bluetooth-central` scan filtered on a Baton service UUID might wake the app when a nearby Mac advertises. The mode is documented ("The app communicates with a Bluetooth accessory while in the background."), but I found no statement about waking on an advertisement. T16.

### Q14. iOS: clipboard (UIPasteboard background, paste prompt/banner, Allow Paste, Universal Clipboard); Share Extension / App Intent / Live Activity / Control Center control / NSE while locked

**One-line answer:** there is no background pasteboard read, and a read without user intent triggers a system notice. The extension types that can run while the device is locked (Notification Service Extension, intents with `alwaysAllowed`, controls) have no documented pasteboard-write behaviour. Plan the iOS clipboard as: write to the pasteboard only from the foreground app on a user action, and put incoming items in an inbox.

1. Reading in the background and the paste notice
   - [REPORT, Apple DTS (Quinn), forum 706761, May 2022] "There's no way to read the pasteboard while you're in the background. This isn't an omission, but rather a matter of policy." In the original post the read returned null and the log showed a `PBErrorDomain` error with code 10 (pasteboard not available at this time). The thread has no workaround and does not discuss writing, extensions or a locked device. https://developer.apple.com/forums/thread/706761
   - [DOC] "Starting in iOS 14, the system notifies the user when an app gets general pasteboard content that originates in a different app without user intent." User intent comes from interactions "such as tapping a system-provided control or pressing Command-V". Properties that do not trigger the notice: `numberOfItems`, `types`, `itemSet(withPasteboardTypes:)`, `hasColors`, `hasImages`, `hasStrings`, `hasURLs`, the `NSItemProvider` `canLoadObject` calls and the pattern-detection methods. https://developer.apple.com/documentation/uikit/uipasteboard
   - [REPORT, press] The per-app Settings entry Paste from Other Apps (Ask, Deny, Allow) appeared in the iOS 16.1 betas, from beta 4 and only for apps that have already asked to paste; Allow lets the app paste without asking again. The page does not say which option is the default. https://mjtsai.com/blog/?p=37419 . [REPORT, vendor doc] The clipboard manager Octoclip states that the setting defaults to Ask and that Allow reduces alerts but does not start monitoring; it also says "iOS does not provide an automatic, permanent background-monitoring permission." https://docs.octoclip.app/advanced/ios/limitations
   - [UNKNOWN] The exact wording and trigger of the iOS 16 and later Allow Paste prompt: I found no Apple page describing it beyond the DocC note above.
2. Universal Clipboard
   - [DOC] On iOS: "When a user signs into iCloud, the general pasteboard automatically transfers its contents to nearby devices that use the same iCloud account." `localOnly` and `expirationDate` (parameters of `setItemProviders`, `setObjects` and `setItems` options) control Handoff behaviour and expiry: "At the time and date that you set, the system removes the pasteboard items from the pasteboard." The page's sentence on which `localOnly` value excludes a pasteboard reads as inverted; check the API reference before relying on it [INFER]. https://developer.apple.com/documentation/uikit/uipasteboard
   - [UNKNOWN] Behaviour with a locked phone as source or target: one AppleVis user wrote "Also, I've seen it fail if one of the devices is locked." (undated, no device named). https://applevis.com/comment/65068
   - [UNKNOWN] Whether any extension (Notification Service Extension, App Intent, Share Extension) can write `UIPasteboard.general` while the device is locked, and whether such a write syncs by Universal Clipboard: no source. T17, T20.
3. Share Extension
   - [INFER] The share sheet is presented from a foreground app on an unlocked device, so Share Extensions are a pull-from-the-phone path that works only when the phone is in use. No document found says this explicitly.
4. App Intents and Shortcuts
   - [DOC] `IntentAuthenticationPolicy.alwaysAllowed`: "A policy that allows the app intent to run at any time, including when the device is locked."; `requiresAuthentication`: "A policy that requires authentication before running the app intent."; `requiresLocalDeviceAuthentication`: "A policy that requires the person to unlock the device running the intent." https://developer.apple.com/documentation/appintents/intentauthenticationpolicy
   - [UNKNOWN] What `perform()` may do on a locked device (network, pasteboard, file write) is not documented. T20.
5. Controls (Control Center, Lock Screen, Action button)
   - [DOC] "For added privacy, require device authentication before a control performs its action, as well as redact the text in a control when the device is locked." A control updates when someone interacts with it, when the app asks to reload it, or when the system receives an APNs push. https://developer.apple.com/documentation/widgetkit/creating-controls-to-perform-actions-across-the-system
   - [REPORT, forum, weak] A TidBITS thread reports that on iOS 18 several Control Center actions prompt for the passcode when Face ID does not authenticate, and that the relevant switch is Allow Access When Locked under Face ID and Passcode. https://talk.tidbits.com/t/ios-18-control-center-requires-unlock/29532
6. Live Activities
   - [DOC] A Live Activity "can’t access the network or receive location updates" (unlike a widget); static and dynamic data "can’t exceed a combined size of 4 KB"; it can be active for up to eight hours and then stay on the Lock Screen up to four more hours (12 hours at most on the Lock Screen); it is updated through ActivityKit in the app or ActivityKit push notifications. ### Q15. iOS: receiving a handoff on a locked device (lock-screen notification with link; Data Protection class choice)

**Recommended path [INFER from the cited docs]:** the Baton server or relay sends an APNs alert push with `mutable-content: 1`; the Notification Service Extension (about 30 seconds) decrypts the end-to-end-encrypted payload and writes the item to a Class C inbox; the lock-screen notification shows the link; a tap leads to the unlock prompt and then to the app. A relay that cannot reach the phone by APNs would have to wait until the app is in the foreground.

1. Notification content on the lock screen
   - [DOC] Category options: `hiddenPreviewsShowTitle`: "Show the notification’s title, even if the user has disabled notification previews for the app."; `hiddenPreviewsShowSubtitle`: "Show the notification’s subtitle, even if the user has disabled notification previews for the app."; and the category property `hiddenPreviewsBodyPlaceholder`: "The placeholder text to display when the system disables notification previews for the app." https://developer.apple.com/documentation/usernotifications/unnotificationcategoryoptions , https://developer.apple.com/documentation/usernotifications/unnotificationcategory/hiddenpreviewsbodyplaceholder
   - [DOC] `UNNotificationActionOptions.authenticationRequired`: abstract "The action can be performed only on an unlocked device." and discussion "When the user selects an action with this option, the system prompts the user to unlock the device." After unlocking the app is notified of the chosen action. https://developer.apple.com/documentation/usernotifications/unnotificationactionoptions/authenticationrequired
   - [INFER] By implication, an action without that option does not prompt for unlock, and a Baton 'Copy' action would be of that kind. Whether its handler runs while the device stays locked, and whether it may write the pasteboard, is [UNKNOWN] (T18).
   - [UNKNOWN] The user-visible default of Show Previews and the Face ID glance behaviour were not verified; Apple's iPhone User Guide pages returned only metadata to the fetch tool.
2. Data Protection and the Keychain
   - [DOC] Class C, Protected Until First User Authentication, is Class A "except that the decrypted class key isn’t removed from memory when the device is locked or the user logged out.", and "This is the default class for all third-party app data not otherwise assigned to a Data Protection class." Class B (Protected Unless Open) is meant for work while locked: "Some files may need to be written while the device is locked or the user is logged out." https://support.apple.com/guide/security/secb010e978a
   - [DOC] `FileProtectionType.complete`: "cannot be read from or written to while the device is locked or booting"; `completeUntilFirstUserAuthentication`: "cannot be accessed until after the device has booted"; `completeUnlessOpen`: "The file is stored in an encrypted format on disk after it is closed." https://developer.apple.com/documentation/foundation/fileprotectiontype
   - [DOC] When `isProtectedDataAvailable` is false, files marked `complete` or `completeUnlessOpen` "cannot be read or written by your app" until the user unlocks. https://developer.apple.com/documentation/uikit/uiapplication/isprotecteddataavailable
   - [DOC] Keychain: `kSecAttrAccessibleAfterFirstUnlock` data "cannot be accessed after a restart until the device has been unlocked once by the user", and "This is recommended for items that need to be accessed by background applications." https://developer.apple.com/documentation/security/ksecattraccessibleafterfirstunlock
   - [REPORT, Apple DTS (Kevin Elliott), forum 760711] Do not modify data to "fix" a before-first-unlock situation unless in the foreground; detect the situation early, for example by probing a dedicated check file, and then block or exit and tell the user (details in Q13 item 3). https://developer.apple.com/forums/thread/760711
   - [INFER] Keep the inbox (ciphertext plus metadata) in Class C and the decryption keys in the Keychain with `AfterFirstUnlock`; never use `complete` for anything the Notification Service Extension or a background push must touch. Before the first unlock after a reboot the extension cannot read the keys: show a generic placeholder and process the item after unlock. [UNKNOWN] whether a Class B file can be created by the extension before first unlock (T17).
3. Link opening
   - [INFER] Tapping a notification on a locked iPhone is expected to lead to the unlock prompt and then to the app. I found no Apple page that states this for the default tap, and it was not tested (T18). For controls and Live Activities see Q14 items 5 and 6.

## E. Implications for Baton (derived from the above; each is [INFER])

1. Design for push-before-lock. The purpose is to leave one device locked and continue on another. What is reliably possible is to move the state while the source device is still in use or at the moment it locks: on macOS flush pending clipboard, link and file announcements when the lock notification, the screen-saver notification or `willSleep` arrives (the documented `willSleep` gives up to 30 seconds); on iOS flush from the background transition (five seconds, extendable with `beginBackgroundTask`). Pulling from a device that is already locked is the unproven case (T6, T9, T10, T12; Q3, Q6, Q14).
2. Treat macOS locked-but-awake as a supported state for the control channel, clipboard set (after T6), file receive, queued links with a notification, and lock and unlock awareness. Hold `NetworkClientActive` or `PreventUserIdleSystemSleep` assertions only while a peer is connected; the header says `NetworkClientActive` keeps the system awake in Dark Wake or Full Wake as long as the Mac is on AC power, can only prevent idle sleep on battery, and that assertions are suggestions the system may not honour under battery, thermal or user circumstances, so peers must expect a sleeping Mac; use `IOPMAssertionDeclareUserActivity(kIOPMUserActiveRemote)` only when frames must be produced, because it lights the physical display.
3. Install and onboarding. Ship the agent inside the signed app, trigger the Local Network alert during onboarding while the person is present (connect a UDP socket to a local address), set `AssociatedBundleIdentifiers` for a plain-plist agent, strip the quarantine attribute from any property list (macOS 27 `launchd` refuses them), and sign with an Apple-issued identity. Let the first connection use the relay, which needs no grant, while the LAN grant is pending.
4. Pre-login components. TN2083 (archived) says an agent set to run in LoginWindow and Aqua gets an instance in the loginwindow context that is terminated when a user logs in, with a second instance in the GUI context. Parsec's login-screen build shows the cost: a LaunchAgent in /Library/LaunchAgents, FileVault off, wired Ethernet. Do not plan on a pre-login Baton component while FileVault is on. After a restart a FileVault Mac is unreachable until a person (or SSH unlock tooling on Apple silicon, macOS 26 and later) supplies the credentials; document this limit.
5. Do not promise to stream a window from a locked Mac, or to control it while locked, until T9 to T12 and T23 pass. Every shipping product found uses a privacy mode (blank the physical display, block local input, lock at the end) that presupposes an unlocked Mac; RustDesk shows that a public-API version exists (T22); Chrome Remote Desktop's lock-like curtain needs a private function and fails headless. If the source must stay locked until the person authorises from the other device, the options found are: (a) Apple's iPhone Mirroring pattern, with a pinned hardware-backed device identity, an authentication step on the controlling device, a time-boxed session and visible indicators; (b) the privacy-mode pattern, in which the session unlocks, blanks and re-locks; (c) a screen-unlock authorization plug-in (DTS 737268 says third parties can extend the unlock UI), which is a separate, risky project.
6. iOS and iPadOS. Never rely on the LAN to reach a locked phone. Use APNs alert pushes with `mutable-content` and a Notification Service Extension for payload decryption, Class C storage, Keychain `AfterFirstUnlock`, and generic placeholder text when keys are unavailable. Background pushes are throttled (two or three an hour). Guideline 4.5.4 requires that the app works without push. Avoid audio, VoIP and location keep-alive tricks (Guideline 2.5.4 risk). A tap on the notification needs an unlock.
7. For iOS-as-source streaming (later phase) target ScreenCaptureKit on iOS 27, not a ReplayKit extension; expect a user-initiated picker, uncertain lock behaviour (T19), and watch the `screen-capture` App Store Connect validation problem (forum 840821).
8. Wake from sleep is a LAN problem (Sleep Proxy, Wake-on-LAN helper, or a scheduled wake set by a root helper); a relay cannot do it. Plan for a sleeping Mac being unreachable by default.

Conflicts

- CONFLICT: `caffeinate -s` ("Create an assertion to prevent the system from sleeping.", valid on AC power only, per the man page mirror) versus the Apple header text that `PreventSystemSleep` was "Deprecated in 10.9. This assertion is not supported in any OS X releases." Unresolved; T3.
- CONFLICT: Apple DTS says it would expect ScreenCaptureKit to work in a locked GUI session, versus a user report against an AI computer-use tool that the Screen Recording API "does not function through the lock screen at the OS level" (no version, API or test shown). Unresolved; T9. Related but different: DTS says there is no native way to run XCUITest on a locked session.
- CONFLICT (different OS generations): a 2024 Jamf thread on Sonoma says the FileVault unlock screen has no network connectivity; Apple's macOS 26 documentation describes unlocking over SSH. Unresolved; T5.
- CONFLICT (minor, between Apple pages): iPhone Mirroring authentication is described as Mac password or Touch ID (Platform Security), Mac login password, Touch ID or Apple Watch (Apple Support 120421) and Touch ID, Face ID or iPhone passcode (Mac User Guide). T15.
- Weak and contested: Wake-on-LAN on Apple silicon (anecdotes only; one user relays a vendor statement that it is not reliable). T4.
- Weak and contested: High Performance Screen Sharing locking the remote Mac on connect (two user threads on macOS 14.2 and 14.3; Apple documents blanking the hardware displays). T12.
