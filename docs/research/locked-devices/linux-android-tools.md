# Baton research: what is technically possible when the source device is LOCKED

Scope: Linux desktops (GNOME, KDE Plasma, X11), Android 16/17, and how existing remote-access tools cope with a locked host.
Research date: 2026-10-14. Every "main"/"master" source file cited was fetched on this date (GNOME Shell/Mutter/GNOME Remote Desktop main is roughly GNOME 51; KWin/PowerDevil/KRdp master is Plasma 6.8 development; Android docs are the Android 17 era docs).
Requirement under test: the user walks away from device A, leaves A LOCKED, and continues on device B.
Windows, macOS and iOS/iPadOS are covered by other research threads and appear here only where a cross-platform tool forces a mention.

## 0. How to read this report

Confidence labels (three levels were asked for; I added [UNKNOWN] for gaps and [IDEA] for design proposals):

- **[DOCS]** confirmed in official documentation or a formal specification.
- **[CODE]** confirmed by source code, an issue-tracker or maintainer statement, or a credible report.
- **[INFER]** inferred by reasoning from facts I did confirm; nobody states it directly in anything I could read.
- **[UNKNOWN]** I found no evidence either way. Every one of these is on the "must verify on real hardware" list (section 4).
- **[IDEA]** (used in Q12 and a few recommendations) a design proposal of mine, supported only by the facts cited beside it and untested.
- A trailing `*` (for example `[DOCS*]`) means the page reached me only through a summarising fetch tool (a small model paraphrased it; I did not read the wording verbatim). Treat as medium confidence. Text in quotation marks inside a `*` item is what the summariser returned as a quote and may not be verbatim.
- The word **undocumented** is written out wherever something relies on an undocumented API, a hidden/privileged permission, or a compositor-internal protocol.

Limits of this research (details in section 6): nothing was tested on real hardware; many hosts were blocked by the sandbox proxy (freedesktop.org, gitlab.gnome.org, invent.kde.org, android.googlesource.com, x.org, source.android.com via curl, docs.rustdesk.com, several vendor sites); the web-search budget ran out part-way, so TeamViewer is not verified at all and the RustDesk CVE list was not obtained; some vendor statements (Parsec, AnyDesk, Apple) came through a summarising fetch tool.

## 2. Findings that matter most for the Baton design

1. On Linux the lock screen is a UI state, not a process boundary. The agent, its sockets and its mDNS keep running; what really stops them is idle-suspend (GNOME and KDE both default to suspend after 15 minutes of inactivity on AC power) and lid-close (which ignores ordinary sleep inhibitors by default).
2. GNOME deliberately tears down all remote-access sessions on lock (ScreenCast, RemoteDesktop, InputCapture) and refuses new ones. Window streaming, portal input and portal clipboard from a locked GNOME session are impossible by design. Anything B needs from a GNOME source must be staged before the lock, or come from a separate headless session.
3. KDE has no such kill switch in the code I read, but KWin sends all input only to the lock screen, and KDE's own answer for "remote use while the seat is locked" (Plasma 6.8 KRdp "exclusive mode") is a virtual monitor plus switching the physical seat to the login greeter. Capture of the real session while locked is unverified on KDE.
4. On Android a locked phone cannot expose its clipboard, cannot be screen-captured (MediaProjection stops on lock; keyguard is FLAG_SECURE), and can keep a listener alive only through a typed foreground service whose survival is device-dependent. Android 17 adds a runtime local-network permission that covers inbound UDP/QUIC for apps targeting SDK 37.
5. Existing tools never stream the real windows of a locked GNOME-like session. They do one of: unattended credentials (AnyDesk, RustDesk, Parsec), a separate virtual session (Chrome Remote Desktop, GNOME Remote Desktop headless, KRdp exclusive mode, Apple Screen Sharing virtual display), root-level capture (Sunshine KMS, RustDesk DRM), or auto-lock when the remote session ends.
6. Security: any process running as the same user can call logind `Session.Unlock` without authentication (polkit is bypassed for the session owner), and both GNOME Shell and KDE's screen locker obey it. A compromised Baton agent can therefore unlock the machine. Baton must never expose a remote-unlock feature (KDE Connect does), and a locked device should run in a "serve staged data only, never initiate, never control" mode.
7. The one pattern that works on every platform examined while the source stays locked is to stage before the user leaves (explicit "send" gesture, or continuous mirroring where the platform allows background clipboard reads: X11 and KDE yes, GNOME and Android no) and deliver later through an end-to-end encrypted store-and-forward mailbox, because nothing then needs the source afterwards (Q12a, Q12b). Live window streaming or remote input from a *locked* source is impossible by design on GNOME and on Android, unverified on KDE, and elsewhere is achieved only by a separate session or by lowering the lock (stored credentials, remote unlock) (Q4, Q9, Q11, Q12d).
8. The worry ("I don't want to leave my previous device unlocked") can be addressed from the other side: after the handoff is acknowledged, ask the old device to lock itself. That is one logind call on Linux (GNOME and KDE both obey it) but needs a device-admin or accessibility route on Android (Q12e). Android also offers one documented primitive for locked receivers: Keystore keys created with `setUnlockedDeviceRequired(true)` still allow public-key encryption while locked and block decryption until unlock (Q12b). The main reachability risks on Android are Android 17's `ACCESS_LOCAL_NETWORK` for inbound and outbound LAN traffic, Low Power Standby, and OEM background killers (Q6).

## 3. Numbered answers

### Part A: Linux (GNOME, KDE Plasma, X11, systemd-logind)

#### Q1. User services and sockets while locked; suspend, linger, inhibitors, lid close, Wake-on-LAN

**Answer.** Locking stops nothing. Suspend freezes everything. An agent can delay suspend by a few seconds but cannot hold it off with an ordinary inhibitor when the lid closes. Wake-on-LAN can resume the hardware, but KDE sends the machine back to sleep after 30 s unless user activity is registered.

1. **The lock screen does not touch processes or sockets.** [CODE]
   - GNOME Shell's screen shield only shows the shield/unlock dialog, sets the logind session's `LockedHint` (`SetLockedHintAsync`), listens to the logind session signals `Lock`/`Unlock`, and takes a `sleep` delay inhibitor so it can lock before suspend. Nothing stops units. https://raw.githubusercontent.com/GNOME/gnome-shell/main/js/ui/screenShield.js
   - KDE's kscreenlocker does the same: it listens to `Lock`/`Unlock`, calls `SetLockedHint`, and takes a `sleep` delay inhibitor described as "Ensuring that the screen gets locked before going to sleep". https://raw.githubusercontent.com/KDE/kscreenlocker/master/logind.cpp
   - Existing tools rely on this: RustDesk's Linux service runs while locked and tests `LockedHint` (`loginctl show-session <sid> --property=LockedHint`); KDE Connect's desktop `lockdevice` plugin reads `LockedHint`; KRdp calls logind `Lock`/`Unlock`. https://raw.githubusercontent.com/rustdesk/hbb_common/ebb4d4a48cf7ed6ca62e93f8ed124065c6408536/src/platform/linux.rs , https://raw.githubusercontent.com/KDE/kdeconnect-kde/master/plugins/lockdevice/lockdeviceplugin.cpp , https://raw.githubusercontent.com/KDE/krdp/master/server/SessionController.cpp
2. **What does stop user processes.** [DOCS]
   - Suspend: "by default these services freeze user.slice while they run. This prevents the execution of any process in any of the user sessions while the system is entering into and resuming from sleep". The same page says applications that want to react to suspend should use inhibitor locks. https://raw.githubusercontent.com/systemd/systemd/main/man/systemd-suspend.service.xml
   - Logout: `KillUserProcesses=` decides whether session processes die (the compiled-in default is distro dependent); processes under `user@.service` survive "depending on the linger settings" (`loginctl enable-linger`); `UserStopDelaySec=` defaults to 10 s. https://raw.githubusercontent.com/systemd/systemd/main/man/logind.conf.xml
   - Linger only matters for the "logged out" case. For the locked case the user manager is already running. A lingering service has no display server, clipboard or browser, so it is useful only for relay-mailbox work. [INFER]
3. **Out-of-the-box idle suspend will stop a locked, idle machine.** [CODE]
   - GNOME upstream defaults: `sleep-inactive-ac-timeout=900`, `sleep-inactive-battery-timeout=900`, both type `suspend`; `idle-delay=300`; `lock-enabled=true`; `lock-delay=0`. https://raw.githubusercontent.com/GNOME/gnome-settings-daemon/master/data/org.gnome.settings-daemon.plugins.power.gschema.xml.in , https://raw.githubusercontent.com/GNOME/gsettings-desktop-schemas/master/schemas/org.gnome.desktop.session.gschema.xml.in , https://raw.githubusercontent.com/GNOME/gsettings-desktop-schemas/master/schemas/org.gnome.desktop.screensaver.gschema.xml.in
   - KDE PowerDevil defaults: auto-suspend (Sleep) after 900 s on AC, 600 s on battery, 300 s on low battery (not in VMs); dim 300 s and screen off 600 s on AC; lid close = Sleep. https://raw.githubusercontent.com/KDE/powerdevil/master/daemon/powerdevilsettingsdefaults.cpp
   - Distributions override these (I did not verify any distro's values). [UNKNOWN]
4. **Inhibitors.**
   - Types and modes: `shutdown`, `sleep`, `idle`, `handle-power-key`, `handle-suspend-key`, `handle-hibernate-key`, `handle-lid-switch`; modes `block` and `delay`; a `delay` inhibitor holds the operation for at most `InhibitDelayMaxSec` (default 5 s). The inhibitor is the file descriptor returned by `Inhibit()`. [DOCS] https://systemd.io/INHIBITOR_LOCKS/ , https://raw.githubusercontent.com/systemd/systemd/main/man/logind.conf.xml
   - Polkit defaults in systemd main: `inhibit-block-sleep` = yes for local active/inactive sessions and `auth_admin_keep` for "any"; `inhibit-delay-sleep` = yes for all; `inhibit-handle-lid-switch` = no for "any", yes for local sessions. [CODE] https://raw.githubusercontent.com/systemd/systemd/main/src/login/org.freedesktop.login1.policy
   - Whether a service started by `systemd --user` (not inside a session scope) counts as "local session" for polkit is **not verified**. [UNKNOWN] Delay inhibitors are allowed for everyone, so a pre-sleep hook is always possible.
   - A pre-sleep hook gets at most 5 s and the network may already be going down (NetworkManager also reacts to sleep). A "push snapshot at sleep" is therefore unreliable; snapshot at the `Lock` signal or at `LockedHint=true` instead. [INFER]
   - GNOME specifics: gsd-power takes a `handle-lid-switch` block inhibitor while an external monitor is attached or the monitor configuration changed recently (released by a timer), and a `sleep` delay inhibitor "GNOME needs to lock the screen". Idle suspend is blocked by session inhibitors with the SUSPEND flag. https://raw.githubusercontent.com/GNOME/gnome-settings-daemon/master/plugins/power/gsd-power-manager.c
   - An "idle" inhibitor (for example `org.freedesktop.ScreenSaver.Inhibit` or the portal's idle flag) also stops screen blanking and auto-lock. Baton must not take one just to stay reachable; that would silently disable the user's auto-lock. [INFER from the GNOME idle-inhibit mapping in gsd-screensaver-proxy] https://raw.githubusercontent.com/GNOME/gnome-settings-daemon/master/plugins/screensaver-proxy/gsd-screensaver-proxy-manager.c
5. **Lid close.**
   - logind: `HandleLidSwitch=` defaults to `suspend`; `HandleLidSwitchDocked=` defaults to `ignore` (docking station or more than one display connected); `LidSwitchIgnoreInhibited=` defaults to `yes`, meaning "shutdown", "reboot", "sleep" and "idle" inhibitors are ignored for lid events; only the low-level `handle-lid-switch` inhibitor is always honoured. [DOCS] https://raw.githubusercontent.com/systemd/systemd/main/man/logind.conf.xml
   - So a plain `sleep` block inhibitor held by Baton does **not** keep a laptop awake when the lid closes; only a `handle-lid-switch` inhibitor would, and that would turn a closed laptop in a bag into a heater. Do not do it by default. [DOCS + INFER]
   - GNOME: with no external monitor logind (or gsd) handles the lid. gsd-power's `do_lid_closed_action` only locks the screen when suspend is inhibited ("Suspend is inhibited but lid is closed, locking the screen"); whether the machine then stays awake depends on logind. [CODE; resulting behaviour UNKNOWN, must test]
   - KDE: PowerDevil handles it itself (`HandleButtonEvents::onLidClosedChanged` then `SuspendSession` with `Explicit=true`), suppressed only when an external monitor is present and the user enabled that option. [CODE] https://raw.githubusercontent.com/KDE/powerdevil/master/daemon/actions/bundled/handlebuttonevents.cpp
6. **Wake-on-LAN and friends.**
   - Tools and settings: `ethtool -s <dev> wol g` (magic packet); NetworkManager `802-3-ethernet.wake-on-lan` (flags phy 0x2, unicast 0x4, multicast 0x8, broadcast 0x10, arp 0x20, magic 0x40; default 1 = use global settings; 0x8000 = ignore) and `802-11-wireless.wake-on-wlan` (any, disconnect, magic, gtk-rekey-failure, eap-identity-request, 4way-handshake, rfkill-release, tcp). [DOCS*] https://networkmanager.dev/docs/api/latest/settings-802-3-ethernet.html , https://networkmanager.dev/docs/api/latest/settings-802-11-wireless.html , https://man7.org/linux/man-pages/man8/ethtool.8.html
   - Practical limits (BIOS/UEFI switch, driver resets, S5 vs S3, Wi-Fi WoWLAN driver support): Arch Wiki offline mirror and a Wi-Fi WoWLAN tutorial. [CODE, credible secondary] https://wikipedia.jakami.de/content/archlinux_en_all_maxi_2026-04/Wake-on-LAN , https://www.cyberciti.biz/faq/configure-wireless-wake-on-lan-for-linux-wifi-wowlan-card/
   - A magic packet is a link-layer frame, so the sender must be on the same L2 segment (or a helper on that LAN relays it). [INFER]
   - KDE specifics: after a wake whose source is Network, Telephony or Timer, PowerDevil registers a 30 s idle timeout and suspends again unless user activity cancels it; the code comment says the consumer of such a wake-up is expected to register user activity. [CODE] https://raw.githubusercontent.com/KDE/powerdevil/master/daemon/actions/bundled/handlebuttonevents.cpp
   - Whether wake works from the s2idle state or only from S3, and on which NICs, is hardware dependent. [UNKNOWN]

#### Q2. Clipboard while locked (X11, Wayland core, wlr-/ext-data-control, GNOME/Mutter, portal clipboard)

**Answer.** X11: yes. Wayland core: no (focus rule). KDE: background access exists through `ext-data-control` for native apps. GNOME: no sanctioned background access at all, and the portal route is switched off while locked.

1. **X11.** Selections belong to the owning client and any client can request them; no focus is involved. The X11 locker only grabs keyboard and pointer (XSecureLock README: it "relies on a keyboard and pointer grab"; other apps can still poll `XQueryKeymap`, `XQueryPointer` and `/dev/input`). So a background agent can read and write the clipboard while locked. [INFER, based on X11 design plus the XSecureLock threat model] https://raw.githubusercontent.com/google/xsecurelock/master/README.md ; untested, see V-X11 in section 4. I could not read the ICCCM/XTest specs (x.org blocked).
2. **Wayland core protocol.** [DOCS*] `wl_data_device.selection`: "The selection event is sent to a client immediately before receiving keyboard focus and when a new selection is set while the client has keyboard focus. The data_offer is valid until a new data_offer or NULL is received or until the client loses keyboard focus." `set_selection` takes "serial number of the event that triggered this request". https://docs.rs/wayland-client/latest/wayland_client/protocol/wl_data_device/enum.Event.html , https://docs.rs/wayland-client/latest/wayland_client/protocol/wl_data_device/enum.Request.html . The official wayland.xml itself was not reachable; docs.rs embeds the same text.
   - While locked the keyboard focus belongs to the lock surface (ext-session-lock-v1: the compositor shows only lock surfaces and gives them the input), so an ordinary client has no focus and therefore no core-protocol clipboard access. [INFER from the two facts; ext-session-lock text: https://wayland.app/protocols/ext-session-lock-v1 [DOCS*]]
3. **Data-control protocols.** `ext-data-control-v1` is described as "This protocol allows a privileged client to control data devices." Support per the registry page (interpretation of the page's markers is medium confidence): supported by KWin 6.7, Sway 1.11, Hyprland 0.52, niri, labwc, river, COSMIC, Mir, Treeland, phoc, Jay; not supported by Mutter 51, Muffin 6.7, Weston, Wayfire, Cage, GameScope. [DOCS*] https://wayland.app/protocols/ext-data-control-v1
   - KWin implements only the `ext` variant (version 1); its source lists `ext_data_control_manager_v1` among the "restricted interfaces" that sandboxed (Flatpak/Snap) clients cannot bind, so native unsandboxed clients can. [CODE] https://raw.githubusercontent.com/KDE/kwin/master/src/wayland_server.cpp , https://raw.githubusercontent.com/KDE/kwin/master/src/wayland/datacontroldevicemanager_v1.cpp
   - KDE's own clipboard library (used by Klipper and KDE Connect's desktop clipboard plugin) tries `ext_data_control`, then wlr-data-control, then falls back to the focus-bound Qt clipboard. On Mutter, that fallback is all there is. [CODE] https://raw.githubusercontent.com/KDE/kguiaddons/master/src/systemclipboard/ksystemclipboard.cpp , https://raw.githubusercontent.com/KDE/kdeconnect-kde/master/plugins/clipboard/clipboardlistener.cpp
   - Whether KWin keeps delivering data-control events while the screen is locked is **not documented**. `LockScreenFilter` filters input events, not selections, so it probably works. [INFER; UNKNOWN until tested]
4. **GNOME/Mutter.**
   - Mutter 51 exposes no data-control protocol; the Deskflow maintainers' bug report quotes the registry ("registry only has `wl_data_device_manager`") and notes that `wl-paste` has to create a focus-grabbing toplevel to read the clipboard; Deskflow dropped its wl-clipboard path and relies on the portal clipboard. [CODE, credible report] https://github.com/deskflow/deskflow/issues/10135
   - The portal clipboard exists but belongs to a RemoteDesktop session ("Clipboard" interface of xdg-desktop-portal). [DOCS] https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Clipboard.html . On GNOME every RemoteDesktop session is closed on lock and cannot be recreated while locked (Q4), so the portal route is closed while locked. [CODE]
   - A GNOME Shell extension runs inside the compositor process and could use the shell's clipboard. Extensions are disabled on the lock screen unless `metadata.json` lists `"unlock-dialog"` in `session-modes` ("Extensions that specify this key are allowed to run, or keep running, on the lock screen"). Whether clipboard APIs work in that mode is untested. [DOCS* + UNKNOWN] https://gjs.guide/extensions/overview/anatomy.html , https://raw.githubusercontent.com/GNOME/gnome-shell/main/js/ui/sessionMode.js
5. **Implication.** On GNOME/Wayland a "capture the clipboard when the user locks" feature is not available to a background daemon even when the machine is unlocked; the user must act (explicit "send to Baton", or copy while a Baton window has focus) before leaving. [INFER]

#### Q3. Opening URLs while locked (Linux)

**Answer.** The mechanisms still work (nothing in logind, GNOME or KDE blocks `xdg-open` or the OpenURI portal while locked, as far as I could find), but the result is invisible until unlock. No source states what happens, so treat "works" as unverified.

1. Mechanisms: `xdg-open`/`gio open`, D-Bus activation, and the OpenURI portal (`org.freedesktop.portal.OpenURI`). [DOCS] https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.OpenURI.html . I found no statement that any of them refuses while a session is locked. [UNKNOWN]
2. Visibility: in GNOME's locked session mode `hasWindows` is false and `hasNotifications` is false; `layout.js` hides `global.window_group` and `top_window_group` when `hasWindows` is false. A browser window opened while locked exists but is not shown. [CODE] https://raw.githubusercontent.com/GNOME/gnome-shell/main/js/ui/sessionMode.js , https://raw.githubusercontent.com/GNOME/gnome-shell/main/js/ui/layout.js
3. KDE: ext-session-lock makes the compositor show only lock surfaces. KDE also has a protocol that lets a surface appear above the lock screen, `kde_lockscreen_overlay_v1`: "Allows a client to request a surface to be visible when the system is locked. This is meant to be used for specific high urgency cases like phone calls or alarms. Warning! ... a desktop environment implementation detail. Regular clients must not use this protocol." KWin treats it as restricted for sandboxed clients. **Undocumented/DE-internal; do not use.** [DOCS + CODE] https://raw.githubusercontent.com/KDE/plasma-wayland-protocols/master/src/protocols/kde-lockscreen-overlay-v1.xml , https://raw.githubusercontent.com/KDE/kwin/master/src/wayland_server.cpp
4. Design consequence: for "device B pushes a link to a locked device A", queue the link and open it when `LockedHint` turns false (plus a notification), rather than opening it into a hidden window. Opening arbitrary URLs automatically on a locked machine is also a drive-by risk, so it must require a paired and trusted sender. [INFER]

#### Q4. Screen capture and input injection while locked; how GNOME Remote Desktop, KRdp and RustDesk treat the lock and login screens; headless/virtual options

**Answer.** On GNOME the compositor kills all remote-access sessions on lock and refuses new ones (confirmed in source). On KDE I found no kill switch, but input is routed only to the lock screen, and KDE's own answer is a virtual monitor plus a greeter on the physical seat. On X11 there is no isolation, but the locker's grab captures injected input.

1. **GNOME: confirmed in source.** [CODE]
   - `gnome-shell/js/ui/main.js` (`_sessionUpdated`): when the session mode has `allowScreencast` false (every mode except `user`, which includes the locked `unlock-dialog` mode) and the backend is not headless, it calls `remoteAccessController.inhibit_remote_access()`; it uninhibits again when the user session is back. https://raw.githubusercontent.com/GNOME/gnome-shell/main/js/ui/main.js , https://raw.githubusercontent.com/GNOME/gnome-shell/main/js/ui/sessionMode.js
   - The `unlock-dialog` mode is pushed when the shield activates (`screenShield.activate()`), which can precede `LockedHint=true` by `lock-delay`. https://raw.githubusercontent.com/GNOME/gnome-shell/main/js/ui/screenShield.js
   - Mutter: `meta_remote_access_controller_inhibit_remote_access()` is documented "Inhibits remote access sessions from being created and running. Any active remote access session will be terminated."; the session managers registered with it are ScreenCast, RemoteDesktop and InputCapture; an inhibited manager closes all its sessions and answers new requests with "Session creation inhibited". https://raw.githubusercontent.com/GNOME/mutter/main/src/backends/meta-remote-access-controller.c , https://raw.githubusercontent.com/GNOME/mutter/main/src/backends/meta-dbus-session-manager.c , https://raw.githubusercontent.com/GNOME/mutter/main/src/backends/meta-backend.c
   - GNOME Shell NEWS 3.37.1: "Inhibit remote access when disabled by session mode". https://raw.githubusercontent.com/GNOME/gnome-shell/main/NEWS
   - GNOME Remote Desktop documents the consequence for its "remote assistance" mode: "locking the screen also closes the remote desktop connection". https://raw.githubusercontent.com/GNOME/gnome-remote-desktop/main/docs/configuration.md [DOCS]
   - Result: PipeWire ScreenCast portal, RemoteDesktop portal (libei input), portal clipboard and InputCapture (Deskflow-style KVM) are all unavailable while the GNOME session is locked, and any existing session is closed at lock time. Re-establishing after unlock needs a new session (restore tokens may avoid a prompt; not verified).
2. **GNOME alternatives that do work while the physical session is locked.**
   - GNOME Remote Desktop **headless single-user** (a separate headless graphical session, `gnome-remote-desktop-headless.service`) and **headless multi-user remote login** (RDP through GDM: system-wide password, then the GDM login screen, then the user's own login). These are independent of the physical session's lock. [DOCS] https://raw.githubusercontent.com/GNOME/gnome-remote-desktop/main/docs/configuration.md
   - Root-level framebuffer capture bypasses compositor policy: Sunshine's KMS capture ("DRM/KMS screen capture from the kernel. This requires that Sunshine has `cap_sys_admin` capability") and RustDesk's DRM backend (a root service exports the scanout buffer). Scope note: Android 17 (API 37) is the current release at the research date. #### Q6. Keeping a listener alive on Android: foreground service types, Doze, standby buckets, FCM, OEM killers, UDP/QUIC, battery, what existing apps do

**Answer.** A typed foreground service (FGS) is the only documented way to keep a process and its sockets running with the screen off. Whether such a service keeps *network* in Doze is contradicted inside Google's own docs (AOSP code says yes). Low Power Standby, when enabled, explicitly cuts network even for FGS apps. High-priority FCM is the documented wake-up path but needs Google services and a push sender. OEM task killers and Android 17's new local-network permission are the practical risks. I found no published battery measurement, and nothing here was tested on a device.

1. **FGS types that could host the listener.** [DOCS] https://developer.android.com/develop/background-work/services/fgs/service-types , https://developer.android.com/develop/background-work/services/fgs/timeout

| Type | What the docs say | Timeout | Fit for Baton (my assessment) |
|---|---|---|---|
| `connectedDevice` | "Interactions with external devices that require a Bluetooth, NFC, IR, USB, or network connection." Prerequisite: declare at least one of CHANGE_NETWORK_STATE, CHANGE_WIFI_STATE, CHANGE_WIFI_MULTICAST_STATE, NFC, TRANSMIT_IR (or hold a Bluetooth/UWB runtime permission, or a USB permission). | none documented | Best documented fit; it is what KDE Connect uses. [INFER] |
| `remoteMessaging` | "Transfer text messages from one device to another. Assists with continuity of a user's messaging tasks when they switch devices." No prerequisites. | none documented | Wording matches link/text handoff, but not file transfer; Play review risk. [INFER] |
| `specialUse` | Free-form use case declared in a manifest `<property>`, "reviewed when you submit your app in the Google Play Console". | none documented | Fallback; Syncthing-Fork ships this with a long justification text. |
| `dataSync` | Data transfer. Apps targeting Android 15+ get 6 hours per 24 hours, then `onTimeout()`; cannot be started from a BOOT_COMPLETED receiver. | 6 h / 24 h | Only for an in-progress transfer, never for an idle listener. |
| `mediaProjection` | Screen capture; user consent before the service starts. | none documented | Streaming only (Q9). |
| `systemExempted` | Reserved for demo mode, device owner, profile owner, emergency-role safety apps, device admin apps, holders of SCHEDULE_EXACT_ALARM or USE_EXACT_ALARM, and VPN apps; otherwise `ForegroundServiceTypeNotAllowedException`. | n/a | Not for Baton. Tailscale uses it as a VPN app. |

   - Only `dataSync` and `mediaProcessing` have the 6 h limit; `shortService` is about 3 minutes. [DOCS]
   - Play Console requires a declaration plus a video per FGS type; "All foreground service types are subject to review". Play maps connectedDevice to "Continuous Data Transfer to an External Device", remoteMessaging to "Relay text communication to another device" ("Not limited to SMS"), and specialUse to "limited scenarios". [DOCS*] https://support.google.com/googleplay/android-developer/answer/13392821
   - BOOT_COMPLETED receivers (Android 15+) may not launch dataSync, camera, mediaPlayback, phoneCall, mediaProjection or microphone services; connectedDevice, specialUse and remoteMessaging are not on that list, so a listener can be restarted at boot (after first unlock, because BOOT_COMPLETED is only delivered then; see Q8). [DOCS] https://developer.android.com/about/versions/15/behavior-changes-15
   - The user can stop the service: since Android 13 the notification-drawer Task Manager ("Active apps", Stop button) removes the whole app from memory and gives the app no callback (`ApplicationExitInfo.REASON_USER_REQUESTED` on next start). [DOCS] https://developer.android.com/develop/background-work/services/fgs/handle-user-stopping
2. **Starting or restarting an FGS from the background is restricted** (Android 12+). Exemptions that matter: a high-priority FCM message ("The system can downgrade the high priority messages ... If the message's priority is downgraded, your app cannot start a foreground service"), a user tap on a notification or widget, the Companion Device Manager permissions REQUEST_COMPANION_START_FOREGROUND_SERVICES_FROM_BACKGROUND or REQUEST_COMPANION_RUN_IN_BACKGROUND (both protection level `normal`), "The user turns off battery optimizations for your app", and a visible SYSTEM_ALERT_WINDOW overlay (Android 15+). [DOCS] https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start ; protection levels from https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/core/res/AndroidManifest.xml [CODE]
   - Android 15 also throws on network requests "outside of a valid process lifecycle" (typically `UnknownHostException` or another `IOException`), so sockets must be created and used while the FGS is running. [DOCS] https://developer.android.com/about/versions/15/behavior-changes-all
3. **Doze and the network: the sources disagree.**
   - Doze page: while in Doze the system "Suspends network access. Ignores wake locks." and defers jobs and standard alarms; there is no foreground-service carve-out on that page. [DOCS] https://developer.android.com/training/monitoring-device-state/doze-standby
   - "Power management resource limits" page, "Resource limits based on app state": "App process is running a foreground service ... Network: No restrictions"; in the device-state table, "Screen off and doze is active ... Network access: Restricted during doze". It adds that "the device state and app state can supersede app standby bucket limits". [DOCS] https://developer.android.com/topic/performance/power/power-details
   - AOSP code: `NetworkPolicyManager.isProcStateAllowedWhileIdleOrPowerSaveMode()` returns true when the process state is at least as important as `PROCESS_STATE_BOUND_FOREGROUND_SERVICE`, i.e. a running FGS keeps network in Doze. [CODE, undocumented platform behaviour] https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/core/java/android/net/NetworkPolicyManager.java
   - **Low Power Standby is different and documented:** "When Low Power Standby is enabled, apps (including apps running foreground services) are subject to additional restrictions while the device is non-interactive, outside of device idle maintenance windows: Their network access is disabled, and any wakelocks they hold are ignored." AOSP agrees (allowed only up to `PROCESS_STATE_BOUND_TOP`). The default on/off state of the feature was not found. [DOCS + CODE; default UNKNOWN] https://developer.android.com/reference/android/os/PowerManager (`isLowPowerStandbyEnabled`)
   - Net: a FGS probably keeps network in Doze on stock Android, and certainly does not in Low Power Standby. Test V-A1 and V-A2 in section 4.
4. **App Standby buckets and quotas.** [DOCS] https://developer.android.com/topic/performance/appstandby , https://developer.android.com/topic/performance/power/power-details
   - An app that "Runs a long running foreground service" is placed in the Active bucket. The restricted bucket (Android 12+) is entered after 8 days without user interaction on Android 13+ unless exempt; exemptions include companion device apps, VPN apps, apps the user set to "unrestricted", and apps with active widgets. In the restricted and rare buckets the bucket table lists network as "Disabled", but the app-state table says an FGS process has "No restrictions"; I did not find a statement that reconciles these two.
   - "User manually restricts app battery" sets jobs and alarms to restricted and leaves network "Access depends on standby bucket behavior".
   - Jobs (WorkManager) are not a substitute for a listener: Android 16 applies the job quota even to jobs running alongside an FGS. https://developer.android.com/about/versions/16/behavior-changes-all
5. **FCM as the wake-up channel.** [DOCS*] https://firebase.google.com/docs/cloud-messaging/android/message-priority
   - "FCM attempts to deliver high priority messages immediately, allowing FCM to wake a sleeping device when necessary and to run some limited processing (including very limited network access)." Normal priority "may be delayed" in Doze.
   - High priority is "meant for time sensitive, user visible content" and "should result in user-facing notifications"; otherwise "your messages may be deprioritized to normal priority or delegated for handling by Google Play services."
   - Since Android 13 the standby bucket no longer decides how many high-priority messages an app gets; the system downgrades senders whose messages do not produce notifications. [DOCS] https://developer.android.com/topic/performance/power/power-details
   - Consequences for Baton: a push wake needs a push sender (a server or relay, so not purely P2P), Google Play services on the phone, and a visible notification per wake. De-Googled phones cannot use it. Alternatives such as UnifiedPush were not researched. [INFER; UNKNOWN for alternatives]
6. **OEM killers and other non-AOSP behaviour.** dontkillmyapp.com is community-maintained; its own scale runs from 0 to 5 (5 is worst) and its pages carry a 2026-06-09 metadata date. [CODE, credible report*]
   - Samsung (5): "By default any app which is not started in 3 days is put to sleep and background tasks including alarms will stop working." and "Make sure Put unused apps to sleep and Auto-disable unused apps is disabled." The page also quotes a 07/2024 Samsung statement that "foreground services of apps targeting Android 14 will be guaranteed to work as intended" (relayed by the site; not independently checked). https://dontkillmyapp.com/samsung
   - Xiaomi (5): "In default settings, background processing simply does not work right and apps using them will break." Exemption needs autostart, "No restrictions" background settings and app locking. https://dontkillmyapp.com/xiaomi
   - OnePlus (5): "Deep optimization or Adaptive Battery" is "the main app killer"; "Sleep standby optimization ... will prevent push notifications from being delivered." https://dontkillmyapp.com/oneplus
   - Google/AOSP (0): "the lowest chance of something going wrong with background processing." https://dontkillmyapp.com/google
   - Google Play services reportedly reboots a phone after three days locked (72 hours; Play services 25.14; no user setting); afterwards the phone is Before First Unlock, so the listener is dead until the user unlocks once. [CODE, credible report*; Google has not documented it] https://cyberinsider.com/google-adds-auto-restart-to-android-to-block-unauthorized-data-extraction/
   - Android 17 adds app memory limits scaled to device RAM; an app that hits one is killed with `ApplicationExitInfo` reason `REASON_OTHER` and a description containing "MemoryLimiter:AnonSwap". A long-lived native QUIC process must not leak. [DOCS] https://developer.android.com/about/versions/17/behavior-changes-all
7. **Can a QUIC/UDP listener survive locked and idle? Three separate questions.**
   - *Process:* yes on stock Android with a typed FGS, unless the user stops it, an OEM kills it, memory limits fire, the 72-hour reboot happens, or the user is in Low Power Standby. [DOCS + CODE + credible reports]
   - *Network permission (Android 17):* for apps targeting SDK 37, "Traffic to and from a local network address requires local network access permission": "Accepting an incoming TCP connection" and "Receiving a incoming UDP unicast, multicast, broadcast" are both listed as requiring `ACCESS_LOCAL_NETWORK` ("These restrictions are implemented deep in the networking stack, and thus they apply to all networking APIs"). Android 16 was opt-in; Android 17 is mandatory for target SDK 37; the permission is in the NEARBY_DEVICES group; `.local` resolution is covered. If the user denies it, LAN traffic is blocked and Baton must use the relay path. A user who already granted another NEARBY_DEVICES permission is not prompted again. The documented alternative is a system picker: with `NsdManager` `DiscoveryRequest.FLAG_SHOW_PICKER` the user selects one device and "Connections to IP addresses obtained this way don't require the ACCESS_LOCAL_NETWORK permission"; that is a user-driven, per-device flow, so it can serve pairing but (my inference) not an unattended inbound listener. For revocation the page suggests a "permission reset counter" to re-ask later. KDE Connect and Syncthing-Fork already declare the permission in their manifests. [DOCS + CODE] https://developer.android.com/privacy-and-security/local-network-permission , https://developer.android.com/about/versions/17/behavior-changes-17
   - *Delivery latency while the screen is off:* the Wi-Fi radio saves power when idle. `WIFI_MODE_FULL_LOW_LATENCY` "is only active when the screen is on" and "when the acquiring app is running in the foreground"; `WIFI_MODE_FULL_HIGH_PERF` is deprecated since API 34 and now maps to the same restricted low-latency mode. [DOCS] https://developer.android.com/reference/android/net/wifi/WifiManager Multicast is filtered unless a `MulticastLock` is held ("can cause a noticeable battery drain"), so mDNS or broadcast discovery of a sleeping phone is unreliable; unicast to a known address is the dependable path. [DOCS + INFER] https://developer.android.com/reference/android/net/wifi/WifiManager.MulticastLock . How long an inbound unicast UDP packet takes to wake the CPU and reach the app, in Doze with an FGS held, is **unknown** (V-A3).
   - *NAT keep-alive:* while-idle alarms are limited to "7 per hour" in Doze and "once per nine minutes, per app" (Doze page), which is far slower than typical UDP NAT timeouts (my assumption; no source read). Android 17 adds `setExactAndAllowWhileIdle` with an `OnAlarmListener`, described as "ideal for apps that currently rely on continuous wakelocks to perform periodic tasks, such as messaging apps maintaining socket connections". [DOCS + INFER] https://developer.android.com/about/versions/17/features
8. **Battery cost.** No official or third-party measurement of a held FGS plus an idle UDP/QUIC socket was found. The only documented cost statements are qualitative (multicast lock "noticeable battery drain"; low-latency Wi-Fi "Battery life may be reduced"). Measure with the test in V-A4. [UNKNOWN]

#### Q7. Clipboard, FGS, accessibility, IME, overlays, Quick Settings tile, share target, notification actions and lock-screen APIs while the phone is locked

**Answer.** On a locked phone no third-party app can read the clipboard, whatever service type or permission it holds. Writing is allowed without focus. Overlays are hidden by the keyguard. Quick Settings tiles and notification actions can run code, optionally behind an unlock prompt. An activity can appear above the lock screen only if it was started legitimately (user tap, or a full-screen intent that Baton should not use).

1. **Reading the clipboard.** [DOCS + CODE]
   - Docs: "Unless your app is the default input method editor (IME) or is the app that currently has focus, your app cannot access clipboard data on Android 10 or higher." https://developer.android.com/about/versions/10/privacy/changes
   - AOSP `ClipboardService.clipboardAccessAllowed()` (reads): allowed for holders of `READ_CLIPBOARD_IN_BACKGROUND`, the default IME, the app whose window has focus, an app with INTERNAL_SYSTEM_WINDOW plus focus, the content-capture service, the augmented-autofill service, and the owner of a virtual device. Foreground services, accessibility services and overlays are **not** in the list. `READ_CLIPBOARD_IN_BACKGROUND` is protection level `signature|role` and marked "@hide Not for use by third-party applications". https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/services/core/java/com/android/server/clipboard/ClipboardService.java , https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/core/res/AndroidManifest.xml
   - **Locked device:** `getPrimaryClip`, `getPrimaryClipDescription`, `hasPrimaryClip`, `hasClipboardText` and `getPrimaryClipSource` each also return null/false when `KeyguardManager.isDeviceLocked(userId, deviceId)` is true, **even for the default IME or a focused app**. [CODE] (same file)
   - One unanswered forum post reports exactly this symptom with KDE Connect on Android 15: clipboard sharing works "except when the screen is locked" and SMS codes reach the desktop only when unlocked. [anecdotal; single post] https://discuss.kde.org/t/kde-connect-share-clipboard-when-screen-is-locked/34153
   - KDE Connect's Android clipboard workaround is **undocumented**, needs a permission granted over adb, and cannot work while locked (no activity can take focus under the keyguard). [CODE + INFER] https://raw.githubusercontent.com/KDE/kdeconnect-android/master/src/main/java/org/kde/kdeconnect/plugins/clipboard/ClipboardListener.kt
2. **Writing the clipboard.** `OP_WRITE_CLIPBOARD`: "Writing is allowed without focus", and `checkAndSetPrimaryClip` has no locked-device check. So B can push text into A's clipboard while A is locked; the user pastes after unlocking. The system auto-clears clips after `DEFAULT_CLIPBOARD_TIMEOUT_MILLIS = 3600000` (1 hour) unless DeviceConfig disables it. Whether Android 13+'s on-screen "copied" confirmation or any access notification fires for a background write was not checked. [CODE; UI behaviour UNKNOWN]
3. **Quick Settings tile.** `TileService.isLocked()`: "Checks if the lock screen is showing. When a device is locked, then showDialog(Dialog) will not present a dialog ... If the behavior of the Tile is safe to do while locked, then the user should use ContextWrapper.startActivity(Intent) to launch an activity on top of the lock screen, otherwise the tile should use unlockAndRun(Runnable) to give the user their security challenge." `isSecure()`: "TileServices should detect when the device is secure and change their behavior accordingly." [DOCS] https://developer.android.com/reference/android/service/quicksettings/TileService . Whether Quick Settings can be pulled down on the lock screen is a user/OEM setting that I did not verify. [UNKNOWN]
4. **Notification actions and visibility.** [DOCS]
   - `Notification.Action.Builder.setAuthenticationRequired(true)`: "the OS will show the keyguard and require successful authentication before invoking the intent. If this is false and the device is locked, the OS will decide whether authentication should be required." https://developer.android.com/reference/android/app/Notification.Action.Builder
   - `setVisibility`: VISIBILITY_PUBLIC (full content on all lock screens and while screen sharing), VISIBILITY_PRIVATE (conceal sensitive content on secure lock screens; supply `setPublicVersion()`), VISIBILITY_SECRET ("Do not reveal any part of this notification on a secure lockscreen"). "The user always has ultimate control over whether their notifications are visible on the lock screen." https://developer.android.com/reference/android/app/Notification , https://developer.android.com/develop/ui/views/notifications/build-notification
5. **Showing UI above the lock screen.**
   - `Activity.setShowWhenLocked(true)`: the activity "will remain in the resumed state visible on-top of the lock screen". `setTurnScreenOn(true)` turns the screen on when the activity resumes; together with `KeyguardManager.requestDismissKeyguard()` the screen turns on and the system shows the credential prompt (it does not bypass it). https://developer.android.com/reference/android/app/Activity
   - But the activity must first be *allowed to start*. Background activity launches are blocked except for a visible window, the current IME, a PendingIntent "sent by the system (for example, from a notification tap)", SYSTEM_ALERT_WINDOW holders and a few others. https://developer.android.com/guide/components/activities/secure-bal

[DOCS] https://developer.android.com/reference/android/app/Notification.Builder , https://source.android.com/docs/core/permissions/fsi-limits [DOCS*] , https://support.google.com/googleplay/android-developer/answer/13392821 [DOCS*]. Baton should not use it to open links.

[CODE, undocumented platform behaviour] https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/services/core/java/com/android/server/wm/WindowState.java , https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/services/core/java/com/android/server/policy/WindowManagerPolicy.java

[UNKNOWN] An IME is allowed to read the clipboard when focused and is a BAL exemption, but Baton as the user's keyboard is a heavy ask and unverified on the lock screen. [INFER]
8. **Share target.** Sharing *from* the phone needs an unlocked phone showing an app, so nothing to design for the locked case. [INFER]
9. **Recommended locked-phone UX:** a notification per incoming item with VISIBILITY_PRIVATE and a public version, and action buttons that call `setAuthenticationRequired(true)` ("Open link", "Copy text", "Save file"). That keeps content off the lock screen and makes the user prove presence before anything executes. [INFER]

#### Q8. Receiving a handoff on a locked phone: notification visibility, full-screen intents, opening a URL, saving files, Direct Boot

**Answer.** After the first unlock since boot, a typed FGS can receive data and write it to app-private storage even while the screen is locked. It cannot open a browser by itself; the user taps a notification and, if you require it, unlocks first. Before the first unlock nothing of Baton runs unless it is Direct Boot aware, and it cannot read its credential-protected pairing keys.

1. **Receiving:** FGS socket or FCM wake (Q6). The phone's CPU and radio behaviour while locked is covered there. [see Q6]
2. **Telling the user:** notification channel importance (heads-up needs high importance), `setVisibility`, public version (Q7). With `USE_FULL_SCREEN_INTENT` denied (Play default for non-calling apps), the lock screen shows an expanded heads-up notification for 60 seconds. [DOCS*] https://source.android.com/docs/core/permissions/fsi-limits ; https://developer.android.com/reference/android/app/NotificationManager (`canUseFullScreenIntent`: "If permission is denied, notification will show up as an expanded heads up notification on lockscreen.")
3. **Opening the URL:** only through a user tap on the notification or one of its actions; those PendingIntents are a documented background-launch exemption. With `setAuthenticationRequired(true)` the OS shows the keyguard first, then fires the `ACTION_VIEW`. Auto-opening on arrival would need a full-screen intent or SYSTEM_ALERT_WINDOW and is both policy-risky and unwise on a locked phone. [DOCS] (sources in Q7)
4. **Saving files:** [DOCS] https://developer.android.com/privacy-and-security/direct-boot
   - "Credential encrypted storage is available after the user has successfully unlocked the device and until the user restarts the device. If the user enables the lock screen after unlocking the device, credential encrypted storage remains available." So after one unlock per boot, a received file can be written into app-private (credential-encrypted) storage while the screen is locked. Writing into shared storage (MediaStore or a user-picked folder) while locked is presumably the same encryption class but was not documented; test V-A9. [DOCS + INFER]
   - Before the first unlock ("Before First Unlock", BFU): only device-encrypted storage, and "By default, apps don't run during Direct Boot mode"; components must be `android:directBootAware="true"` and receive `ACTION_LOCKED_BOOT_COMPLETED`. `ACTION_USER_UNLOCKED` and `ACTION_BOOT_COMPLETED` come only after the first unlock. https://developer.android.com/reference/android/content/Intent
   - Design consequence: pairing keys live in credential-encrypted storage, so a BFU phone cannot authenticate peers. Do not move keys into device-encrypted storage to "fix" this; it weakens protection for a stolen phone. A BFU phone is simply unreachable until first unlock; the sender should queue (Q12b). [INFER]
5. **Private space:** "When a user locks the private space, all apps in the private space are stopped, and those apps can't perform foreground or background activities, including showing notifications." If Baton is installed there it cannot receive while the space is locked. [DOCS] https://developer.android.com/about/versions/15/behavior-changes-all
6. **Smart Lock:** `KeyguardManager.isDeviceLocked()` treats a device kept unlocked by a trusted Bluetooth device or trusted location as unlocked. A "locked" test must use the same call the system uses, or the app will behave as if locked when the user's phone is effectively open. [DOCS] https://developer.android.com/reference/android/app/KeyguardManager

#### Q9. Android as a streaming source: MediaProjection consent, behaviour on lock, input injection, Play policy, scrcpy and RustDesk

**Answer.** An Android phone can be streamed only while unlocked and after a fresh system consent dialog; the projection ends when the keyguard appears. Remote input needs an AccessibilityService (Play-policy-sensitive, may be blocked by Advanced Protection Mode) or shell-level privileges (adb, Shizuku). Nothing lets a normal app see or drive the lock screen.

1. **Consent per session.** "Your app must request user consent before each media projection session. A session is a single call to `createVirtualDisplay()`. A MediaProjection token must be used only once"; on Android 14+ reuse throws `SecurityException`. [DOCS] https://developer.android.com/media/grow/media-projection . Since Android 10 the dialog cannot be hidden on future requests ("the dialog shows every time"). [DOCS*] https://source.android.com/docs/core/permissions/restricted-screen-reading . Android 14 added single-app sharing.
2. **Behaviour on lock.** Android 15 QPR1 and higher: a status-bar chip alerts the user and "screen projection automatically stops when the device screen is locked"; the doc states the app "automatically suspends screen projection when the lock screen activates". [DOCS] https://developer.android.com/about/versions/15/behavior-changes-all
   - AOSP code (`MediaProjectionStopController`): on keyguard lock it fires `STOP_REASON_KEYGUARD`, and `isStartForbidden()` refuses to start a projection while the keyguard is showing, unless the grant is exempt. Both paths sit behind the flag `mediaProjectionKeyguardRestrictions` (the docs say the behaviour ships from Android 15 QPR1; I cannot see the release flag value). Exemptions: the "Disable Screenshare protections" developer option; the `RECORD_SENSITIVE_CONTENT` permission (protection level `signature`, @hide); the `OP_PROJECT_MEDIA` appop ("Some tools use media projection by granting the OP_PROJECT_MEDIA app op via a shell command"); the `COMPANION_DEVICE_APP_STREAMING` role (needs `REQUEST_COMPANION_PROFILE_APP_STREAMING`, `signature|privileged`, "Not for use by third-party applications"); bugreport-allowlisted packages; or a projection with no VirtualDisplay. [CODE, **undocumented platform behaviour**] https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/services/core/java/com/android/server/media/projection/MediaProjectionStopController.java , https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/core/res/AndroidManifest.xml , https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/core/java/android/companion/AssociationRequest.java
   - A remote-support vendor documents an adb-set app operation that makes the grant permanent across reboots, and the vendor says the device must be physically accessible and unlocked to run it and that this is not a public API surface. [CODE, vendor doc*] https://docs.tsplus.net/remote-support-v3/android-permanently-enable-project-media-permission . This depends on **undocumented** appops and on USB debugging; do not build on it.
   - Even exempt projections do not capture the keyguard: it is `FLAG_SECURE`; the scrcpy maintainer says it "cannot be mirrored anymore with shell permissions since Android 12". [CODE, credible report*] https://github.com/Genymobile/scrcpy/issues/5625 , https://github.com/Genymobile/scrcpy/issues/5391
3. **Input injection.**
   - `AccessibilityService.dispatchGesture` / `performGlobalAction` with `android:canPerformGestures="true"`: what RustDesk's Android host uses. The user has to enable the service in Settings. https://raw.githubusercontent.com/rustdesk/rustdesk/master/flutter/android/app/src/main/kotlin/com/carriez/flutter_hbb/InputService.kt , https://raw.githubusercontent.com/rustdesk/rustdesk/master/flutter/android/app/src/main/res/xml/accessibility_service_config.xml [CODE]
   - Play policy: the AccessibilityService API is not blocked, but needs prominent in-app disclosure and a Console declaration; only apps "designed to help people with disabilities" may be labelled accessibility tools, and "automation tools, assistants, monitoring apps" are listed as non-qualifying; "Any use of the Accessibility API that enables an app to autonomously initiate, plan, and execute actions" is prohibited. Remote control is not mentioned on the page. [DOCS*] https://support.google.com/googleplay/android-developer/answer/10964491
   - Android 17 Advanced Protection Mode (opt-in) blocks sideloading and restricts USB data signalling (official), and Android 17 Beta 2 reportedly stops non-accessibility apps from using the AccessibilityService API while it is on. [DOCS for AAPM; CODE, credible report* for the accessibility part, beta-time, not in stable docs] https://developer.android.com/about/versions/17/features , https://thehackernews.com/2026/03/android-17-blocks-non-accessibility.html
   - `INJECT_EVENTS` is `signature` ("Not for use by third-party applications"). adb/shell-level injection works through Shizuku, which "guides users to run a process, Shizuku server, with root or ADB first" and relays calls to system services; it relies on **undocumented** system APIs and an adb-privileged helper. [CODE] https://raw.githubusercontent.com/RikkaApps/Shizuku/master/README.md . Whether a Shizuku grant survives reboot without re-running adb was not verified. [UNKNOWN]
   - scrcpy: its physical-keyboard mode and its separate virtual display both need USB debugging enabled on the phone. [CODE, credible report*] scrcpy issues above; https://raw.githubusercontent.com/Genymobile/scrcpy/master/doc/keyboard.md
4. **RustDesk on Android (source).** MediaProjection FGS + AccessibilityService; when the screen is off and a touch event arrives it acquires a `SCREEN_BRIGHT_WAKE_LOCK | ACQUIRE_CAUSES_WAKEUP` wake lock for 5 seconds to turn the screen on; on `MediaProjection.Callback.onStop` it tears capture down and asks again (a transparent permission activity, so a user must be present); notification `lockscreenVisibility = VISIBILITY_PRIVATE`. I found no code that unlocks the phone. [CODE] `MainService.kt` link in Q6.
5. **Distribution.** Android developer verification takes effect September 30, 2026 for installs from participating stores in Brazil, Indonesia, Singapore and Thailand on certified Android 7+ devices, and expands globally in 2027; there is a "Register an open source app" guide and a limited-distribution account. Baton's Android build will have to be registered. [DOCS] https://developer.android.com/developer-verification

#### Q10. Detecting lock, unlock and screen state on Android

**Answer.** There is no public broadcast for "device locked". Use `ACTION_SCREEN_OFF`, `ACTION_SCREEN_ON` and `ACTION_USER_PRESENT` as triggers and `KeyguardManager.isDeviceLocked()` as the source of truth. The listener APIs need a signature/assistant permission.

Full signal list is in section 5. Behaviour notes: [DOCS] https://developer.android.com/reference/android/content/Intent , https://developer.android.com/reference/android/app/KeyguardManager , https://developer.android.com/reference/android/os/PowerManager

- `ACTION_SCREEN_OFF` / `ACTION_SCREEN_ON`: "the name of this broadcast action refers to the power state of the screen but it is actually sent in response to changes in the overall interactive state of the device"; "You cannot receive this through components declared in manifests, only by explicitly registering for it with Context.registerReceiver()". An FGS can register in `onCreate` (KDE Connect does for SCREEN_ON).
- `ACTION_USER_PRESENT`: "Sent when the user is present after device wakes up (e.g when the keyguard is gone)."
- `isKeyguardLocked()` is true while the lock screen is "showing", "regardless of whether the screen happens to be on", and even when the lock screen is only a swipe. `isDeviceLocked()` means authentication is required; "Swipe does not count as authentication", and a device kept unlocked by a trusted Bluetooth device or location "is considered unlocked". `isDeviceSecure()` says whether a PIN/pattern/password is configured, independent of the current state.
- `addKeyguardLockedStateListener` (API 33) and `addDeviceLockedStateListener` (API 36.1) both "Require Manifest.permission.SUBSCRIBE_TO_KEYGUARD_LOCKED_STATE", which AOSP declares `signature|module|role` ("Intended for use by ROLE_ASSISTANT and signature apps only"). A normal app cannot use them. [DOCS + CODE]
- `UserManager.isUserUnlocked()`, `ACTION_USER_UNLOCKED` ("credential-encrypted private storage has become unlocked"; registered receivers only) and `ACTION_LOCKED_BOOT_COMPLETED` tell BFU from AFU. `Intent.ACTION_BOOT_COMPLETED` fires after the first unlock.
- Private space: register for `ACTION_PROFILE_AVAILABLE` / `ACTION_PROFILE_UNAVAILABLE` and call `UserManager.isQuietModeEnabled()`. https://developer.android.com/about/versions/15/behavior-changes-all
- Doze and standby state: `PowerManager.isDeviceIdleMode()` with `ACTION_DEVICE_IDLE_MODE_CHANGED`, `isDeviceLightIdleMode()`, `isLowPowerStandbyEnabled()` with `ACTION_LOW_POWER_STANDBY_ENABLED_CHANGED`, `isPowerSaveMode()`, `isIgnoringBatteryOptimizations(pkg)`.
- Companion Device Manager presence (`startObservingDevicePresence(ObservingDevicePresenceRequest)`, `REQUEST_OBSERVE_COMPANION_DEVICE_PRESENCE`) reports Bluetooth LE range and Bluetooth connection changes only: "WiFi devices are not supported." It binds your `CompanionDeviceService` on presence, and associated apps can use the REQUEST_COMPANION_* background permissions (Q6). https://developer.android.com/reference/android/companion/CompanionDeviceManager , https://developer.android.com/develop/connectivity/bluetooth/companion-device-pairing
- Race conditions and the need to re-check after each broadcast are my inference, not documented. [INFER]

### Part C: Existing tools and design techniques

#### Q11. What existing remote-access tools do to the physical screen and local input, and what a person at the keyboard can do

**Answer.** No tool I could verify protects a *locked, unattended* machine by itself. They fall into three groups: (1) tools that connect with stored credentials and then rely on an opt-in privacy feature (RustDesk, AnyDesk, Parsec); (2) tools that move the remote user to a different session so the console is never shared (Chrome Remote Desktop, KRdp exclusive mode, GNOME Remote Desktop headless, Apple virtual display, Apollo virtual display); (3) tools that mirror the physical session and openly assume a cooperative person at the keyboard (VNC servers, Sunshine). Several privacy features are requested by the *controlling* side or stop working exactly at the lock and secure-desktop transitions. GNOME Remote Desktop and KRdp are covered in Q4. #### Q12. Cross-cutting design techniques for "works while the source is locked", evaluated

Labels: facts are marked as elsewhere; everything marked **[IDEA]** is my design proposal, supported only by the cited facts and untested.

**Answer.** Of the five techniques, (a) and (b) together are the only ones that satisfy "the source may be locked, asleep or unreachable" for discrete items (URL, text, file) on every platform I examined, because neither needs the source after the push. (c) is a best-effort helper, not a guarantee. (d) is the only verified route to streaming from a desktop whose physical session is locked, and it changes the product from "the windows I left" to "a session I can use". (e) is cheap on Linux and needs a privileged or accessibility API on Android. None of them lets Baton read a locked GNOME clipboard or capture a locked Android screen.

**What each technique can deliver when the source is locked**

| Payload | (a) push snapshot | (b) mailbox | (c) wake | (d) separate session | (e) auto-lock |
|---|---|---|---|---|---|
| Discrete item (URL, text, file) already staged | Yes | Yes, also when the target is offline | Not needed | Not needed | Safe afterwards |
| Continuous clipboard | Only where a background read is possible: X11 yes, KDE yes (Q2); GNOME and Android no | Same limit at the source | n/a | n/a | n/a |
| Live window stream or remote input | No | No | Wakes hardware only; machine comes back locked | Only verified route on GNOME (Q4.2); on KDE capture of the locked session is unverified and KRdp exclusive mode is KDE's own route (Q4.3); not available on Android | Lock after the stream ends |

**(a) Push a snapshot at lock or sleep**
1. *Triggers that exist.* Linux: logind `Lock` signal, `LockedHint` change, `PrepareForSleep(true)` with a `delay` inhibitor of at most `InhibitDelayMaxSec` (default 5 s); GNOME and KDE both lock *before* sleeping through a sleep delay inhibitor (Q1, Q5). Android: `ACTION_SCREEN_OFF` in a dynamically registered receiver, then `KeyguardManager.isDeviceLocked()`; there is no "about to lock" callback (Q10). [DOCS/CODE]
2. *The lock does not stop a push.* Locking leaves processes and sockets running (Q1), so an agent can send at the lock event on Linux. The 5 s sleep window is unreliable because the network may already be going down. [CODE + INFER] Prefer the lock event, not `PrepareForSleep`.
3. *What can be read at that moment is the limit.* GNOME shuts ScreenCast, RemoteDesktop and portal clipboard at shield activation (Q4) and has no background clipboard access at all (Q2); Android returns null for background clipboard reads and for any read while locked (Q7). A snapshot at lock time therefore cannot contain "whatever is in the clipboard" on GNOME or Android. The data must already be in Baton's hands: an explicit "Send to my other device" gesture (share target, tray menu, hotkey, notification action, all of which run while the user is present), or continuous mirroring where the platform allows it (X11, KDE). [INFER from Q2, Q4, Q7]
4. *Unwanted pushes.* Many locks are idle timeouts with the user still around. An implicit push at every lock would deliver content to other devices nobody asked for. Stage it instead (technique b) and surface it on the other device only when the user asks for it. [IDEA]
5. *Security.* The push happens while the user is physically present, so no extra authentication is needed at the source; the receiver must still treat it as untrusted input (see the threat model below).
6. *Verdict.* Primary mechanism for discrete items. It removes any dependence on the source being reachable afterwards. It does not cover streaming.

**(b) End-to-end encrypted store-and-forward relay mailbox**
1. *Precedents.* Magic Wormhole's rendezvous server keeps "an unordered set of messages" per mailbox, "queued for delivery to clients which connect later", persisted in a database; all messages except the PAKE setup are encrypted "so the server cannot read the contents"; phases are visible; the server neither de-duplicates nor orders messages (clients must), and mailboxes disappear after a period of inactivity with no fixed duration given. [DOCS*] https://magic-wormhole.readthedocs.io/en/latest/server-protocol.html . FCM is a store-and-forward channel for small payloads: "If the device isn't connected to FCM, the message is stored until a connection is established", default and maximum lifetime four weeks (28 days) on Android, data messages "can have a 4KB maximum payload", and at most 100 pending non-collapsible messages before "all stored messages are discarded". [DOCS*] https://firebase.google.com/docs/cloud-messaging/customize-messages/setting-message-lifespan , https://firebase.google.com/docs/cloud-messaging/concept-options . Tailscale's Taildrop page says transfers are "encrypted peer-to-peer" and that an interrupted transfer can resume "for up to an hour", but does not say what happens when the receiver is offline, asleep or locked. [DOCS*] https://tailscale.com/kb/1106/taildrop
2. *Properties a Baton mailbox would need.* All **[IDEA]**:
   - Opaque ciphertext plus minimal routing data; sender authenticated by a key from pairing; per-item sequence numbers and a replay window kept by the receiver (the relay may not dedupe, per Wormhole); short default TTL; per-device quotas; delete on acknowledgement; revoke purges a device's mailbox.
   - Large files: upload an encrypted blob and send only its content key and location in the small message, which also fits FCM's 4 KB limit if FCM is the wake channel.
   - The relay learns who talks to whom, when and how much. Padding, rotating mailbox identifiers and not logging addresses reduce this; they do not remove it.
   - A compromised relay can drop, delay, replay and traffic-analyse, but must not be able to read or forge items.
3. *Locked receivers.* Items addressed to a locked device should be decrypted only after unlock. Android documents a fitting primitive: for a key generated with `setUnlockedDeviceRequired(true)`, "Public key operations aren't restricted ... and may be performed even while the device is locked", while private-key use waits for unlock. So the relay or a sender can encrypt to the phone's Keystore public key while the phone is locked, and only an unlocked phone can open it. Caveats from the same page: Android 12 to 14 had bugs (keys unusable without a secure lock screen, deleted when the lock screen is removed, not re-authorised by non-strong biometrics). [DOCS] https://developer.android.com/reference/android/security/keystore/KeyGenParameterSpec.Builder . I found no equivalent OS-level control on Linux; whether GNOME Keyring or KWallet stay unlocked while the screen is locked was not checked. [UNKNOWN]
4. *Verdict.* Required wherever the target can be asleep, in Doze, before first unlock or on another network. Cost: a relay with state, and retention policy decisions.

**(c) Wake mechanisms**
1. *Wake-on-LAN from another paired device.*
   - Mechanism: a magic packet is 6 bytes of 0xFF, 16 copies of the target MAC, optionally followed by a password; "sent in the clear, making it vulnerable to eavesdropping". [DOCS*] https://datatracker.ietf.org/doc/html/draft-cheshire-edns0-owner-option (an expired individual draft that describes the packet while discussing Sleep Proxy). Linux enablement, NetworkManager properties, WoWLAN driver limits and the same-L2-segment requirement are in Q1.6. KDE re-suspends 30 s after a network wake unless user activity is registered (Q1.6). Whether wake works from s2idle on a given machine is unknown (V-L4).
   - Android as the sender: sending a UDP broadcast needs `ACCESS_LOCAL_NETWORK` ("Sending a UDP unicast, multicast, broadcast: yes") for apps targeting SDK 37; denial blocks it. [DOCS] https://developer.android.com/privacy-and-security/local-network-permission
   - Verdict: best-effort, hardware dependent, unauthenticated by design (it can only wake; the machine returns to the lock screen). Worth offering as an option, never as a requirement.
2. *Bonjour Sleep Proxy.* A sleeping host registers its records with a proxy on the LAN; the proxy answers for it and sends a magic packet when traffic arrives, and stops proxying when the host wakes. The only specification I could open is an expired individual Internet-Draft (draft-cheshire-edns0-owner-option-01, 2017) with an EDNS0 "Owner" option carrying MAC addresses, a sequence number and an optional password; its only security note is that the magic packet is sent in the clear. [DOCS*] URL above. Apple's Bonjour overview page does not mention Sleep Proxy. Avahi's `docs/TODO` lists "sleep proxy" and "goodbye/hello on sleep/suspend/wake" as not yet done (the file is undated). [CODE] https://raw.githubusercontent.com/avahi/avahi/master/docs/TODO . I found no sleep-proxy client or server for Linux, Windows or Android. Verdict: Apple-ecosystem only; not a cross-platform wake mechanism. [INFER]
   - Correction (review, 2026-10-14): the verdict above is too strong. The documentation of a tool that runs on Windows, Linux and macOS says that it speaks the Sleep Proxy protocol as a proxy and as a client. See review-additions.md, which gives the pages and the quotations.
3. *Push to a mobile app.* High-priority FCM can wake a sleeping Android device but must produce a user-visible notification or it is deprioritised; limits are in Q6.5 and the FGS-start exemption in Q6.2. Pushing to a *desktop* has no equivalent: a suspended Linux desktop has `user.slice` frozen (Q1.2), so the only desktop wake paths are WoL, a hardware RTC alarm, or the user opening the lid. A systemd timer with `WakeSystem=true` "will cause the system to resume from suspend", but "this functionality requires privileges and is thus generally only available in the system service manager", and it does not suspend the machine again. [DOCS] https://raw.githubusercontent.com/systemd/systemd/main/man/systemd.timer.xml . Verdict: use FCM for Android; for desktops combine the relay mailbox with WoL as an optional extra. [IDEA]
4. *Wake does not unlock.* After any wake the machine is at the lock screen. Wake solves reachability for the agent, not capture or input.

**(d) Separate session, VM or container**
1. *Evidence that it works.* GNOME Remote Desktop headless single-user and multi-user modes (Q4.2); KRdp exclusive mode with a virtual monitor and the physical seat switched to the greeter (Q4.3); Chrome Remote Desktop's Linux Virtual Me2Me, Windows loopback-RDP and macOS switched-out session (Q11); Apollo's per-stream virtual display on Windows; Apple's "Connect to a virtual display" mode. [DOCS/CODE]
2. *What it changes.* The remote user gets a *new* desktop, not the windows left open on the locked one. Continuity then has to come from files, URLs and application profiles, which Baton would have to carry (technique a/b). Whether two sessions can share one browser profile or application state was not examined. [UNKNOWN]
3. *Weak points seen in source.* KRdp's exclusive mode deliberately unlocks the user's session behind the greeter, and its own comments say VT switching must not be allowed to break things, so someone at the keyboard may reach an unlocked desktop (Q4.3, must test: V-K5). Chrome Remote Desktop on macOS leaves the user's session logged in (switched out) while connected. A headless session as the same user is not isolated from a compromised agent: it is the user's account. [CODE + INFER]
4. *VM or container.* Heavier, with no access to the user's real apps and GPU, and a container does not isolate the agent from the user's own session. I found no evidence supporting it for this use. [IDEA, not recommended]
5. *Verdict.* Needed only if Baton promises streaming from a source that stays locked. For Android there is no equivalent (Q9).

**(e) Proximity or event-based auto-lock after a successful handoff**
1. *Locking is a safe-direction action and is easy on Linux.* logind `Session.Lock` (or `loginctl lock-session`) is honoured by GNOME Shell and kscreenlocker and is allowed for the session owner without polkit (Q5). RustDesk locks through `xdg-screensaver lock` (Linux), `CGSession -suspend` (macOS) and `LockWorkStation` (Windows). [CODE]
2. *On Android the lock needs a privileged or accessibility route.* `DevicePolicyManager.lockNow()` ("Make the device lock immediately, as if the lock screen timeout has expired") needs the app to be an activated device administrator (the device-administration guide lists a `<force-lock />` policy in the admin metadata and shows `dpm.lockNow()` in its "Set device lock" section; I did not see the permission sentence in the reference text). The same guide carries a banner that some admin policies have been deprecated since Android 9, and I could not open the deprecation page, so whether `force-lock` is affected is unknown. `AccessibilityService.GLOBAL_ACTION_LOCK_SCREEN` ("Action to lock the screen", API 28) needs an enabled accessibility service with the Play policy consequences in Q9. [DOCS] https://developer.android.com/guide/topics/admin/device-admin , https://developer.android.com/reference/android/accessibilityservice/AccessibilityService
3. *Trigger choice.* Event-based is better supported than proximity: lock A when B reports that the handoff finished *and* B is unlocked and in use. Bluetooth proximity needs BLE signal-strength heuristics that I did not research; on Android, Companion Device Manager presence reports only Bluetooth LE and Bluetooth connection changes ("WiFi devices are not supported") (Q10). [IDEA]
4. *Ordering.* Lock only after the transfer is acknowledged: on GNOME the lock kills remote-access sessions at once (Q4.1), and any transfer that depends on them dies.
5. *Abuse.* A remotely triggerable lock lets a compromised paired device lock the user out repeatedly (nuisance, not disclosure); rate-limit it. The reverse command must not exist: KDE Connect implements remote Unlock, on by default (Q11), and a same-uid process can already call logind `Unlock` (Q5), so Baton must never add an unlock path. [CODE + IDEA]
6. *Verdict.* Directly addresses the concern ("I don't want to leave my previous device unlocked") for devices where locking is a one-line call; offer it as an optional "lock the old device when handoff completes" setting.

**Threat model: someone steals the *locked* device while the agent is running and the network is up**

Evidence-backed facts first, then design proposals. Assets: pairing and identity keys, queued or staged content, the ability to send items to the person's other devices, and mailbox access at the relay.

| # | Attack | Basis | Mitigation (all [IDEA] unless marked) |
|---|---|---|---|
| 1 | Probe the running agent's listener over the LAN or the relay | The lock stops nothing (Q1); Android keeps the FGS alive (Q6) | Mutual authentication in the first flight, no parsing of unauthenticated input beyond the handshake, rate limits, nothing served to unpaired peers. |
| 2 | Use the stolen device's keys to push malicious URLs or files to the person's other devices | The agent holds the private key while locked | Receiver never auto-opens; shows sender; per-peer rights (for example links yes, files only into quarantine); quick revoke from any other paired device, propagated through the relay; trust expires after N days without contact. |
| 3 | Read content queued for the stolen device | The agent can decrypt while running | Encrypt queued items to a key that is usable only after unlock: Android Keystore `setUnlockedDeviceRequired(true)` [DOCS]; on Linux no equivalent found [UNKNOWN]. Short TTL; revoke purges the mailbox. |
| 4 | Turn the agent into an unlocker | Any same-uid process can call logind `Unlock` and GNOME and KDE obey [CODE] | Baton never calls `Unlock`; no remote-unlock feature (KDE Connect has one [CODE]); run the agent under systemd user-unit hardening [IDEA]. The lock is not a barrier against malware running as the user. |
| 5 | Leak incoming content on the lock screen | Android notification visibility is user-controlled [DOCS]; GNOME hides notifications in locked mode (`hasNotifications` false) [CODE]; KDE lock-screen notifications not checked [UNKNOWN] | `VISIBILITY_PRIVATE` with a public version; actions with `setAuthenticationRequired(true)` (Q7); queue and show after unlock. |
| 6 | Auto-open or auto-save content received while locked | Drive-by risk (Q3) | Locked mode is receive-to-quarantine only: no URL opening, no clipboard write, no file execution until unlock. |
| 7 | Physical attacks that skip the lock (boot from USB, DMA, cold boot) | Out of scope for the agent; Android credential-encrypted storage stays available from first unlock until reboot [DOCS]; a reported 72-hour auto-reboot returns the phone to Before First Unlock [CODE*] | Full-disk encryption on Linux; do not keep long-term keys unprotected; accept that an After-First-Unlock phone is more exposed than a rebooted one. |
| 8 | Relay compromise or traffic analysis | Wormhole precedent [DOCS*] | End-to-end encryption and signatures; padding; minimal retention. |
| 9 | Wake a stolen sleeping laptop | Magic packet is unauthenticated and in the clear [DOCS*] | Only wakes; the machine returns to the lock screen. Low risk. |
| 10 | Lock-out abuse by a compromised paired device | Remote lock exists in KDE Connect [CODE] | Rate-limit and notify on lock requests. |

**Suggested composition [IDEA].** Treat "locked" as a mode, not an obstacle: (1) stage before the user leaves (a) into an E2EE mailbox (b); (2) while `LockedHint` is true or `isDeviceLocked()` is true, the agent serves only what was staged, accepts items only into a quarantine queue, never initiates, never controls; (3) wake helpers (c) are optional; (4) streaming from a locked desktop, if promised at all, comes from a separate session (d) and ends with an automatic lock (e); (5) no remote unlock anywhere. The rest of this report says what is verified and what must be tested before relying on it.

## 4. Must verify on real hardware

Nothing in this report was tested on a device. Each item names what is unknown, the exact test, and what the result decides. **P1** means the result can change whether the "works while locked" promise is possible at all. Record OS and compositor versions, hardware, and firmware settings with every result. For adb-based tests, `adb shell dumpsys deviceidle force-idle deep` forces deep Doze and `adb shell dumpsys deviceidle unforce` and `adb shell dumpsys battery reset` undo test state; a forced state is not the same as natural Doze (see V-A3).

### Linux, any desktop (logind, power, network)

- **V-L1 (P2). Lid close against inhibitors.** Unknown: resulting behaviour on GNOME and KDE (Q1.5). Test: on a laptop with no external monitor, run `systemd-inhibit --what=sleep --who=baton-test --why=test --mode=block sleep 3600`, lock the screen, close the lid, watch `journalctl -u systemd-logind -f`; repeat with `--what=handle-lid-switch`, and again with an external monitor attached. Decides: whether any inhibitor can keep a locked laptop reachable with the lid closed (documented answer: only `handle-lid-switch`).
- **V-L2 (P1). Idle suspend while locked, and polkit for inhibitors taken by a user service.** Unknown: whether `systemd --user` services may take `block` and `delay` inhibitors (Q1.4). Test: `systemd-run --user --unit=baton-inh systemd-inhibit --what=sleep --mode=delay --who=baton --why=test sleep 600` and the same with `--mode=block`; check `systemd-inhibit --list` and the exit status. Then set auto-suspend to 1 minute (GNOME: `gsettings set org.gnome.settings-daemon.plugins.power sleep-inactive-ac-timeout 60`; KDE: System Settings, Power Management, suspend after 1 minute), lock, and record the time the machine stops answering a UDP echo from another device and the `PrepareForSleep` signal (`busctl --system monitor org.freedesktop.login1`). Decides: whether a locked, idle desktop can be kept awake by a normal user service (and whether it should be).
- **V-L3 (P1). Reachability while locked.** Unknown: LAN and relay reachability of a user-service UDP/QUIC listener with the lock engaged and the screen blanked. Test: run a UDP echo as a user service, lock (`loginctl lock-session`), let DPMS blank the screen, and ping the echo from a phone every 30 s for 2 hours on GNOME, KDE and one X11 session; log `loginctl show-session "$XDG_SESSION_ID" -p LockedHint -p IdleHint`; repeat with Wi-Fi power save on and off (`iw dev <if> get power_save`). Decides: Q1's "locking stops nothing" in practice, and the latency cost of Wi-Fi power save.
- **V-L4 (P1). Wake-on-LAN.** Unknown: whether WoL and WoWLAN work from `s2idle` and from S3 on the target machines, and what happens after the wake on KDE (30 s re-suspend). Test: `ethtool <if> | grep Wake-on`, `sudo ethtool -s <if> wol g`, suspend (`systemctl suspend`), send a magic packet from a second device on the same segment (any sender, for example `wakeonlan`), record success per sleep state, wired and Wi-Fi; on KDE time how long the machine stays awake after the packet with no input and with an `org.freedesktop.ScreenSaver.SimulateUserActivity` call from a client. Decides: whether WoL is worth offering at all.
- **V-L5 (P2). What a `PrepareForSleep` hook can still do.** Test: a client that takes a `delay` inhibitor and, on `PrepareForSleep(true)`, sends a UDP packet to a LAN peer and logs the result and timestamp, compared with NetworkManager's sleep log lines in `journalctl`. Decides: whether "push at sleep" is ever viable (Q12a assumes not).
- **V-L6 (P1, security). Same-user unlock.** Test: `loginctl lock-session`, then from an SSH session of the same user (not root, no sudo) `loginctl unlock-session`; repeat from a `systemd --user` service; on GNOME and KDE. Decides: confirmation of the Q5 claim that any same-uid process can unlock; therefore Baton must never expose unlock.
- **V-L7 (P2). `xdg-screensaver lock` and `LockedHint` for other lockers.** Test: run `xdg-screensaver lock` on GNOME, KDE, Xfce, Cinnamon and an i3 session with `xss-lock`; after each, read `loginctl show-session "$XDG_SESSION_ID" -p LockedHint`; also try swaylock, i3lock, hyprlock. Decides: whether `LockedHint` is a reliable cross-desktop lock signal (Q5) and whether RustDesk's lock call works.
- **V-L8 (P2). Signal timing.** Test: `dbus-monitor --session "interface='org.gnome.ScreenSaver'"` (GNOME) or `"interface='org.freedesktop.ScreenSaver'"` (KDE) plus `busctl --system monitor org.freedesktop.login1` while locking by hotkey, by idle timeout, by lid close; record the order and delay between `Lock`, `ActiveChanged(true)` and `LockedHint=true` and the `lock-delay` effect on GNOME. Decides: the right trigger for Q12a.

### X11 (Xfce, Cinnamon, MATE, i3)

- **V-X11 (P2). Clipboard, input and capture under lockers.** For each of xsecurelock, i3lock (with `xss-lock`), xfce4-screensaver, cinnamon-screensaver, mate-screensaver, light-locker: lock, then from SSH with `DISPLAY` and `XAUTHORITY` set run `xclip -selection clipboard -i <<< test` and `xclip -selection clipboard -o`; `xdotool key a` (note where the key lands); `xdotool search --onlyvisible --name .`; `import -window root /tmp/s.png` and inspect it. Decides: Q2.1 and Q4.4 (all currently inferred).

### Android (stock and OEM)

- **V-A1 (P1). Does a foreground service keep network in Doze?** Test: app with a `connectedDevice` FGS (and `ACCESS_LOCAL_NETWORK` granted) holding a UDP echo socket; screen off, device stationary and unplugged; `adb shell dumpsys deviceidle force-idle deep`; from a LAN host send one UDP packet every 10 s for 10 minutes and record replies; repeat charging, and with the FGS stopped as control. Decides: the Doze-page versus AOSP-code conflict (Q6.3).
- **V-A2 (P1). Low Power Standby.** Test: on Android 16/17 Pixel and one Samsung, check Settings, Battery for Low Power Standby, record its default state, enable it, and repeat V-A1 with the screen off; log `PowerManager.isLowPowerStandbyEnabled()` and `ACTION_LOW_POWER_STANDBY_ENABLED_CHANGED`. Decides: whether the feature breaks an FGS listener by default and whether Baton must ask the user to exempt it.
- **V-A3 (P1). Natural (not forced) deep sleep latency.** Test: leave the phone idle overnight, screen off, unplugged, on home Wi-Fi, with the FGS and an echo socket; from a LAN host send a packet at 5, 15, 30, 60 and 120 minutes of idleness (10 trials each) and log latency and loss; repeat with the keepalive sent by the phone at 30 s, 5 min and 15 min and record when the router's NAT or the phone's Wi-Fi power save drops the path; note router DTIM settings. Decides: whether direct LAN reachability of a sleeping phone is real, and what relay/FCM must cover.
- **V-A4 (P2). Battery cost.** Test: three arms of 12 hours each overnight on two devices from 100% charge: (1) no app, (2) FGS idle with no socket, (3) FGS plus an idle UDP/QUIC socket with 30 s and with 5 min keepalives; `adb shell dumpsys batterystats --reset` before, `adb bugreport` after, compare drain and wakeups in Battery Historian. Decides: whether an always-on FGS is acceptable (Q6.8).
- **V-A5 (P1). Android 17 local-network permission.** Test: the same app built with target SDK 36 and 37 on Android 17; grant, deny, and revoke `ACCESS_LOCAL_NETWORK`; try inbound UDP, inbound TCP, outbound TCP, a UDP broadcast and an mDNS lookup; record errors and whether the FGS keeps running after denial. Decides: Q6.7 and the relay-fallback design.
- **V-A6 (P2). MediaProjection and lock.** Test: start a projection, lock the phone, log `MediaProjection.Callback.onStop()` and its timing; on a second run use the developer option "Disable Screenshare protections" if present; compare. Also check whether the keyguard appears in the frames. Decides: Q9.2 (docs, AOSP flag state, and exemptions).
- **V-A7 (P1). Clipboard while locked.** Test: from an FGS with no focus, while locked, call `ClipboardManager.setPrimaryClip(...)`, then unlock and paste in another app; also call `getPrimaryClip()` while locked (expect null) and while unlocked and unfocused (expect null or denial); note any "pasted from" or access toast. Repeat once with the app set as the default keyboard. Decides: Q7.1 and Q7.2.
- **V-A8 (P2). Notifications on the lock screen.** Test: post notifications with `VISIBILITY_PUBLIC`, `PRIVATE` with a public version, and `SECRET`, and an action built with `setAuthenticationRequired(true)` that opens a URL; with a secure lock screen, check what is shown, whether tapping the action prompts for credentials before the browser opens, and what happens with `USE_FULL_SCREEN_INTENT` denied. Decides: the locked-phone UX (Q7.4, Q8.3).
- **V-A9 (P1). Receiving a file before and after first unlock.** Test: (1) reboot, do not unlock, send a file from another device and see whether any component runs (declare a `directBootAware` service and log `ACTION_LOCKED_BOOT_COMPLETED`); (2) unlock once, lock again, send a file and write it to app-private storage, then to MediaStore and to a user-granted SAF folder; record which writes succeed while locked. Decides: Q8.4 and whether received files must be queued.
- **V-A10 (P2). AccessibilityService on the keyguard.** Test: a minimal service with `canPerformGestures` and window retrieval enabled; call `performGlobalAction(GLOBAL_ACTION_LOCK_SCREEN)`; log events received from the keyguard window (gestures over the lock screen are not part of this copy, because Baton never types into a lock screen); repeat with Advanced Protection Mode on (Android 17). Decides: Q7.7 and the viability of lock-from-app (Q12e).
- **V-A11 (P3). Shell-level input and Shizuku (not reproduced).** The procedure is left out of this copy, because it concerns input at the lock screen. Baton has no use for it.
- **V-A12 (P3). Overlay on the keyguard.** Test: a `TYPE_APPLICATION_OVERLAY` window drawn over everything, then lock; check visibility. Decides: Q7.6 (code says hidden).
- **V-A13 (P1). OEM survival.** Test: on Pixel, Samsung (One UI), Xiaomi (HyperOS), OnePlus (OxygenOS) with default settings: install the FGS + echo app, set it up as a normal user would (no exemptions), leave screen off for 24 hours and 72 hours, query the echo every 15 minutes, and read `adb shell dumpsys activity exit-info <package>` afterwards; then repeat after applying the vendor's recommended exemptions from dontkillmyapp.com. Decides: whether OEM killers invalidate the listener model and what onboarding must ask for (Q6.6).
- **V-A14 (P2). 72-hour auto-reboot.** Test: leave a Pixel with the Play services version that carries the feature locked for 73 hours; record the reboot time, the FGS state and the BFU state afterwards. Decides: the secondary report in Q6.6.
- **V-A15 (P2). Keystore unlocked-device keys.** Test: generate an EC or RSA key with `setUnlockedDeviceRequired(true)`; encrypt to its public key while locked; try to decrypt while locked (record the exception) and after unlock; repeat on Android 12, 13, 14 and 16/17 and with face unlock (a non-strong biometric). Decides: the mailbox design in Q12b.

## 6. Sources, limitations and provenance

### 6.1 How the evidence was gathered

- Date: 2026-10-14. Official documentation (developer.android.com, systemd man-page sources, flatpak.github.io portal docs, LizardByte, Chromium policy templates) and source code (raw files from GitHub `main` or `master` branches of GNOME Shell, Mutter, gnome-settings-daemon, GNOME Remote Desktop, KWin, kscreenlocker, PowerDevil, KRdp, xdg-desktop-portal-kde, kdeconnect-kde, kdeconnect-android, systemd, AOSP `platform/frameworks/base` mirror, RustDesk, Chromium, Sunshine, Apollo, Shizuku, scrcpy, Syncthing-Fork, Tailscale) were fetched directly over HTTPS through the sandbox proxy. Branch heads are not release tags: GNOME is roughly 51, Plasma is the 6.8 development line, Android is the Android 17 era `main`. Shipped OEM and distribution builds can differ.
- Items marked `*` came through a summarising fetch tool. This covers Parsec, AnyDesk, Apple support pages, Firebase pages, Tailscale's Taildrop page, the Magic Wormhole protocol page, the IETF Sleep Proxy draft, wayland.app registry pages, docs.rs, the Play Console help pages and dontkillmyapp.com. Quotation marks inside those items are the summariser's quotes.
- Secondary sources used only where primary ones were missing: an offline copy of the Arch Wiki (third-party mirror, April 2026) and a cyberciti.biz tutorial for Wake-on-LAN and WoWLAN practicalities, scrcpy issue threads and a remote-support vendor page for the MediaProjection appop, a CyberInsider article for the 72-hour reboot, a The Hacker News article for the Android 17 beta accessibility restriction, and one KDE Discuss post for the KDE Connect lock-screen clipboard symptom.

### 6.2 Limits of this research

1. **Nothing was tested on hardware.** Every behaviour statement is from documentation, source reading or reports. Section 4 lists the tests.
2. **The web-search budget ran out part-way.** After that I used only direct fetches of known primary-source URLs and did not route around the limit through search engines, readers, proxies or archives. Consequences: TeamViewer is entirely unverified; the RustDesk CVE history was not obtained (NVD was blocked, the repository publishes no advisories I could find, and `SECURITY.md` returned 404); I could not look for newer secondary reports on topics such as UnifiedPush, Android 17 accessibility restrictions, or battery measurements.
3. **Hosts the proxy refused (HTTP 403 on CONNECT) at one time or another:** freedesktop.org, gitlab.gnome.org, invent.kde.org, android.googlesource.com, x.org, learn.microsoft.com, docs.rustdesk.com, services.nvd.nist.gov, developers.google.com, man7.org (late in the work), networkmanager.dev (late), wayland.app via curl, github.com wiki pages, and several vendor sites via curl (support.anydesk.com, support.parsec.app, community.teamviewer.com, docs.lizardbyte.dev, dontkillmyapp.com, firebase.google.com). I used the raw GitHub copy or the summarising fetch tool where possible; TeamViewer pages returned robots-disallowed errors. The GitHub API was not enabled for this session.
4. **Windows, macOS, iOS and iPadOS are out of scope** here; sibling research threads cover them. Where a cross-platform tool forced a mention (RustDesk, Chrome Remote Desktop, Parsec, AnyDesk, Apple Screen Sharing), I report only what the pages said.
5. **Not checked at all:** UnifiedPush or other non-Google push paths; how GNOME Keyring or KWallet behave while the screen is locked; KDE lock-screen notification policy; distro default power settings; whether Wayland compositors other than Mutter and KWin (Sway, Hyprland, COSMIC) lock the way KWin does; the Android Low Power Standby default; the status of `force-lock` under Android's device-admin deprecation; Bluetooth-proximity lock heuristics.

### 6.3 Where sources conflict or are silent (stated plainly)

1. **Foreground service network in Doze.** The Doze page lists network as suspended without an FGS exception; the "power management resource limits" page says an FGS process has "No restrictions" on network but also "Restricted during doze" for the device state; AOSP code lets a process at `BOUND_FOREGROUND_SERVICE` or better keep network in Doze. Low Power Standby is documented to cut network even for FGS apps. Unresolved without V-A1 and V-A2 (Q6.3).
2. **Standby buckets.** The bucket table says network is disabled in the restricted and rare buckets, while the app-state table says an FGS process has no restrictions. No page reconciles them (Q6.4).
3. **MediaProjection and the keyguard.** The Android 15 behaviour-change page says projection stops when the lock screen activates (from Android 15 QPR1). The AOSP implementation is behind a flag whose shipped value I cannot see; the exemptions (appop, hidden permission, developer option) exist only in code (Q9.2).
4. **Samsung background limits.** dontkillmyapp says apps not started in three days are put to sleep, yet quotes a Samsung statement (July 2024) that foreground services of apps targeting Android 14 are guaranteed to work. Not independently checked (Q6.6).
5. **Accessibility service under Android 17 Advanced Protection.** The official Android 17 feature page mentions the mode and `AdvancedProtectionManager`; the restriction on non-accessibility apps appears only in a news report on a beta (Q9.3).
6. **Parsec on Linux.** The help-centre index annotates a Linux article as "Linux host"; the article itself says Linux does not support hosting. I used the article text (Q11.3).
7. **KRdp exclusive mode (Plasma 6.8).** Described by `master` source and a "This Week in Plasma" post, not by a release note or user documentation; the code comments mark the VT-switch handling and the placement of the lock calls as unfinished (Q4.3).
8. **Silent sources.** AnyDesk and Apple do not say whether the host locks at session end; Parsec does not say whether the physical keyboard is blocked in Privacy Mode; no source says what a Linux desktop does with `xdg-open` while locked; no source says whether KWin delivers data-control or screencast frames while locked.

### 6.4 Everything here that relies on something undocumented

Each is marked in the text; collected for convenience. Do not build the product on these without a fallback.

- Linux: `kde_lockscreen_overlay_v1` (KDE: "Regular clients must not use this protocol"); KWin's restricted interfaces and `org_kde_kwin_fake_input`; GNOME's `inhibit_remote_access` chain and `unlock-dialog` session mode (internal; documented in source and NEWS only). logind `LockedHint` itself is documented, but only GNOME and KDE were verified to set it (Q5).
- Android (AOSP hidden or source-only behaviour): the FGS-in-Doze rule in `NetworkPolicyManager`; the clipboard locked-device null return and the `READ_CLIPBOARD_IN_BACKGROUND` permission; the MediaProjection keyguard stop controller and its exemptions, the `PROJECT_MEDIA` appop and `RECORD_SENSITIVE_CONTENT`; keyguard hiding of overlay windows; `INJECT_EVENTS`; Shizuku; KDE Connect's `READ_LOGS` logcat trick; the privileged `COMPANION_DEVICE_APP_STREAMING` role.
- Reports without Google documentation: the 72-hour locked auto-reboot; the Android 17 beta accessibility restriction.
- Other tools: RustDesk's use of `CGSession -suspend` (no Apple documentation found), and its magnifier-style Windows privacy window, whose source uses process and DLL injection (a `WindowInjection.dll` check, a process named `RuntimeBroker_rustdesk.exe` derived from `RuntimeBroker.exe`, and remote-memory and APC calls; read at the constant and import level only).

### 6.5 What would change these conclusions

A change to Mutter's remote-access policy (for example an allow-list that keeps ScreenCast alive on lock); KWin adding lock handling to screencast; Google documenting the FGS-in-Doze rule or changing Low Power Standby defaults; the MediaProjection keyguard flag or its exemptions changing; Android 17 final behaviour of `ACCESS_LOCAL_NETWORK` when denied; and any result from section 4 that contradicts an inference marked `[INFER]`.
