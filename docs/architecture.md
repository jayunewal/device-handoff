# Architecture

This document describes how Baton is put together. The trust model is in [security.md](security.md). The wire format is specified in [protocol.md](protocol.md).

## Layers

```
 device A                                        device B
┌──────────────────────────────┐                ┌──────────────────────────────┐
│ UI: command line, later      │                │ UI                           │
│ Flutter apps                 │                │                              │
├──────────────────────────────┤                ├──────────────────────────────┤
│ baton-agent                  │                │ baton-agent                  │
│ clipboard, opening links,    │                │                              │
│ acting on policies           │                │                              │
├──────────────────────────────┤                ├──────────────────────────────┤
│ baton-core                   │  QUIC + TLS    │ baton-core                   │
│ identity, trust store,       │◄──────────────►│                              │
│ pairing, handoff, inbox      │  (via iroh)    │                              │
├──────────────────────────────┤                ├──────────────────────────────┤
│ baton-proto                  │                │ baton-proto                  │
│ message types, framing       │                │                              │
└──────────────────────────────┘                └──────────────────────────────┘
```

| Layer | Responsibility | Platform code? |
| --- | --- | --- |
| `baton-proto` | Message types, framing and the pairing ticket format. No I/O, so it can be tested and fuzzed on its own. | No |
| `baton-core` | Device identity, the trust store, pairing, discovery, the encrypted transport, the handoff service and the inbox where received items rest. Everything that must behave identically on every platform. | No |
| `baton-fs` | File system calls that the standard library does not have. There are five: move a file or a folder to a new name, and refuse if the name is taken, so that a file that was received never replaces one that the person has; mark a received file as one that came from elsewhere, the way a browser marks a download (the quarantine attribute on a Mac, the `Zone.Identifier` stream on Windows); hide a folder (on Windows, where a dot at the start of the name is not enough); ask how much room a volume has; and take the flag that makes a read fail when it would wait off an open file, which the sender sets so that opening a pipe does not hold it and does not want for the reads that follow. The calls need `unsafe` code, which is why they have a crate of their own. | Yes (each call has a version for each system) |
| `baton-agent` | The parts that touch the desktop: reading and writing the clipboard, opening links, and acting on the per-device policies that open or apply what arrives instead of leaving it in the inbox. | Yes (desktop) |
| `baton-app` | What a graphical front end calls: start the node, pair, send, take and send files, read the inbox, show and share windows, and hear what happens, as plain values and a stream of events. It puts the core's parts in the order a screen needs them and holds no protocol logic. | No |
| `baton-ffi` | The bridge to Dart: Dart-friendly copies of `baton-app`'s values and calls, and the glue that `flutter_rust_bridge` generates around them. It decides nothing. | Generated glue only |
| `baton-stream` | Window streaming (milestone 5), built a piece at a time. It holds the start of a stream, the frame header, the source's accounting of frames in flight, the viewer's choice of which frame to decode, with the limits on what it holds, what a viewer that controls the window may do (its events, the checks on their numbers, and the rules that confine them to the shared window), the messages of the two control streams, the conversion of H.264 pictures between the form they have on the wire and the form that the encoder and the decoder of an Apple device use, and the size of the pictures that a sequence parameter set describes, which a viewer reads before a decoder does so that it can refuse a picture beyond what it said it takes. No I/O and no platform code, so all of it can be tested on any computer. See [ADR 0009](adr/0009-window-streaming.md). | No |
| `baton-stream-abi` | The small C interface through which the platform code of a device (Swift, on an Apple device) shows the windows of other devices and shares a window of its own. `include/baton_stream_abi.h` is the interface: every struct, number and function, with the rules for who owns what, which thread a call is made on and what each failure means, and with the sizes and offsets asserted in the header. The platform registers a table of functions once (`baton_stream_register_viewer`), and the crate makes the `WindowViewer` that `baton-app` takes from it: the platform says what it can show and makes a decoder and a screen for each window, and the crate gives its decoder each frame in the form that Apple's decoders take, with the parameter sets apart, after it has held every sequence parameter set to what the platform said it can show, as the picture is shown and as it is coded. A call made from inside a call into the platform is refused, because the session's lock is held there; a panic is answered with an error code and never unwinds into the platform's frames; a screen is released once; and the number of a link, which the platform keeps to say that its decoder failed, is never used again, so a late call about a session that ended is an error and not a use after free. To share windows the platform registers a second table (`baton_stream_register_sharer`), and the crate makes the `WindowSharer` that `baton-app` takes from it. The person picks the window in the system's own picker, which the platform shows when the app asks and whose answer it gives with `baton_stream_pick_done`; from then on the Rust side owns the window and releases it exactly once, whether or not it was ever started. It asks the platform to prepare the window (to choose the first picture, within what the viewer of the other device takes) only after the other person has said yes, and to start it when the session runs, so nothing is captured for a no. The capture threads of the platform then ask the session, with the number of the link that `start` gave, whether to make a picture and of what kind (`baton_stream_source_begin`), hand it each picture the encoder made (`baton_stream_source_sent`), start a new size of picture, pause and resume, or end the session, with a sentence for the person when something went wrong. The crate converts each picture from the form that Apple's encoder makes into the form of the wire, refuses one that cannot go on the wire (a length that reaches beyond the picture, a key frame without a slice of an IDR picture or without both kinds of parameter set, a picture over the limit of the protocol), and holds the size of the picture to what the protocol allows and the viewer takes. `ended` and `release` are called from a thread of the Rust side with no lock held, so the platform may stop its capture threads in them, and a call about a session that has ended is answered as the session would and then as a link that is not open. The numbers of the links of screens and of sources come from one counter and are never used again. Its hand-written `unsafe` is in two modules, one for each direction, as CONTRIBUTING.md asks. | Only the interface |
| Viewer for Apple devices (Swift, in `apps/baton/rust_builder`) | The platform side of `baton-stream-abi` on an iPhone, an iPad and a Mac, in the Flutter plugin that already builds the Rust library. Flutter registers it before Dart runs, and it gives the library the table of functions with which the device shows windows. `BatonViewer.swift` holds what needs no Apple framework: the functions the Rust side calls, the reading of the structs it passes (nothing traps on what it passes), the rules for which picture is shown and when a decoder has failed, and the places that windows are drawn on, with the decoder and the screen given to it as protocols, so that it is built and tested with any Swift compiler. `BatonH264Decoder.swift` decodes with VideoToolbox, the hardware decoder where the device has one, into pictures that Flutter draws as they are. `BatonStreamPlugin.swift` is the only file that knows Flutter: it takes two textures from Flutter at launch, because Flutter takes a texture only on the platform thread and the Rust side asks for a screen from a thread of its own, and gives one to each window. Flutter on a Mac gives no texture until its engine runs, which is after the plugins are registered, so the plugin asks again until it has them; the viewer is registered at once, since what the device can show does not depend on them. A texture with no window draws a blank picture and not none, because Flutter on an iPhone goes on drawing the last picture of a texture that answers with none, and the next window would show it. The files are the same for iOS and macOS, and a Dart test fails if the two folders or the header differ. | Yes |
| UI | Presents devices, pairing and received items. The command-line program (`baton-cli`, the `baton` binary) came first; the Flutter app in `apps/baton`, starting with iPhone, iPad and Mac, calls `baton-app` through `baton-ffi`. | Yes |

The Flutter app reaches `baton-app` through `baton-ffi` (see [The bridge](#the-bridge)), which holds `unsafe` code only in the glue it generates. The only other `unsafe` code in the repository is in `baton-fs`, in the module that makes its system calls, and in `baton-stream-abi`, in the two modules that cross the C interface to the platform code. On mobile the app implements the equivalent of `baton-agent` natively (share sheet, Shortcuts, Android intents), because those platforms do not let a background process read the clipboard or open links the way a desktop agent does.

## The command-line program

`baton-cli` builds the `baton` program, the first front end. It holds no protocol logic: it opens a state directory, starts a `Node` from `baton-core` when a command needs the network, and turns what the core reports into text for a person.

- **One-shot commands** (`id`, `devices`, `pair offer`, `pair join`, `unpair`, `ping`, `send`, `inbox`) do one thing and exit. **`baton listen`** keeps a node running so that other devices can reach this one, announces what arrives, and doubles as a prompt that takes the same commands without the word `baton`. A device can be reached only while something is listening, and a pairing offer is made at the same prompt so that the address in its ticket is still the right one when the other device joins.
- **Only one process runs the node.** The commands that start the network or change the list of devices take `baton.lock` first and say so when another window already holds it. Reading needs no lock: `baton inbox` and `baton devices` work while `baton listen` runs, because the inbox is a file with a lock of its own (see [State on disk](#state-on-disk)).
- **Questions and the prompt share standard input.** One thread reads lines. A line goes to the question that is waiting for an answer, such as "type yes to pair", and otherwise to the prompt, so a pairing request can interrupt a listening prompt without the two taking each other's lines. A question is registered before it is printed, so an answer that arrives at once, as when input is piped, is never taken for a command. Questions are asked one at a time: a pairing request that arrives while the person is answering `inbox clear` waits until that command has printed its result, so a `yes` meant for one question cannot answer another.
- **Everything another device chose is escaped before it is printed**, error messages included (some carry the reason a device gave for hanging up), and only `http` and `https` links are opened ([security.md](security.md)). Nothing is opened, copied or applied by itself: the program has no agent and cannot yet tell whether the device is locked, so it only keeps what arrives.
- **Files are opened by the commands that need them.** An inbox file that cannot be read stops `baton inbox` and `baton listen`, which would have nowhere to keep what arrives, and says how to start a new one. It does not stop `baton id`, `baton devices` or `baton unpair`.

## The app layer

`baton-app` is what a graphical front end calls. Like the command-line program it holds no protocol logic. It puts the core's parts in the order a screen needs them, so that each front end does not do that again and get it wrong in its own way. A front end written in another language reaches it through a bridge that copies the values below and keeps nothing of its own.

- **One object, plain values.** `App::start` opens the state directory, takes its lock, loads the identity, the paired devices and the inbox, and starts the node. Everything it hands back is plain data a bridge can copy without knowing Baton's types: ids are 64 hexadecimal characters, times are seconds since the Unix epoch, and a device is shown by its name, system and fingerprint. `stop` can be called more than once and from anywhere: the work runs on a task of its own, and every call returns once the network is down and the folder is free. Neither a question waiting for the person nor an offer that is showing keeps a dropped app alive: dropping the last copy ends everything that runs in the background and the stream of events, though without telling the connected devices, which `stop` does.
- **Screens hear what happens.** `App::events` is a stream of changes: an item arrived, the list of devices changed, a device is asking to pair, a pairing offer ended. A screen that falls too far behind gets one "resync" event and reads the lists again, so a slow screen can neither stall the app nor make it hold events without limit. Reading the lists (`devices`, `inbox`) never waits for the network.
- **Pairing is two calls and an answer.** The device that shows a ticket calls `offer_pairing`, which returns the ticket to show as text or a QR code and later reports how the offer ended: paired, expired, withdrawn, declined, abandoned or failed. The device that has the ticket calls `join_pairing`, which hands over the six-digit code to show while it waits. When someone joins, the offering side gets a request with the other device's name, system, fingerprint and code, and answers it with `answer_pairing`. A request that cannot be answered any more, because the offer was withdrawn or the other device left, is taken off the screen with an event, and a late answer to it counts for nothing. One offer and one join are open at a time, and a new offer replaces the old one; offers are made one after another, in the order they were asked for, so that two quick taps cannot leave the older offer showing. A "yes" cannot be taken back once the node has claimed it, and the screen is always told what happened to the devices. A screen that withdraws the offer just after the yes is told whichever of the two reached the node first: that the devices paired, or that the offer was withdrawn and the other device turned away. A pairing screen therefore leaves the offer alone after a yes. The offer ends by itself, with an event.
- **Files go both ways, and the person is asked first.** A device takes files only when the app gives it a folder for them (`Options::receive_dir`). `receiving` says whether it does, and a folder that cannot be used leaves Baton running and taking no files, with the reason. Each transfer that another device offers is put to the person as `Event::TransferRequested`: who asks, how many files and folders and how many bytes, and the first names offered, cleaned the way a device name is, because another device wrote them. `answer_transfer` answers once, and the person has two minutes. A question that cannot be answered any more (the sender gave up, the time ran out, the app stopped) is taken off the screen with `TransferRequestEnded`, and stopping the app turns a question that is showing into a no. Nothing is kept before the yes, and the files are put in the folder only when the transfer has ended and each file has been checked ([ADR 0008](adr/0008-file-transfer.md)), so the folder never holds half a file. `TransferEnded` says how a transfer that was taken ended: every file in place except some that could not be saved, or given up with nothing kept. It also says where the items that arrived are (`saved`: the full path of each file and folder at the top of what was offered, in that order, with the number that a taken name got, so these are the names to look for and not the ones the person was asked about). The core hands the places to the app layer once, just before the end (`TransferHandler::placed`), and they are kept out of `Debug` output like the names are. `send_files` takes paths, walks them (what cannot be sent is counted and left out) and returns a `FileSend` at once. `progress` is cheap to read, `cancel` gives the transfer up and tells the other device, and `outcome` says how it ended, with the kinds of error the other calls use. Letting go of a `FileSend` gives the transfer up. The layer has no progress for a transfer that is being taken.
- **Windows come from the platform the app is given.** `App::start_with` takes a `Windows`: a `WindowViewer` for showing the windows of other devices (what the device can show, and the decoder and the screen it makes for a window the person said yes to) and a `WindowSharer` for sharing its own (the picker, and what the person picked: the window's title and size, the choice of picture within what the viewer takes, and the capture). The platform's frameworks are not part of the layer, so a device that is given none takes no part and says so to the devices it is paired with. The pictures go from the network into the platform's decoder and never pass through the layer's values or the screen, which is given only the number of the screen to draw. What the platform says it can show is checked against the protocol's limits when the app starts, so one that is set up wrongly fails there and not at the first window.
- **A window is a question, a session and an end.** An offer from a paired device reaches the screen as `WindowRequested` and waits for `answer_window`, as a pairing request does; it is taken back with `WindowRequestEnded` when the other device withdraws it or the time runs out, and that event carries a sentence when the person said yes and the platform could not show the window after all. `share_window` has the person pick a window, offers it and returns when the person at the other device has answered: started, declined with a sentence that names the device, or nothing chosen. A window that starts is a `WindowSession`, and a screen follows it by `WindowStarted` and `WindowEnded`, which says whether this device ended it, the other did, the connection was lost, or something failed. `end_window` ends one from either side. A device offers or shows one window at a time, and unpairing the other device or stopping the app ends it.
- **Errors say what a screen can do about them.** Every failure carries a kind for the screen to choose its words by, such as the other device being unreachable or the folder being in use by another Baton, and a message of one short line that is safe to show: whatever another device chose to say has been cleaned first. Tickets and the content of received items are kept out of `Debug` output, so logging a value cannot leak them. A received link is a string another device chose, so the layer says which ones a screen may open and what to open (`web_address`: the address of an `http` or `https` link in the form that was checked, as the command-line program does) instead of leaving each screen to remember. A screen opens that address and not the text that was sent, because another parser can read the same text differently.
- **The name is the person's to choose.** The core falls back to a name taken from the computer, which on a phone is rarely one a person would pick. The app asks for a name the first time and saves it with `settings::set_device_name` before it starts (a name with nothing visible in it is refused with a kind of its own, so the name field can say so), and `Options::lan_discovery` and `Options::port_mapping` override those settings for one run. On iOS the app turns both off, because multicast needs an entitlement that a free Apple ID cannot sign with, and asking the router for a port starts with a multicast message; until discovery through Apple's own service is added, an iPhone or iPad finds the other device through the relay and then moves to a direct path. That follows Apple's documentation and has not been tried on a device yet.
- **No platform code.** The layer runs the same on every system and is tested on Linux, macOS and Windows with two copies on one machine. The screens, the camera that reads a QR code and the share sheet belong to the front end.

## The bridge

`baton-ffi` is what lets Dart call `baton-app`. It decides nothing: a call goes straight to the app layer and what comes back is copied into plain values, so the bridge cannot let a device do more than the app layer does.

- **A written API and generated glue.** `crates/baton-ffi/src/api` is the whole surface: copies of the app layer's values (`model.rs`, `error.rs`), one object, `Baton`, that wraps a running `App` (`baton.rs`), and the few functions that need no running Baton: the ones that choose and save the device's name, and `recentLog`. [flutter_rust_bridge](https://github.com/fzyzcjy/flutter_rust_bridge) turns those into Dart classes in `apps/baton/lib/src/rust` and writes the glue on both sides. The generated files are committed, and CI writes them again and fails if they differ, so a change to the API cannot reach Dart half done. The Rust crate, the Dart package and the code generator must be the same version (2.13.0), and each says so where it is set.
- **What the app sees.** `Baton.start` returns the running object, whose methods are the app layer's. A few calls that cannot wait for anything are synchronous (`me`, `answerPairing`, `cancelOffer`, `cancelJoin`, `receiving`, `answerTransfer`, `webAddress`, `windowAbilities`, `answerWindow` and `endWindow`); the rest return a `Future`, and `shareWindow` is one that can take as long as two people take to decide. `sendFiles` returns a `Future` of a `FileSend`, whose `progress()` and `cancel()` are synchronous and whose `outcome()` is a `Future`. A failure throws a `BatonError`, whose `kind` the screen chooses its words by and whose `message` is one line that is safe to show, as in the app layer. `joinPairing()` returns a `Stream` of one pairing's progress: the code to show, then the device that was paired or the reason it was not. `events()` returns a `Future` of a `Stream`, and the stream carries events from the moment that future completes until the app stops, so a screen awaits it before it reads the devices and the inbox and loses nothing in between. The stream does not keep the `Baton` alive: one that Dart lets go of without calling `stop` ends it, and the folder is free again. A join that fails ends the stream with an item, not a thrown error, so a screen handles the outcome in one place.
- **Dart prints what it holds.** On the Rust side, `Debug` output leaves out tickets and the content of received items. The classes the generator writes for choices (`Event`, `JoinProgress`, `OfferOutcome` and `ReceivedItem`) do not: `ReceivedItem.toString()` includes the link or the text that was sent, which may be a password or a sign-in link, and `JoinProgress.code` the pairing code. A screen does not print or log these, or put them in an error message; it shows what the person needs to see and nothing else. The classes it writes for plain values (`PreviewName`, `TransferRequest`, `TransferEnd`, `WindowRequest` and `WindowSession`) have no `toString`, but what is in them prints wherever a screen prints it: a name in `preview` is the name of a file, `TransferEnd.saved` has the full path of each item that arrived, with the name of the folder that the person keeps their files in, and the `title` of a window can name a document, a person or a page.
- **A quiet stream cannot be cancelled at once.** Dart builds these streams from an `async*` generator, and cancelling one finishes only when the generator next yields. The `Future` that `cancel()` returns therefore stays open until the next event arrives. A screen holds one `events()` subscription for as long as the app runs, lets `stop` end it, and does not wait for `cancel()` where it has other work to do.
- **The log is kept for the screen.** On a phone, or in a Mac app that was opened from the Finder, nobody sees standard error, so the library also keeps its last 400 log lines in memory (`recent_log`, from `logbuf.rs`) for the Diagnostics page. A line is made safe on the way in, because these lines get pasted into public issues: it is cut to 600 characters; control characters and the ones that turn text round are replaced; anything that looks like a pairing code (`BATON1:` and the rest of its event, since the parser of a code ignores white space) is taken out, because a code is a bearer secret while its offer lasts; a key of 64 hexadecimal digits is cut to the short form that Baton's own lines use for a device; the account name in a path becomes `~`; and a public IP address is shown only by its kind and port (`public IPv4 (hidden):41641`), because it names the network the device is on and, with the port mapping, a port on the router that leads to it. Candidates are parsed as addresses and not matched by their look, since a time or a version looks like part of one (`logbuf/hide.rs`). Standard error stays complete for a developer, and nothing is written to disk. A panic is logged as well, by a hook that calls the one before it afterwards (`logbuf/panics.rs`). That needs two things of the log: lines are made safe before its list is held, so that the hook, which runs on the thread that panicked, never waits for a lock that thread holds; and a panic inside that cleaning is left out of the log, because it could panic again on its own message, and a panic inside a panic hook ends the process. The lines still name this device and the ones paired with it, by name and short id, and show the addresses of the local network and the relay's, and the page says so before the person copies them.
- **The platform's viewer and sharer.** `Baton.start` gives the app the viewer and the sharer that the platform code registered through `baton-stream-abi` before the call, if it registered them, so one library serves a device that can show windows, one that can share them and one that does neither. The library carries the functions of that interface in its shared form as well as its static one, because it uses the crate that has them. A Dart test looks them up in the library built for the computer, and the two Mac jobs of CI look for them in the app they build.
- **`unsafe` stays in the generated module.** The workspace forbids `unsafe_code`, and a forbid cannot be lifted, so this crate lists its lints itself: `unsafe_code` is denied everywhere, with an allow on the generated module alone. The rest of the list is copied from the workspace, and a test fails if the two drift apart.
- **How the library reaches the app.** For iOS and macOS the Xcode build runs [Cargokit](https://github.com/irondash/cargokit), which builds `baton-ffi` as a static library and links it in (`apps/baton/rust_builder` holds the copy and its MIT license). The Dart tests load the library built for the computer they run on instead; [apps/baton/README.md](../apps/baton/README.md) says how.

## The app

`apps/baton` is the Flutter app. It holds no protocol logic: what a screen shows and does comes from `baton-app` through the bridge, and the screens only choose words and layout.

- **Two small interfaces.** The screens are written against `Backend` (the name saved for this device, and starting Baton) and `Session` (a running Baton: this device, its events, the paired devices, where the device can be reached, the calls that pair a device or forget one, the ones that send a link or some text, check that a device answers, and read and empty the inbox, and the ones that send files and answer a request for files) in `lib/src/backend.dart`. `lib/src/rust_backend.dart` is the only file that calls the generated bridge, so widget tests run the whole app against a fake on any computer, and the one place that depends on the Rust library is the one place that has to be tried on a phone.
- **One controller for each job, and no state-management package.** `AppController` takes the app from looking for a saved name, through asking for one and starting Baton, to a running Baton or a failure it can show and try again; `DevicesController` keeps the devices screen up to date from the events, and asks where the device can be reached every few seconds, because there is no event for that. Both are `ChangeNotifier`s that a `ListenableBuilder` reads. A failure that is not Baton's, such as a library that cannot be loaded, is shown too, with what it was, because a screen that says nothing cannot be reported.
- **Pairing has a controller on each side.** `OfferController` is the device that shows a code: it asks for an offer, has the ticket drawn as a QR code (`qr.dart`), asks the person about each device that wants to pair, one at a time, and says how the offer ended. `JoinController` is the device that reads a code: the ticket comes from the camera (`scanner.dart`, the `mobile_scanner` package, which reads with Apple's Vision framework) or from text pasted in, and the six digits it shows are for the person to compare with the other screen while the other device decides. Both keep to what the app layer promises: only the person at the offering device says yes, a joiner that goes away spends the offer, and a screen that is closed gives its pairing up, because an offer that nobody can see should not stay open. The ticket is a bearer secret while the offer lasts, so a screen shows it only as a QR code and by way of the copy button, never as text on the screen. A device with no camera, or a person who said no to it, pastes the code instead. On a Mac and an iPhone signed in to the same Apple ID the clipboard is shared, so that is a copy on one and a paste on the other. That is Apple's Universal Clipboard, which needs Handoff, Wi-Fi and Bluetooth turned on on both and the devices close together, so the guide also says how to get the text across without it.
- **Sending has a controller, and so does the inbox.** `SendController` sends what the person typed to one device: a web address on its own goes as a link, written out as the library wrote it, and anything else as text, exactly as typed. It says what happened in a sentence made from the app layer's message, and leaves what was typed in the box when a send fails. A send to a device that is not there takes as long as the core's connect timeout, so the screen says that it is waiting and that Baton gives up after a while. `InboxController` listens to the events before it reads the inbox, so that an item that arrives during the first read is not lost, reads again when it missed events, counts the listed items that are newer than the newest one the person has seen (so an item whose event was missed counts too, and one the core has dropped does not), and hands each arrival to the home screen.
- **Files have a controller on each side.** `FilesController` sends what the person chose to one device. It shows what is going (the first name and how many more), a bar that fills with the bytes that went out and moves without filling while Baton connects or waits to try again, what Baton is doing in words, and a button to stop, and it says how the transfer ended in a sentence made from the app layer's message. Giving the transfer up says nothing, because the person knows. It reads the progress four times a second, because there is no event for it, and leaving the screen gives the transfer up, so the screen asks first. `TransfersController` is for the other side and belongs to the home screen. It holds the questions that devices put to the person, answers each once however often it is tapped, keeps the transfers that were taken and are on their way, and the last five that ended. `TransfersPanel` shows them at the bottom of both places, so that a question is seen wherever the person is. A transfer that kept something has a button on its card that takes the person to the files (`Show in Finder` on a Mac, `Show in Files` on an iPhone or an iPad; see "Showing the files that arrived" below), and the card says so when they were moved or deleted since. Over another screen a notice says who asks and nothing of what, because the names of files can be private, and a button leads back to the question. `FileChooser` is what the screens ask to choose. The system's chooser (`file_selector`: the open panel on a Mac, the sheet of the Files app on an iPhone or an iPad, which copies what is chosen into the app's temporary folder, so that a very large file needs room for two copies while it goes) chooses folders only on a Mac. When the sending is over, however it went, and when the screen was gone before there was anything to send, the screen hands the paths back with `release`, and an iPhone or an iPad deletes the copies. It deletes only plain files that are inside the temporary folder of the app, with links resolved, so a link, a folder, a path that climbs out of that folder and everything that a Mac's panel gives are left alone. Copies of a transfer that stopped because Baton was closed stay until iOS clears them.
- **Windows have a controller, a panel and a screen.** `WindowsController` belongs to the home screen, like `TransfersController`. It holds the offers that devices make to show a window and answers each once however often it is tapped, keeps the window that is being opened (the person said yes and the first picture has not come; after twenty seconds it says that the window did not open), the windows that run, whether this device shows them or shares them, and how the last five ended, in the words of the app layer. `WindowsPanel` shows all of that at the bottom of both places and takes no room when there is nothing to show, so that an offer is seen wherever the person is. Over another screen a notice says who offers and nothing of what, because the title of a window can be private. The button that shares a window is on the row of a device, and only a device that the library says can share a window has it. `WindowScreen` draws a window that another device shows: the platform gives the session the number of a texture and draws into it as the pictures arrive, and the screen shows that texture as large as the screen allows with its shape kept, and zoomed with two fingers. A window is only looked at, and leaving the screen ends it, after asking, because the other device would have to share it again. A window that ends by itself stays on the screen and says how (the other device stopped it, the connection was lost, or what went wrong), with a button to close it. Titles and the names of applications come from the other device, so they are made fit to show like any text that is sent: the marks that cannot be seen or that turn text round show as a replacement mark, and each run of spaces and line ends is one space.
- **What another device sends is shown, not trusted.** The notice that something arrived says who sent what kind of thing and never what it holds, because it can be a password and a notice is seen by anyone looking at the screen. Text is shown as it was sent, except that line ends are the same everywhere and the characters that cannot be seen or that turn text round show as a replacement mark (control characters, the direction marks, embeddings, overrides and isolates, and the zero-width and format characters listed in `lib/src/format.dart`, but not the joiners that emoji sequences and several scripts need), so that a line cannot read as one address and be copied as another; copying gives the original. A long text is cut to six lines, and the card asks the layout, at the width it has and in the size and weight of letters the person chose (Bold Text makes letters wider, and lines wrap earlier), whether the cut hides anything, because counting characters and line ends gets that wrong as soon as lines wrap. The card works out the style once and gives it both to the text and to the measuring. A link is opened only if the library's `web_address` gives an `http` or `https` address back, and the app opens that address, not the text it was sent. `links.dart` checks the scheme once more on the way to `url_launcher`, because the parser there is not the one that checked it here, and writes down only what went wrong when a link would not open, never the link, since it can hold a sign-in token.
- **Diagnostics are for a bug report.** An app on a phone cannot be asked to print anything, so the Diagnostics page (the menu at the top of the devices screen, or **Show details** when Baton could not start) lists a few facts and the library's last log lines and copies them as one text. `DiagnosticsController` reads the facts again whenever the person asks: the system, this device's name and short id (the id the log calls it by), how many devices are paired, the relay, the addresses other devices can try and whether the local network is searched. The fingerprint is left out, because it can be worked out from the key that is announced on the local network, and would let anyone who later sees the device there tie it to the report. The addresses follow the rule of the log (`describeAddress`: public ones by kind and port, text that is not an address not at all), and the account name in the start-up problem and in a message of the library becomes `~` (`hideAccountNames`); the tests list the same cases as `hide.rs`. A failure that is not the library's is named by its type and not by what it says, and every line is shown the way the inbox shows received text. It also works with no running Baton, because a Baton that could not start is when a person most needs it.
- **Where Baton keeps its files.** `Library/Application Support/baton-app` inside the app's own container: the sandbox on a Mac, the app's data on an iPhone or iPad. The folder holds the key that makes the device what it is, and a backup restored onto another device would carry the key there, so both apps mark the folder as left out of backups (`AppDelegate.swift`, `MainFlutterWindow.swift`). The name is written in those two files and in `rust_backend.dart`, and a test fails if they disagree.
- **How the app finds that folder.** `support_folder.dart` says where `Library/Application Support` is. An iPhone or an iPad is asked, through a method channel that `AppDelegate.swift` answers with the folder it gets from the system, and its environment is not read, because iOS 27 starts an app without `HOME` in it (Baton, which looked for `HOME`, did not start on such a phone). A Mac's app is sandboxed, so its `HOME` is the folder of its sandbox and is always there. A test fails if the names of the channel and of the question in `AppDelegate.swift` and `support_folder.dart` disagree. The iPhone job in CI asks the app for the folder in a simulator, which gives an app no `HOME` either, and checks that the folder is there, that the app made Baton's folder in it when it opened, and that the library opens it. Earlier builds found the same folder from `HOME`, which for an app named the folder of the app, so a phone that is set up keeps its key and its devices. CI cannot check that, because the simulator gives no `HOME` to compare the answer with.
- **Where received files go.** The `Documents` folder of the app on an iPhone or an iPad, which the Files app lists because `Info.plist` says so (`UIFileSharingEnabled` and `LSSupportsOpeningDocumentsInPlace`), and the `Downloads` folder of the person on a Mac. The Mac app is sandboxed, so its home folder is its container and a Downloads folder made there is not one that anyone would look in. `MainFlutterWindow.swift` finds the real one from the user database (`getpwuid`), which the entitlement `com.apple.security.files.downloads.read-write` lets the app write to, checks that a file can be made in it, and otherwise gives the Downloads folder of the container, so that files still arrive. `support_folder.dart` asks both apps on the channel that says where Baton keeps its files (`receiveFolder` is the second question). A system that cannot say leaves Baton running without taking files, and the screens say why. A test fails if the names of the channel and of the question disagree between the apps and `support_folder.dart`, and if the entitlements or the keys in `Info.plist` are lost. None of this has been tried on a real Mac or phone yet. The jobs in CI that start the app check that the folder is there and that a file can be made in it.
- **Showing the files that arrived.** The card of a transfer that kept something has a button that takes the person to the files, with the places that `TransferEnded` gave (`saved`). `file_shower.dart` asks the app on a channel of its own (`io.github.jayunewal.baton/files`, the question `show`, with the full paths as the argument). A Mac opens Finder with the items selected (`NSWorkspace.activateFileViewerSelecting`, in `MainFlutterWindow.swift`). An iPhone or an iPad opens the Files app at the folder that holds them (`AppDelegate.swift`: the path of the folder under the `shareddocuments` scheme, which is how the Files app is asked to open the `Documents` folder of an app), which is the Baton folder, or the folder itself when one folder arrived alone. A file is shown by the folder that holds it, because a folder is what that scheme is used for, and the Baton folder is where every file that arrived is. Both apps answer `false` when none of the paths is there any more, which the card says in words (they were moved or deleted since), and a system that cannot be asked is said to have failed, with where the files are. Neither app opens a file: Baton shows what arrived, and what a file does when it is opened is for the person to choose, so a test fails if the Mac app starts to open files. A test fails as well if the names of the channel and of the question disagree between the apps and `file_shower.dart`. The jobs in CI ask both apps about a file that is not there, which shows that the question reaches the code and is understood without anything opening, because showing a file would take the person out of the app. None of this has been tried on a real Mac or phone yet.
- **The screen stays on only while two devices pair, files go or a window shows.** A phone turns its screen off, and locks, after a while without a touch, and Baton on a phone works only while it is on the screen, so a screen that went off while the person was on the other device would take the pairing with it. Each pairing controller takes an `AwakeHold` (`awake.dart`) from the moment a code is asked for, or the camera starts to wait for one, until the person is told how it ended, and lets it go when the screen is closed. Each step of the pairing (a code made, a request, an answer) renews the hold, which lets go by itself after five minutes without one (no step lasts longer by itself: a code is shown for five minutes at most, the person has under three to answer a request, and reaching the other device and hearing its answer take less, so a screen still open after that has been forgotten), and stays let go until the next step or until the controller releases it, so a screen that forgot to let go cannot leave a phone that never locks. A phone has one setting for the screen and the holds of two screens can overlap (back from one screen and at once to another, while the first is still sliding away), so the keeper counts the holds and turns the setting on for the first and off for the last. Nothing else in Baton holds the screen: a phone that never locks is the opposite of what Baton is for, and the person's Auto-Lock decides the rest of the time. Files keep it on as well, by the same hold. The device that sends keeps it from the choice of files until the transfer ends, renewed at each step of the progress. The device that is asked keeps it from a request, and from the yes, for the same five minutes, because nothing says how far a transfer that is being taken has got, so a transfer longer than that can let the phone lock. Windows keep it on as well, by the same hold: from an offer that waits, and from the yes until the window ends. While a window shows it is renewed every minute, because nobody touches a phone that is only watched, and a hold that was not renewed would let go after five minutes. The hold asks the iOS app through a method channel, which sets `isIdleTimerDisabled`, sets it again when the app comes back to the screen and clears it when the app goes away; on other systems the hold does nothing yet. A test fails if the names of the channel and its methods in `AppDelegate.swift` and `awake.dart` disagree, and the iPhone job in CI asks the system, in a simulator, whether the screen is being kept on while a code is waited for and after the pairing.
- **The Mac app is sandboxed**, with the entitlements to connect out and to accept connections, which a device that is reached directly needs, to use the camera, which scanning a code needs, to write to the Downloads folder, where received files go, and to read the files and folders that the person chooses to send. Whether the sandbox lets the relay through, or a connection from another device, has not been tried yet: the integration test that CI runs on a Mac turns the relay and discovery off and pairs two Batons that are both in the app's own process, so it shows that connections between addresses on this computer get through the sandbox and nothing more.
- **Finding the library.** The Xcode build runs [Cargokit](https://github.com/irondash/cargokit), which builds `baton-ffi` as a static library and links it into a framework called `baton_ffi`; the app opens `baton_ffi.framework/baton_ffi` and looks the functions up by name, so the link keeps every global symbol (`-force_load`, and no stripping of them). A static library does not bring the system frameworks it needs, so the pod names them: `SystemConfiguration` on both systems and `Network` on the iPhone and iPad.
- **Checked on real Macs in CI.** Besides the Linux job that holds the generated bridge and the Dart tests to the Rust library, one job builds the Mac app, checks that the framework holds the functions the app looks up and that the sandbox allows the network and the camera, starts the app, has it name a device, pairs it with a second Baton through the real screens (the runner has no camera, so the code is pasted in), receives a text from that Baton and sends it a link through the real screens, checks that the app is given a folder for received files that it can write to and that the send screen offers files, and keeps the built app as a download; another builds the iPhone and iPad app without signing, checks the same, and does the same in a simulator. CI cannot install on a device, which needs someone's Apple ID, so [docs/install-the-app.md](install-the-app.md) says how to build and install the app from your own Mac.

## Connecting devices

Every device has an Ed25519 key pair. The public key is the device's identity. Devices dial each other by that key, and the QUIC/TLS handshake proves both sides hold the keys they claim, so a connection to a given identity cannot be impersonated.

Reaching a device uses the best path available, tried in this order:

1. **Local network.** Devices announce themselves on the LAN with mDNS and connect directly.
2. **Direct over the internet.** A relay helps both sides learn each other's public addresses and hole-punch through NAT.
3. **Relay.** If no direct path works, traffic flows through a relay. The relay forwards encrypted packets addressed to a public key. It cannot read or alter them.

The relays Baton uses by default are the iroh project's public ones. According to iroh's documentation they are rate limited and meant for development and hobby use, so a transfer that cannot go direct is only as fast as that shared limit. That is fine for trying Baton out. The self-hostable server runs a relay of its own with limits its owner sets, and the file transfer benchmark includes a relayed run so the cost shows up in the numbers.

Connection handling comes from [iroh](https://github.com/n0-computer/iroh) (see [ADR 0003](adr/0003-iroh-transport.md)). The rest of Baton talks to it through a small boundary in `baton-core` so the transport can change.

What a device knows about how to reach another is kept with the pairing: the ticket carries the offerer's relay and direct addresses, and after every connection each side remembers the relay and addresses that worked. A device that restarts can therefore reach its paired devices before discovery has found anything, and devices that cannot find each other any other way still connect through a relay.

Connections start with a small window and the gate raises it for paired devices. |

It reaches the network only through `wire`, so its tests run it against the real table of incoming transfers in memory, and against a wire that a test scripts to cause each fault that section 8 describes. `quic` is that wire over a node's connections: each attempt dials a session connection of its own and not the one the node keeps for requests, so that a transfer that is tried again is on a new connection and neither the node closing an idle connection nor an ordinary request that replaces a dead one can cut it off. A request goes on a stream of its own and a lane on a unidirectional stream with a lower priority than requests, so that a `Finish` or a `Cancel` does not wait behind file data. It reads what goes wrong with a stream as the engine decides by: a stop with each code, a request that gets no answer in time, a connection that the other device ended because it does not know this device. A lane that is dropped before it ended is reset, because QUIC finishes a stream that is dropped. An offer to a device whose hello does not say that it takes files is not made: the link answers it as that device would, with `Declined(Unsupported)`, while a `Finish` and a `Cancel` still go. |
| `streaming` | The two ends of a window streaming session ([ADR 0009](adr/0009-window-streaming.md)). `view` is the viewer's end: it takes the frames and the source's control stream that `uni` hands it, reads each picture into memory of its own while the rules of `baton-stream` count the bytes, gives the pictures to the platform's decoder in the order those rules choose, and writes the viewer's control stream (a report a few times a second, what the viewer wants, and the requests for a key frame). It ends the session when the source ends it or breaks a rule (describing a picture beyond what the viewer said it can take is one), when the connection ends, when the person ends it, when the source does not open its control stream in time, and when a message of the source stalls. The next offer to the same device waits for the answer to such a `Stop`, three seconds at most, because the viewer lets go of its place when it answers, and an offer that met the place still taken would be refused as `RateLimited`. On a yes it shows the application what the viewer can take, lets it choose the picture within that, and starts the source's end with the connection held open for as long as the session runs. A device has one session as a source at a time, and unpairing the viewer or stopping the node gives up an offer that waits. |
| `ratelimit`, `wire`, `link`, `clock`, `util` | Small shared parts: a sliding-window limiter, reading and writing frames with deadlines, describing which path a connection took, a clock that tests can control, and helpers that keep one failing task from taking others down. |

An incoming connection passes through these checks, in this order:

```
incoming packet
   │  Admission     Asks the sender to prove its address first when attempts arrive faster than
   │                the node wants to handle. Costs the node a small reply, not a handshake.
   ▼
QUIC and TLS handshake        both ends are now known by their keys
   │  Gate          baton/1 from a key that is not paired: closed with 403, nothing remembered.
   │                baton/1 from a paired key: the connection's window is raised.
   │                baton-pair/1: allowed, because the person is not paired yet, and left small.
   ▼
SessionServer or PairServer   each connection runs as a task of its own, so a bug reachable
   │                          from the network cannot stop the node accepting connections
   │  per request   Still paired? Then Intake: kind of item, size, repeat, rate limit.
   ▼
the application's HandoffHandler
```

Outgoing requests use a pool that keeps one connection per paired device. It opens the connection on first use and says `Hello`, reuses it for later requests, retries once on a new connection if a reused one turned out to be dead, and closes connections that have been idle for two minutes. Unpairing a device closes its connections, whichever side opened them.

## Trust

A device only talks to devices it has paired with. Pairing is explicit: one device offers a one-time ticket (shown as a QR code or text), the other redeems it, and the person on the offering device approves the request after checking that a six-digit code shown on both devices is the same. There is no way to switch the approval off. Both sides then remember each other's public key in a local trust store (`devices.json`, see [State on disk](#state-on-disk)). Connections from any other key are refused after the handshake, before any application data is read. The check is repeated for each request, so unpairing a device ends its access at once, including on connections that are already open.

There are no accounts in milestone 1. Accounts arrive in milestone 4 as an *introducer*: a server that tells your devices about each other. It is never in the data path and never holds the keys needed to read content.

### Same-account sync: a signed roster (design, not built)

Pairing every pair of devices by hand is how tools such as KDE Connect work, and it is tedious past three or four devices. The plan for milestone 4 is a *roster* instead: the list of a person's device keys, kept as a chain of membership changes.

- Each change, adding a device or removing one, is signed by a device that is already in the roster and carries the hash of the change before it. A device checks the whole chain from the first entry before it trusts anything in it.
- Pairing a new phone with any one device adds it to the roster. The others trust it because the chain is signed by a key they already trust, with no further pairing.
- The account server only relays roster changes. It holds no roster key, so it cannot add a device on its own. A compromised server could hold updates back or replay old ones, which the chain and a sequence number make visible, but it could not forge a device. That keeps the promise that the server is an introducer and never in the data path, even if it is compromised.
- A removal is a signed entry too. A device that sees it drops the key like a manual unpairing, including closing live connections.

Open questions: what to do when two devices change the roster at the same time (a fork), how a person recovers when every device is lost, and whether a device that was offline for a long time should accept a long chain without asking.

The trust store leaves room for this before its format is in use: each entry records how the device came to be trusted (`provenance`, today only `paired`), and a device trusted through the roster will also say who vouched for it.

## State on disk

Each device keeps its state in one directory, which belongs to a single device identity. By default that is the per-user *local* data directory (`~/.local/share/baton` on Linux, `~/Library/Application Support/baton` on macOS, `%LOCALAPPDATA%\baton\data` on Windows), never a roaming or synced one, because a copied device key would make two machines the same device. As a second line of defence the identity file records which machine made the key, and Baton refuses it on another one. Set `BATON_HOME` to use another directory, for example to run two instances on one machine.

| File | Contents | Notes |
| --- | --- | --- |
| `identity.toml` | The device's Ed25519 secret key. | Created on first run. Readable by its owner only; Baton refuses to use it if other users can read or change it. |
| `devices.json` | The trust store: paired devices, the name the person knows each by, how each came to be trusted, their last known addresses and their per-device policies. | Replaced atomically on every change. A file that cannot be read is an error, never an empty list. Refused if other users can read or change it. |
| `config.toml` | Settings a person edits by hand (device name, relays, discovery, limits). | Optional. Unknown keys are rejected so a typo cannot silently leave a setting on. Refused if other users can change it. |
| `inbox.json` | Links and text received and not yet dealt with, each with its sender, the time and a number that counts up and is never reused. | Replaced atomically on every change. At most `handoff.max_inbox_items` items and 3 MiB, the oldest dropped first. Readable by its owner only, because clipboard text can be a password. A file that cannot be read is an error, never an empty inbox. |
| `inbox.lock` | An advisory lock held for the length of one change to the inbox. | The listener adds to the inbox while other commands read and clear it, so unlike the rest of the state it is changed by several processes. A change takes this lock and reads the file again first. Reading takes no lock. |
| `baton.lock` | An advisory lock. | Only one process may run a node in a state directory at a time. |

State files are written to a temporary file in the same directory, flushed, and renamed over the target, so a crash leaves the old file or the new one. On Unix, files and a directory that Baton creates are readable by their owner only. A state directory that already exists is not changed, because it may be used for other things (think `BATON_HOME=$HOME`), but it is refused if other users can write to it, since they could replace the files in it. `identity.toml`, `devices.json` and `inbox.json` are refused if other users can read or change them, and `config.toml` if they can change it; the check is made on the file that is then read. Files are read with a size cap, and a file written by a newer, incompatible version is refused rather than misread or overwritten.

## Handoff

Moving something to another device is a *handoff item*: a link, some clipboard text, and later files and tabs. The receiver does not blindly act on an item. What happens next is decided by a per-device policy on the receiving side. By default received links and clipboard text go to an inbox and nothing is opened or overwritten until the person chooses; auto-open and auto-apply are opt-in, per device. See [security.md](security.md) for why.

The inbox is part of `baton-core`: `InboxHandler` is the handler that keeps a link or some clipboard text in `inbox.json` and answers the sender, and the command-line program uses it. A device set to ignore links, or clipboard text, from another device declines them as blocked. Everything else is kept, including links set to open and text set to apply, because those settings are carried out by the agent, which comes with the locked-device rules below, and a device that cannot yet tell whether it is locked should not open anything. The agent will act on an item that is already in the inbox, so a setting never changes what is stored.

## Locked devices

Handing work off means walking away from the first device, so that device is usually locked and often asleep. Baton has to work in that state: an app that needs the source unlocked fails at its one job. [locked-devices.md](locked-devices.md) records what each operating system allows, with the evidence and the tests still to run on real hardware. The rules below are the short form of what follows from it.

- **The agent does not need an unlocked session.** On desktops it is a per-user background process that starts at sign-in, not a system service. A lock should leave it running (reported on Linux, inferred on Windows and macOS until the tests in locked-devices.md have been run). Sleep and a restart before sign-in do not. Receiving items, answering pings and delivering what the person sent should work with the screen locked.
- **Stage before leaving.** What a person might want to continue cannot be counted on to be readable once the device locks, and on phones it is readable only while the app is in the foreground. So a hand-off starts while the person is at the device: an explicit "continue on" gesture that names the device or, where the platform allows it and the person turns it on, a clipboard that is staged continuously. Items sent by a gesture wait in an outbox for their device. The lock event itself sends nothing new, because many locks are idle timeouts and a push at every one would deliver what nobody asked to move.
- **A hand-off does not need the source afterwards.** An item goes directly when both devices are awake, waits in the sender's outbox otherwise, and, once accounts exist (milestone 4), waits encrypted in a mailbox on the server. A locked sender keeps delivering what the person explicitly sent, including by dialing the device it was sent to, and a "send and lock" gesture waits for the other device's acknowledgement before it locks the source. Only the mailbox works when the sender has gone to sleep before the other device appears.
- **Locked mode.** While a device is locked, or when it cannot tell, it accepts items into the inbox and does nothing else with them: nothing is opened or applied. It starts no hand-off of its own, but it finishes the ones the person started, delivering what was explicitly sent to the device it was sent to. It serves staged items, which nobody addressed, to a paired device only if the person allowed that for that device, which is off by default. A locked device refuses to start a send, and every phone action that starts one asks for authentication (see [locked-devices.md](locked-devices.md#52-stage-before-leaving-and-do-not-read-a-locked-device)).
- **Baton never unlocks anything.** There is no remote-unlock feature, now or later. Where the platform allows it, the source can lock itself once the other device has acknowledged a hand-off ("send and lock"), and a paired device can be allowed to ask for that lock, which is off by default.
- **Keys stay readable at the lock screen.** The device key and the trust store live in storage that is available after the first unlock of the device, not in storage that is sealed whenever the screen locks. A keystore that locks with the screen would make the agent deaf exactly when it is needed.
- **Sleep is the real limit.** Waking a device is Wake-on-LAN on desktops and push notifications through a gateway on phones (milestone 4). Both are best effort and nothing depends on them, and after every resume all connections are treated as dead.
- **Limits stay visible.** Some things cannot be done on a locked device, such as capturing a window from a locked desktop. No documented API allows it on any platform examined. Those limits are documented per platform, not hidden.

## Platform boundaries

Some things only native code can do, and they are kept out of the core:

| Capability | macOS | Windows | Linux | Android | iOS and iPadOS |
| --- | --- | --- | --- | --- | --- |
| Clipboard | Pasteboard | Win32 clipboard | X11 or Wayland | ClipboardManager (foreground only) | UIPasteboard (foreground only, paste banner) |
| Open a link | Launch Services | ShellExecute | xdg-open | Intents | UIApplication |
| Window capture (milestone 5) | ScreenCaptureKit | Windows.Graphics.Capture | PipeWire | MediaProjection | ReplayKit (view only) |
| Video encoder and decoder (milestone 5) | VideoToolbox | Later | Later | Later | VideoToolbox (decode first) |
| Input from a viewer (milestone 5) | CGEvent, with the person's consent | Later | Later | Later | Not applicable |
| Background connection | Yes | Yes | Yes | Foreground service | No; push notification wakes the app |

## Non-goals

- Extracting the internal state of arbitrary apps. No platform allows it.
- Remote control of iOS or iPadOS through Apple's private interfaces.
- Being a general remote desktop or VPN product.
