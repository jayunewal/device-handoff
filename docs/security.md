# Security model

What Baton protects, who it defends against, and how. Each mechanism below says whether it is *implemented*, *partly implemented* or *planned* (designed but not built yet). Pull requests update this page as they land, so it never claims more than the code does.

To report a vulnerability, see [SECURITY.md](../SECURITY.md).

## What is being protected

- **The contents of handoff items** while they travel: clipboard text, links, and later files and tabs.
- **The device key.** Whoever holds it *is* that device to every device that paired with it.
- **The list of paired devices.** It decides who may send things to this device.
- **What this device does with an item.** Opening a link or replacing the clipboard acts on the person's behalf, so it must not happen because a stranger asked.

## Who is considered

| Adversary | Can do | Baton's answer |
| --- | --- | --- |
| Passive or active network attacker on the LAN or the internet | Read, drop, modify or replay packets | The connection is QUIC with TLS 1.3, mutually authenticated by device keys. Tampering fails the handshake; content is unreadable. |
| Relay operator | See which public keys talk, from which IP addresses, and how much | Relays forward ciphertext only. Metadata is visible to them (see limitations). Relays are replaceable and self-hostable. |
| Unpaired device that can reach this one | Dial this device's address or public key | After the handshake the connection is closed unless the peer's key is in the trust store. No application data is read first, and nothing is remembered about the stranger. |
| Someone who sees a pairing ticket (QR code over the shoulder, a leaked screenshot) | Try to pair | A ticket works once and expires after five minutes. A request must carry a proof that only a holder of the ticket's secret can make, and the person on the offering device must approve it, by checking that a six-digit code shown on both devices is the same and reading the name and key fingerprint. The code depends on the session, so a stranger's device cannot show the one the person is waiting for. An offer puts one request to the person, and a ticket whose request is declined, goes unanswered or is abandoned by the device that sent it is spent, so one that leaked is dead and cannot raise a second prompt with a second code to guess. |
| Someone who does not hold a ticket but wants to pair, or to find out whether a device is offering to | Guess secrets, probe for an open offer, cancel an offer in progress | The secret has 256 bits. Every request without a valid proof is refused the same way and after the same delay, whether the proof was wrong, the offer expired, or there is no offer at all. A wrong proof does not void the offer, so nobody can cancel a pairing by spoiling it. |
| Someone who floods the device with connection attempts or requests | Use up CPU, memory, connection slots or the person's attention | Layered limits, best-effort (see below). Strangers are closed right after the handshake and leave no state behind. A flood can slow the device down or make it unreachable for a while, but cannot make it act. |
| A paired device that is lost, stolen or compromised | Send items as a trusted peer | The receiver's per-device policy limits the impact: items go to an inbox, and links and clipboard are not acted on automatically unless the person opted in. A device that sends too much is rate limited. A device that the person at a Mac allowed to start sessions can also look at that Mac, and with the other setting control it, while it is awake and unlocked (window streaming, below); that setting is off by default. Unpairing removes the key and the settings with it, and closes live connections, including ones in use at that moment. |
| Another local user or process on the same machine | Read key files, talk to the control socket | Key and state files are readable only by the owner. The control socket is private to the user. |

Out of scope: an attacker who controls an unlocked user session or the operating system, traffic analysis by a global observer, and hiding metadata from relays.

## Mechanisms

| Mechanism | Status |
| --- | --- |
| **Device identity.** An Ed25519 key per device, generated on first run and stored in a file only the owner can read; Baton refuses to use a key file that other users can read, and never overwrites one it cannot parse. The public key is the device's identity everywhere. The file also records which machine made the key, as a hash of the operating system's own machine identifier (`/etc/machine-id`, `IOPlatformUUID`, `MachineGuid`), and Baton refuses a key file it finds on another machine, which is what a migration tool or a backup restore produces. Where no identifier can be read, nothing is checked. | Implemented |
| **State directory and files.** A state directory that Baton creates is private to its owner from the start. One that already exists is never re-moded, because it may belong to something else (`BATON_HOME=$HOME`, or `/tmp`), and is refused if other users can write to it, since they could replace the files in it whatever the files' modes. `devices.json`, which decides who may connect, gets the same check as the key file, and `config.toml`, which controls relays and discovery, is refused if other users can change it. The check is made on the open file, so nothing can be swapped in between checking and reading. | Implemented on Unix; see the Windows limitation below |
| **Authenticated, encrypted transport.** QUIC and TLS 1.3 through iroh; both ends are identified by their keys, so a connection to a given identity cannot be impersonated. Only the two Baton protocols are accepted, peers cannot open one-way streams or send datagrams, and a handler that panics cannot stop the node from accepting connections. | Implemented |
| **Access control after the handshake.** The session protocol accepts only keys in the trust store, checked right after the handshake and again for every request. Everything else is closed with an error code before any message is read. Removing a device from the trust store is in effect before anything is told about it, and it closes the device's live connections in both directions; the check on each request also refuses a connection that was being set up while the device was removed. The pairing protocol is open to anyone by necessity and is covered below. | Implemented |
| **Pairing.** One device creates a ticket holding its address and a random 256-bit secret, valid for five minutes and for one successful use. The joiner proves it knows the secret with a keyed hash bound to both device keys and to the TLS session, so the secret itself is not sent and a proof cannot be replayed on another connection. Both devices then work out a six-digit confirmation code from the same inputs and show it, and the offering person approves only if the codes are the same, seeing the joiner's name and key fingerprint too; there is no setting that skips this. A request without a valid proof is answered the same way and after the same delay whatever the reason, so a stranger learns nothing, and a request that is declined ends the offer. Only one offer is open at a time. | Implemented |
| **Flood resistance at the door.** When connection attempts arrive faster than 64 a second from addresses that have not proven themselves, they are asked for a QUIC retry token first, which a real device answers by itself and a forged address never sees. A proven address may start 20 connections every 10 seconds (an IPv6 sender is counted by its /64, since a host can use any address in it). Through a relay, a paired device's key has an allowance of its own that no stranger can use up, because the key is looked up before the handshake; every other key is treated like an address that has not proven itself and shares one small allowance once it has, because keys cost nothing to make. At most 8 pairing connections are served at once: when they are all taken, a newcomer pushes out the oldest one that has not shown a valid proof, and one that sends no request within 10 seconds is closed anyway, so idle connections cannot hold the places. A paired device may hold 8 connections, the oldest of which are closed first. | Implemented, best-effort |
| **Trust store.** Paired keys are stored with names, last-known addresses and policies, written atomically (temporary file, flush, rename) in a file only the owner can read. A damaged file is an error, never an empty list, and is never overwritten; a file from a newer version is refused. The list is capped at 256 devices. A change is saved before it takes effect, so a failed write changes nothing, and checking whether a device is paired never waits for a save. Addresses and relays that a peer reports are cleaned before they are remembered, kept in a fixed order, and, after the first of each, saved at most once a minute per device, so a peer cannot turn its connections into disk writes. | Implemented |
| **Handoff policy.** Per paired device, on the receiving side. Defaults: links and clipboard text go to an inbox. Auto-opening links and auto-applying the clipboard are opt-in. Only `http` and `https` links are ever opened. | Settings and cautious defaults implemented. Until the agent exists, a link set to open and text set to apply are kept in the inbox like the rest, and ignored kinds are declined. Opening and applying arrive with the agent |
| **Received items and the inbox.** An item from a paired device is checked before it is kept. A link must be a well-formed address without spaces or control characters, and it is kept in its normal form: plain ASCII, with characters that reorder text or hide part of the address percent-encoded. A page title is cleaned like a device name, with room for 256 characters where a name has 64, and both the title and the sender's name are cleaned again when they are read back. Clipboard text is kept exactly as sent, so a front end that prints it must not pass control characters on to a terminal. The inbox is one file that only its owner can read, changed under a lock because the listener and the commands that read and clear it are separate processes, and kept to `handoff.max_inbox_items` items (200 by default) and 3 MiB with the oldest dropped first. A damaged inbox is an error and is never overwritten. An item that cannot be kept is declined, so the sender is never told that something was accepted when it was not. | Implemented |
| **Strict message decoding.** A message is read completely as CBOR and rejected unless it is exactly one well-formed item, before any of it is interpreted. Sizes are checked before anything is allocated, nesting is limited, and unknown variants of fixed enums are errors. The decoders are covered by property tests, by a test that damages valid messages in every position and compares the decoder with an independent CBOR checker, and by fuzz targets. | Implemented in `baton-proto` |
| **Received files.** Only a paired device can offer files, over a connection that has proved who it is. The offer is put to the person with the name of the device and how much is coming, and nothing is kept until they say yes. They have two minutes, and a no, a timeout and an app that stops keep nothing. The files are written into a hidden folder inside the destination, checked against their hashes, and moved into place only when the transfer has ended, one by one and never over anything that exists, so a folder never holds half a file. The receiver chooses every name: characters the file system does not allow and the ones that only disguise a name are replaced, a name that is taken gets a number, and a link inside a folder is neither followed nor made. Baton does not open what arrives: the button on the card of a finished transfer shows the files in Finder or the Files app, and what a file does when it is opened is for the person to choose. A paired device may have two transfers going at once, with four lanes each. See [section 8 of the protocol](protocol.md#8-file-transfer) and [ADR 0008](adr/0008-file-transfer.md). | Implemented in the library and in the app. Not yet tried on an iPhone or a Mac |
| **Resource limits.** Maximum frame and item sizes checked before allocating, a limit of 16 concurrent streams per connection and a deadline for a request to arrive and for its answer (both are for the small control messages; file transfer will have budgets of its own), flow-control windows that cap the unread data one connection can make a device hold at 64 KiB until the device on the other end is known to be paired, which is all a stranger ever gets, and at 16 MiB after that (less than the library default allows, and enough for one stream to fill a fast path; see ADR 0007), a rate limit on items per paired device (30 a minute by default; one whole file transfer will count as one item), and a size limit on clipboard text. A retry of an item that was already handled is recognised and not handled again, and does not count against the rate limit. | Implemented for what exists; the file transfer budgets come with file transfer |
| **Display names.** Names that arrive from a peer have control characters and every invisible or text-reordering character removed (zero-width characters, direction overrides, variation selectors, tag characters, blank Hangul fillers) and are length-limited before they reach a prompt or a log. A name is a label and never a reason to trust a device: look-alike letters survive cleaning, so prompts show the key fingerprint beside it. A device is shown under the name the person gave it when pairing, not under the name it reports later. A changed name is remembered and flagged for the person to accept or ignore, and two paired devices shown under the same name are flagged too, so a paired device cannot pass itself off as another one. | Partly implemented: the sanitiser is in `baton-proto`; the trust store and the pairing exchange apply it, the trust store keeps the person's name apart from the reported one and flags renames and shared names; the command line shows each beside the key fingerprint and escapes it first (see the row below), and the agent's prompts come with the agent |
| **What the command line prints and opens.** Everything another device chose (a link, a title, some text, a name, the reason it gave for hanging up) is printed with control characters, the C1 range, direction overrides and line or paragraph separators shown as visible escapes such as `\u{1b}`, so what arrives cannot move the cursor, clear the screen, change the window title, set the clipboard or make a link read differently from what it is. A lone carriage return is escaped too, since it would let later text overwrite earlier. Error messages are escaped as a whole when they are made, since some carry text a device chose, and what a device said when it hung up is kept on one line so that it cannot pass for a line of the program's own. The program's log keeps the networking library's messages out unless `-v` is given. `baton inbox open` opens `http` and `https` links and nothing else: a `file:` link, a custom app scheme or `ms-msdt:` are shown but never opened, because opening them can start programs. Nothing is opened, copied or applied unless the person types the command for it, and a command that asks "are you sure?" (pairing, unpairing, clearing the inbox) treats anything but `yes` as no. Only one process runs a device at a time; reading the inbox and the list of devices needs no lock and works while another window is listening. | Implemented |
| **What a bug report shows.** The app keeps its last 400 log lines in memory only, and the Diagnostics page copies them with a few facts, to be pasted into public issues. A line is cut to 600 characters, text that turns around or hides is replaced, a pairing code is removed together with the rest of its event, a key of 64 hexadecimal digits is cut to the short form of a device, the account name in a path becomes `~`, and a public IP address is shown only by its kind and port, because it names the network and, with the port mapping, a port on the router that leads to the device. The fingerprint is not on the page, because it can be worked out from the key that is announced on the local network (see private discovery below). A panic is logged through the same cleaning. What is left is still personal: the names of the device and of the ones paired with it, their short ids, the addresses of the local network and the address of the relay, and the page says so before the person copies it. | Implemented in `baton-ffi` and the app |
| **Private discovery.** On the local network a device announces a short value that changes every 15 minutes and that only its paired devices can recognise, instead of its permanent key. See the design goal below. | Planned, after milestone 1 |
| **Key storage in OS keystores** (Keychain, Credential Manager, Secret Service, Android Keystore). The move must keep the key readable while the screen is locked, because the agent has to work then: Keychain items with `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`, iOS files with `NSFileProtectionCompleteUntilFirstUserAuthentication`, Android Keystore keys without `setUnlockedDeviceRequired`, and a different home for the key where a Secret Service collection locks with the screen (a KWallet option, and some GNOME setups). The default classes (`WhenUnlocked`, `NSFileProtectionComplete`) would leave the agent deaf at the lock screen. `ThisDeviceOnly` Keychain items and DPAPI-protected secrets also do not move between machines, which ends the problem of copied identities on those platforms. | Planned, later milestone |
| **Honoring "concealed" clipboard flags** that password managers set. | Planned, later milestone |
| **No unlocking, ever.** Baton has no feature that unlocks a device and no code that calls a platform's unlock function. On Linux any process of the same user can ask the session to unlock without a password, so a compromised agent could do it, and other tools ship a remote-unlock feature. See [locked-devices.md](locked-devices.md#55-baton-never-unlocks). | A rule for every milestone; nothing to build |
| **Locked mode.** While a device is locked, or when it cannot tell, received items go to the inbox and nothing is opened, applied or started, even where the person's policy would allow it once unlocked. The device still delivers items the person explicitly sent to a named device, and only to that device, but serves staged items to a paired device only if the person allowed that for that device. An open pairing offer ends at the lock. A locked device also refuses to start a send (with a short list of exceptions while it cannot tell whether it is locked), and every phone action that starts a send asks for authentication, so someone who holds only the locked device cannot create items. See [locked-devices.md](locked-devices.md#54-locked-mode-on-the-receiving-side) for receiving and [section 5.2](locked-devices.md#52-stage-before-leaving-and-do-not-read-a-locked-device) for sending. | Planned, with the agent |
| **Window streaming and remote input.** A session is offered by the device whose screen is shown, to one paired device, and needs a yes from that device. The person at the Mac picks the window or the screen in the system's own picker, chooses at each offer whether to grant control (view only is the default), sees which device is viewing or controlling, and can stop or take control away at any time. A viewer can make a Mac start sharing its main display, and wish for control, only for a device that the person at the Mac allowed beforehand: a setting for each paired device, off by default, with looking and controlling apart, that is changed only at the Mac and by no message. No one at the Mac is asked then, so that setting is the yes, and it is read when the request arrives and not when the connection began. The offer is the ordinary one. It carries control only if the viewer wished for it and the setting allows it, and the viewer takes no more control than it wished for. The viewer takes without asking only the offer that answers its own start (from the device it asked, under the id it chose, of the kind it asked for, while it waits), so a Mac cannot put a session on a phone that did not ask for one. A phone that is stolen or left unlocked, and was allowed, can therefore look at a Mac that is awake and unlocked, and with the other setting control it; that is the cost of the setting, and a locked Mac is not woken or unlocked by it. A start counts as one item against the limit of the device, and a start that the setting refuses costs nothing. Input is checked before it is used and dropped unless its point is inside the shared window and nothing is in front of the window at that point. A key goes only to the shared window, and only while that window has the keyboard, no window of the same application lies over it, and no menu of the application is open. The events of a window go to the system, as if the person at the Mac did them, so the pointer of the Mac moves with them and an event goes to whatever has the pointer or the keyboard at the moment it is posted, which the checks above judged to be the window a few milliseconds before, or longer before for an event late in a batch (inferred: something that changes in between, such as the person at the Mac clicking elsewhere, can send an event to another window). The shortcuts that the system keeps for itself (search, the application switcher, Mission Control, force quit, locking and logging out, and moving the keys to the menu bar or the Dock) are left out by a list of the defaults of the system, so a Mac whose shortcuts were changed may act on other keys. A whole display can be controlled too, and then the person grants the whole screen, with every window on it and the keys that the system keeps for itself: the point has to be inside the display and a key goes to whatever has the keyboard, the person chooses that for each offer, or beforehand for a device that starts its own sessions, the Mac shows that the display is controlled, and a lock of the Mac still stops all input. The person in control of a display can cover or hide the Mac's own card and press its Stop button, so what stays is the person's yes for that offer or for that device, the indicator that the system shows for a screen that is shared, and the lock. A button or a key that was pressed is always released, also when control is turned off. The Mac stays unlocked while it streams, and nothing is shown or typed at the lock screen. A session that a paired device started with control is private ([ADR 0011](adr/0011-privacy-mode.md)): while it lasts the screens of the Mac are black and the app holds its keyboard and pointer, so that nobody at the Mac can read what is done or use the unlocked Mac, except for what the person at the other device lifts (below), and when the session ends, whatever the cause, including a connection that drops, the Mac is locked and only then do the screens and the keys come back. A Mac that cannot be locked stays dark and held. Three presses of Escape at the Mac end the session and lock it, unless the keys are lifted. A program that has the keyboard to itself, such as a password field, can still receive keys from the Mac, until the session notices a key and ends; it sees the last key only, so a key at the Mac that is followed by a key from the other device before the next look is not seen, and while the other device goes on typing into such a program a person at the Mac can put more than a character or two there. A Mac whose app has not been let hold the keys and the pointer starts no such session. A session that looks only, or that the person at the Mac started, is not private; that is by design. The person at the other device can lift two things in the settings of the session, each by itself and as often as they like: that the screens show what is on them, and that the keys and the pointer of the Mac can be used at it. Both are off at the start of every session, and nothing is remembered for a device. While the screens are lifted anyone near the Mac sees what is done, what is typed and the notifications included. While the keys and the pointer are lifted anyone at the Mac can use it, unlocked, and the three presses of Escape and the notice of a key at the Mac do nothing. So a device that is allowed to control a Mac can light it and open its keys while the session lasts, which is the cost of the setting for control. Only a private session takes the message, and a Mac whose platform cannot lift anything does not tell the other device that it may. Whatever ends the session puts back what was lifted and then locks the Mac, a part that cannot be put back ends the session, and the guard is told no differently, so a Mac whose app dies with something lifted is locked in the same way. A device that vanishes while something is lifted leaves the Mac as it is until the session ends, at the latest 30 seconds after its last report. A key or a button that is down at the Mac when the keys are held again may stay down as far as the system knows until it is next pressed. A quit of the app, which the person at the other device can cause by mistake, locks the Mac first, and waits for that for ten seconds at most. A guard, a small program inside the app that the app starts for each private session and that inherits the app's sandbox, locks the Mac if the app dies (a crash, a kill) or hangs: it is armed before the screens go dark, it is told four times a second that the session is well, and it locks the Mac, in the same three ways, when the pipe from the app closes, when nothing comes for three seconds, or when it is told to terminate, and ends without locking when the session ends. After a crash or a kill the screens show the desktop and the keys work for the moment that the guard takes to see it and lock the Mac, a fraction of a second. After a hang the screens stay dark for the three seconds that the guard waits and the keys may come back for a moment (a process that does not answer probably loses its hold of them: inferred, not tried), and the Mac is then locked; a hung app that is still alive probably keeps the screens dark until it is ended. A Mac whose guard cannot be started starts no private session, a guard that is lost ends the session, and killing the app and the guard together leaves the Mac open. Sound is not part of the promise: the speakers of the Mac play on. Pictures are not written to disk, and window titles are shown but never logged. A viewer reads the size that the parameter sets of a picture describe, as it is shown and as it is coded, and refuses a picture beyond what it said it can take before its decoder sees it, because a decoder allocates by the sets and they come from another device. The Swift that receives a frame reads each struct only up to its stated size, checks every pointer and count, gives the decoder a copy of the picture and of the sets, and does not trap on what it is given. On the sharing side the window that the person picked belongs to the app from the moment the platform hands it over, and is let go of exactly once; the platform is asked to capture it only after the other device has said yes, and a no ends with nothing captured. The Rust side reads what the platform's encoder hands over as it would read what the network gives: a length that reaches beyond the picture, a key frame without a slice of an IDR picture or without a sequence and a picture parameter set, more or larger parameter sets than the interface allows, and a picture larger than the protocol allows are refused before anything goes out, and the size of the picture that a platform asks for is held to what the protocol allows and what the viewer said it takes, and so is the size that the parameter sets of a key frame describe, since the viewer refuses a larger picture and nothing on this device would say why. The Swift that shares a window does the same with what the Rust side passes it, and captures only what the person picked in the picker of the system, a window or a whole display, so that the app never sees anything else, and the system shows that it is shared and lets the person stop it. For a session that a viewer started, the Mac captures its main display without the picker, since the person allowed that for the device beforehand, and the consent of the system to record the screen, which the person gave once, stands in the place of the picker; without that consent the Mac captures nothing and tells the device that it needs permission. See [ADR 0009](adr/0009-window-streaming.md) and [ADR 0010](adr/0010-sessions-that-the-viewer-starts.md). | Planned, milestone 5 |

## Design goal: private discovery

A device that wants to be found on the local network announces its public key over mDNS, and with DNS discovery on it also publishes where to reach that key in a public DNS service. A key that never changes is a tracking handle. Anyone on the same café Wi-Fi learns it, and can then ask public DNS from anywhere, at any later time, whether the device is online and roughly which region it is in. Other tools in this space broadcast stable identifiers in the same way. Baton aims to do better: someone who is not paired with a device should learn nothing that links one sighting of it to another.

The sketch below is to be refined when it is built.

- At pairing, each device gives the other a random 32-byte *presence key*.
- On the local network a device announces only `BLAKE3-keyed(presence key, current 15-minute window)` cut to about eight bytes, plus its addresses. A paired device works out the value it expects from each peer, accepting the neighbouring windows to allow for clock skew. Everyone else sees a value that changes every window and links to nothing. It is the same idea as the resolvable private addresses in Bluetooth.
- iroh's discovery is pluggable, so this can be a discovery service of Baton's own rather than a fork.
- On the internet side, the trust store already remembers each peer's home relay, which is enough to dial it. A DNS lookup is needed only after that relay changes, so DNS discovery stays off by default until a record under a name derived for each pair can replace the one published under the device key.

Open questions: whether there is one presence key per device or one per pair (a key per pair makes the announcement larger and shows how many devices are paired, while a key per device has to be replaced and handed out again whenever a device is unpaired), and how a device that was offline for longer than a window catches up.

## Known limitations

- **Metadata is not hidden.** To find devices on the local network, Baton announces its public key and addresses over mDNS to everyone on that network. The service name is specific to Baton, but a person on the same Wi-Fi can see that a Baton device is present. Because the key never changes, it can also be used to recognise the same device on other networks. Private discovery, described above, is the planned fix. Relays see which keys talk to each other and from where. Turn LAN discovery off in settings if that matters to you.
- **DNS discovery trades privacy for convenience, so it is off by default.** With it on, a device publishes where to reach its key in a public DNS service run by the iroh project. Anyone who has ever seen the key, for example from the local-network announcement on a café Wi-Fi, can later ask whether the device is online and roughly where. Paired devices already remember each other's relay, so the lookup only helps after a peer's relay changes. If devices stop finding each other after moving between networks, turn on `network.dns_discovery`. A record published under a name derived for each pair would remove the trade-off (see private discovery above).
- **Port mapping opens a port.** To let devices on different networks connect directly, Baton asks the router to forward a port (UPnP, NAT-PMP or PCP). Set `network.port_mapping = false` to stop it. Connections then use a relay when no direct path can be found by other means.
- **Flood resistance is best-effort.** The limits on connection attempts cannot tell a forged address from a real one until it answers a retry token, and they are tuned so that ordinary use never notices them. A determined attacker with enough bandwidth, or enough addresses, can still make a device slow or unreachable. What they cannot do is get a stranger's request acted on. In particular, connections that show nothing cannot hold the pairing places, because newcomers push them out, so keeping real joiners out takes a rate of new connections, each with a finished handshake, far above what the admission limits let one source start. It does not affect devices that are already paired, which use separate connections and limits.
- **A ticket is a bearer secret.** Anyone who gets it before it expires or is used can request pairing. The approval step is the safeguard: compare the six-digit code on both devices, and decline if the other device shows no code or a different one. Do not paste tickets into services that keep logs. A QR code swapped for a different one by someone with physical access would pair the joiner with their device, and the confirmation code cannot catch that, because it matches between the joiner and the device it really talked to. The device you meant to pair with never gets a request, so notice when it does not, and compare the fingerprint the joiner prints with the one on the device you meant.
- **Windows file permissions are not set by Baton.** On Windows the state directory and its files inherit the permissions of their parent. For the default location, `%LOCALAPPDATA%`, that is the user's own profile, which other users cannot read. A `BATON_HOME` somewhere else is not restricted and nothing checks it. An explicit owner-only access list set when the directory is created is planned, together with a test on real Windows; it is not shipped untested.
- **A copied identity is caught only where Baton can identify the machine.** The check covers Linux, macOS and Windows desktops. It cannot see an app's data restored onto a new phone, a container without a machine identifier, or a copy made by someone who can also edit the key file. Until the key lives in a keystore that cannot leave the device, use one state folder per device, and after restoring a backup onto a new machine, pair again.
- **The clipboard may contain secrets.** Automatic clipboard sync is off by default. Until Baton honors the "concealed" flags password managers set, turning it on for a device means everything copied on the other devices is sent to it.
- **The inbox is stored on disk unencrypted**, readable only by the owner. Anything you send to a device can be read from its inbox by anyone who can read that user's files.
- **Pairing is not atomic.** If the connection drops after the offering side approves but before the joiner stores the result, the two sides disagree about whether they are paired. Run pairing again.
- **Compromise of a paired device is not contained by cryptography**, only by policy. Remove the device from the others as soon as you know.
