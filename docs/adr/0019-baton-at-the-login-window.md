# 0019: Baton at the login window: a small Baton starts with the Mac, shows the login window to a paired phone and passes its input

Status: superseded in part by [ADR 0020](0020-screen-sharing-at-the-login-window.md). L1 and L2 below were tried on the person's Mac on 2026-11-11 and both failed, so the capture-and-post decision below is not built further. The device and the pairing it describes stay, and are reused as they are in ADR 0020.

## Context

[ADR 0017](0017-away-from-home.md) lets a phone give the password of an account to a Mac that restarted with FileVault on, over SSH, so that the Mac can start. On 2026-11-11 the person tried it at home on one Mac (macOS 27.2, FileVault on, Remote Login on, a build signed with the Baton Signing certificate). The Mac did not sign the account in. Its logs show that the system was up and showing its login window, and that nobody signed in until the person did it by hand, about three minutes later. In those minutes the phone could reach the Mac's SSH door (**Check the way** said that the way is open), so the network was up at the login window, and the phone had nothing of Baton to talk to. Baton for Mac is a login item of one account (`SMAppService.mainApp`, [architecture.md](../architecture.md)), so it starts when that account has signed in and not before. The part of the start where a password is taken is not in the Mac's logs, so that the unlock itself came from the phone is the likeliest reading and not a measured one.

The person asked for the missing part: a service of Baton that starts with the Mac, before anyone signs in, so that the phone can come in, with a setting that turns it off.

What is known, and how well:

- Nothing documented signs an account in while FileVault is on. The ways that were found are FileVault off with automatic sign-in, a screen sharing client, and a plug-in of the authorisation (reported: Apple's documentation and the answers of Apple's engineers on the developer forums, as the research of this project read them on 2026-11-11). Automatic sign-in is switched off by FileVault, an authenticated restart (`fdesetup authrestart`) skips the disk password once and then stops at the login window, and no command of device management that signs a person in was found (not tried here).
- FileVault itself signs the account in after a password that was typed at the Mac's own start screen, unless `DisableFDEAutoLogin` is set (reported). It was not set on the person's Mac, and the unlock over SSH did not sign anyone in (observed once).
- An engineer of Apple's developer technical support says on the developer forums (thread 814152) that a screen sharing product loads one launch agent for both the `Aqua` and the `LoginWindow` session types, that the agent captures the screen and posts the events while a daemon does the global things such as the network connection, that capture before sign-in works on macOS 14.4 and later, and that a daemon must not touch the window server (reported by an engineer, and checked against the thread in the review of this record). The thread spells the key `LimitLoadToSession`; launchd.plist(5) spells it `LimitLoadToSessionType`, and the file of this program uses the manual's spelling.
- Apple's technical note TN2083 (Daemons and Agents) says that an agent that is loaded for the login window runs in the login window context and is ended when a user logs in, that a second instance starts then in the user's session if the agent is loaded for that session too, and that a daemon cannot connect to the window server (documented; read in the review of this record). The part that was read does not say as which user a login window agent runs, which stays inferred, and launchd.plist(5) says that `UserName` is ignored for agents and applies only to services in the privileged system domain (documented).
- Two developers report that events posted from an agent in the login window did not arrive (threads 62687 and 724740, neither answered by Apple). Apple changed the Screen Recording policy in macOS 15 and did not publish the new rule (thread 768146), and the entitlement that screen sharing products may ask for needs the paid developer program. Whether capture and typing at the login window work for a build that is signed with the Baton Signing certificate, on macOS 27, is not known.
- The Mac app is sandboxed ([the entitlements](../../apps/baton/macos/Runner/Release.entitlements)), so it cannot write a system folder or start a program as root. A second program is built here the way the guard of the privacy mode is: by a script of the app's build that puts it into the app next to the app's own program (`apps/baton/macos/Guard/build-guard.sh`).
- A pairing is put to a person, who compares a code on both devices, and nothing outside the tests approves for them ([ADR 0006](0006-pairing-admission-and-requests.md)).

## Decision

**A small Baton of its own starts when the Mac shows its login window.** It is one program, `baton-loginwindow`, which launchd starts as a launch agent for the `LoginWindow` session type (a file in `/Library/LaunchAgents` with `LimitLoadToSessionType` set to `LoginWindow`, run at load and kept alive). It runs from the moment the login window is up, and the system ends it when someone signs in (documented, TN2083; L5 looks). That it runs as root is inferred, from the processes of the login window running as root and from launchd ignoring `UserName` for agents, so that nothing in its file can change it (L3 looks). It is the Rust library of the app without a screen of its own (`baton-app`, with the platform of the Mac for capture and input, as in [ADR 0009](0009-window-streaming.md) and [ADR 0010](0010-sessions-that-the-viewer-starts.md)), and it keeps what it needs in a folder of its own that only root can read.

**One agent and no daemon, for now, and the price of that is named.** A daemon cannot connect to the window server, so the part that captures and posts has to be an agent, and one agent is the smallest thing that answers L1 and L2. The price is that launchd honours `UserName` only for daemons: the part that listens, which could run as a user of its own in a daemon, runs as root here, together with the part that captures and posts (Consequences says what that means). Splitting the program into a daemon that listens as a user of its own and an agent that only captures and posts is the first hardening, and the fix of the gap after the sign-in (below), which needs something that lasts across the sign-in, is likely to bring a daemon back as well. It is left for later because it is a second program and an interface between two programs, built before L1 and L2 have said whether the picture and the typing work at all.

**It is a device of its own, and a phone pairs with it like with any device.** It has a key of its own and a list of devices of its own, and the phone shows it as another device, `<name of the Mac> (login window)`. The pairing is done in Terminal at the Mac: the program prints a ticket and puts it on the clipboard, the person gives it to the phone (**Add a device**, **Enter code**), and types in Terminal the six digits that the phone shows, since nobody else is at a Mac that has no screen of its own for it. The program checks them against the six that it worked out itself and does not print them, so the person has to read them off the phone. It prints nothing else that the device sent with the question but the system it says it runs, and above all not its name: a stranger who holds the ticket works the six digits out before it sends its name, and a cleaned name keeps digits, so a name could be the digits a few lines above where the person types them (the name and the fingerprint are shown once the phone is paired). And a `yes` or a Return that was typed before the phone asked is not taken for them (a terminal keeps what is typed while a program waits, so a `yes` would be waiting for the first device that asked). The key and the list of the app are not shared, for two reasons. The app's folder is in its sandbox, where a program that is not the app is kept out (inferred, not tried here), so the program could not read it. And a copy of the key would make two programs one device, which answer in turn. The price of a list of its own is that the app cannot see or change it: it is in a folder that only root can read, outside the sandbox. So removing a phone in the app does not remove it here, and forgetting the Mac at the phone does not either, since an unpairing is local to the device that does it (the roster that would spread it is a design that is not built, see [architecture.md](../architecture.md)). Two things end the trust of a phone, `baton-loginwindow forget` and the remove script, and both are run in Terminal at a Mac that someone has signed in to. For a lost phone they are the only way, and the card in Settings says so when it is built.

**It offers the main screen with control, and nothing else.** To a device that it paired with it gives the main display, and passes the events of the phone to the login window, as a session that the phone starts ([ADR 0010](0010-sessions-that-the-viewer-starts.md)); the pairing sets the `start` setting of that device to control, and nothing in the program changes it. It takes no links, text or files, reads nothing of what the person works on, and does not unlock anything. It asks nobody, since nobody is signed in to be asked. It does not cover the display or hold the keyboard of the Mac as the privacy mode does ([ADR 0011](0011-privacy-mode.md)): nothing private is on a login window, and a hold there could lock the person out. The phone's own rule stays: it checks the person who holds it before it starts a screen session, by their face, or by the passcode of the phone when the face is not recognised ([security.md](../security.md)), whatever the Mac is.

**It is installed by the person, with an administrator's password, as plain files, and removed the same way.** The app stays sandboxed and does not do it. A card in the Settings of the app says what the program does and shows one line to paste in Terminal. The line runs, with `sudo`, a script that is in the app (`Contents/Resources/login-window/install.sh`): it copies the program into `/Library/Application Support/Baton/LoginWindow/`, owned by root and writable by no one else (a program that root runs must not sit where the processes of a person can replace it), checks that it is signed with the same certificate as the app (its designated requirement, since each person makes their own Baton Signing certificate and any valid signature would pass otherwise), writes the launch agent file, and starts the pairing. `uninstall.sh` removes the agent, the folder and with it every pairing, and is the switch that turns it off. The newer in-app way (`SMAppService.daemon`) is not used: it is unproven with the Baton Signing certificate and asks for an approval in System Settings, while plain files need neither that nor an Apple account.

**No password is stored. The person types it on the phone.** The phone shows the login window and passes taps and keys, and the person types the password of the account as at the Mac. Typing it for the person, with the box of [ADR 0013](0013-unlock-from-a-phone.md) opened by the face, is a later change that needs L1 to pass and the box in the folder of the program, set up in Terminal; it has its own pull request and is read against that record.

**After the sign-in the session ends, and the phone goes on with the normal Baton.** The login window goes away when someone signs in, and the system ends the program with it (documented, TN2083). The phone's session ends with it, and the person opens the Mac under its own name. A later change makes the phone do that itself after the unlock: wait for the login window device, open it, and open the normal Mac when it ends.

**A gap remains, and in it the Mac is open.** The session at the login window ends with the account signed in and nothing holding the keyboard and the pointer of the Mac: no cover, no hold and no lock. Anyone at the Mac can use the signed-in account, and see its desktop, from the sign-in until the phone's next session starts and the privacy mode of the app takes the Mac over. [ADR 0011](0011-privacy-mode.md) says that a Mac that another device controls locks when the session ends, and this session ends with the Mac open. How long the gap lasts, for a phone that opens the Mac at once, is the time that the app of the account needs to start plus the time that the phone needs to connect and start its session (L6 measures it). For a phone that does not, because the way dropped or the person stopped, Baton sets no limit: the Mac stays open until its own screen lock locks it, which is the person's setting and can be never. The fix is a later change, not designed here beyond what it has to do: the same program, loaded for the `Aqua` session too, covers the display and holds the keyboard from the sign-in until the app takes over, when a phone's session was running at the login window, and locks the Mac if no session follows within a set time. Until it is built, the guide and the card in Settings say so.

**What the program may do, and what it may not.** It runs as root and listens on the network before anyone signs in. It listens as every Baton does: a stranger is closed after the handshake, pairing is refused unless the person opened an offer in Terminal a moment ago, and only a device on its own list can ask for a session ([ADR 0006](0006-pairing-admission-and-requests.md)). It opens no shell, runs no command, reads and writes nothing outside its own folder and the screen and input of the login window, logs no key that is typed (the log says that a session began and ended, and nothing more), and does not run in any session but the login window. launchd starts it again if it dies. **This list is what the code promises, and not a limit that the system enforces**: nothing holds a program that runs as root to it once the code is wrong, and Consequences says what that means. The commands that the person runs in Terminal, `pair` and `forget`, run as root too, under `sudo` in the person's session. `pair` starts the same node that listens, with the network on for as long as the pairing takes, so the same limits and the same risk apply to it.

**If the two unproven points fail.** L1 (events at the login window) and L2 (capture at the login window) decide. If capture is refused, the program cannot show the login window, and what is left is typing blind with the box of ADR 0013 into the name and password fields, which the login window can be set to show so that typing is predictable; that needs L1. If posted events do not arrive, neither control nor typing works, and the plug-in of the authorisation is what is left, which ADR 0013 turned down for what a faulty one does (no account can sign in until the Mac is repaired from recovery) and which gets a record of its own before anyone builds it. If both fail, nothing of Baton reaches the login window, and the person signs in at the Mac. The screen sharing of macOS may reach the login window after the unlock (reported by the research of this project, not tried here), and the guide does not name it.

## How it will be measured

Without Apple hardware, on every pull request: the Rust part runs against a platform that plays the Mac, with a pairing and each way it is refused, a device that was not paired, the `start` setting, no links, text or files, the permissions of the folder, and the stop on a signal. On a Mac, by the person at it, with the notes of the install thread (a Log Out shows the login window again, so L1 and L2 need no restart):

- **L1. Events at the login window.** A launch agent for the `LoginWindow` session type, signed with the Baton Signing certificate and given Accessibility in System Settings, posts three harmless letters. Does the password field show three dots? Does it differ when the login window shows name and password fields (`SHOWFULLNAME`), as it does for a Mac with several accounts?
- **L2. Capture at the login window.** The same kind of agent captures one picture of the main display. Does it, does the system ask for a permission that cannot be given at the login window, and does it still work after a restart?
- **L3. The start after the unlock.** Restart the Mac and tap **Unlock** on the phone. Does the agent start at all after the unlock over SSH, as which user does it run (`ps -o user= -p` and its process number says), how long after the first line of the system's log, and how long until the phone can reach it?
- **L4. The pairing in Terminal.** The ticket on the clipboard and on the phone, the codes, the refusal of a pairing that nobody offered, and what the program does when the phone gives up half way.
- **L5. The sign-in from the phone.** Tap the account, type the password, press Return: how long from the tap to the desktop, and what the phone shows when the login window goes away.
- **L6. The gap.** After the sign-in, how long does the desktop show on the display of the Mac before the app covers it, when the phone starts its session at once?
- **L7. The end.** The remove script leaves no file, no agent and no pairing, and the phone says that the device does not answer. A person at the Mac signs in as usual with the agent installed and with the agent killed. Does the installed agent show under **Login Items** and **Allow in the Background** in System Settings, and does turning it off there stop it at the next login window? If so, that is a way to turn it off without Terminal. Apple's page on login items covers only items that are registered with its framework, so this is a check and not a known fact.
- **L8. Away.** L3 and L5 through the route of ADR 0017.
- **L9. A switch of user.** With one account signed in, switch to the login window that a switch of user shows. Does an agent start there while the other account stays signed in, can the phone reach it, and what does it show? Baton shares several accounts at once, so this will come up.

## Alternatives considered

- **The key and the list of the app.** The phone would see one Mac, and nothing would have to be paired again. The folder of the app is not readable by another program (macOS keeps the sandbox container of an app from programs that are not the app: inferred, not tried here), and a copy of the key makes two programs one device. It was the first shape of this record. The price of the shape chosen instead is that the app cannot remove a phone from the list of the program (the lost phone, under Consequences).
- **A launch daemon and an agent, with a way between them.** It is the shape that Apple's engineer describes: the daemon does the global things, such as the network connection, and the agent the things of the window server. It is the shape that takes root off the code that listens, since launchd honours `UserName` for a daemon, and it lets the connection outlive the login window, which the fix of the gap needs. It was left for later because it is a second program and an interface between two programs, built before L1 and L2 have said whether the picture and the typing work. It is likely to come back as the first hardening.
- **`SMAppService.daemon`.** Unproven with the Baton Signing certificate, and it needs an approval in System Settings. Plain files in `/Library` need none.
- **A plug-in of the authorisation.** The most direct way, since it hands macOS the password with no typing and no screen permission, and the most dangerous: a faulty plug-in can leave no account able to sign in. Plan B, with a record of its own, if L1 fails.
- **The screen sharing of macOS, reached from Baton.** The phone would need a client of the protocol that macOS speaks, the Mac would have one more door open, and the session would not have the check of the phone's own rule or the input rules of Baton. It may be a stopgap: it is reported to reach the login window once the disk is unlocked, which was not tried here, and the guide does not name it. If the guide is to name it, it has to say what it costs: one more door open on the Mac.
- **Automatic sign-in, with FileVault off or the password in a scrambled file.** The first gives up the disk's protection, the second keeps the password where a thief of the Mac could read it, and the person's rule is that no password lies there.
- **An authenticated restart.** It covers only restarts that the Mac itself starts, and stops at the login window.
- **Device management.** No command of it signs a person in.
- **The Mac App Store.** A sandboxed app cannot install a launch agent or write `/Library`. Baton for Mac stays a direct download.

## Consequences

- **A program that runs as root listens on the network before anyone signs in.** It answers like every Baton, and it can show and steer a login window for a device that the person paired with it in Terminal. Someone who holds a paired phone and gets past its check, by the face or by the passcode of the phone, reaches the login window, and what stands in the way is the password of an account and the delay that macOS puts after wrong ones.
- **A flaw in the code that answers a stranger would give root on a Mac whose disk is unlocked.** The handshake, the link to the relay and the announcement on the local network all run in the program, as root, on what a stranger sends, before anyone knows whether it is paired. Who can reach that code follows from the network settings that the program takes unless its folder says otherwise (`NetworkConfig` in `crates/baton-core/src/config.rs`): the public relay is on, the announcement on the local network is on, the router is asked to open a port, and the lookup in public DNS is off. So any device on the same network finds the program, anyone who learns its key reaches it through the relay, and where the router grants the port that is asked of it, anyone on the internet who learns the address reaches the handshake directly, with no relay in between (inferred from the defaults, not tried). The list under "What the program may do" is what the code promises, and nothing in the system holds the program to it once the code is wrong. What would limit the reach is not built: a daemon that listens as a user of its own while the agent only captures and posts, which takes root off the code that answers strangers; and a program with no relay and a fixed port that the route of ADR 0017 reaches at the Mac's home address, which takes the internet out of the way in (the settings have no port to fix today).
- **After the sign-in the Mac is open until the next session takes it over.** The session at the login window ends with the account signed in and nothing holding the keyboard and the pointer, so anyone at the Mac can use it until the phone's next session starts and the privacy mode of the app takes over. [ADR 0011](0011-privacy-mode.md) says that a Mac that another device controls locks when the session ends, and this one ends open. For a phone that opens the Mac at once, the gap is the start of the app plus the connection of the phone (L6 measures it). If no session comes, nothing of Baton limits it, and the Mac stays open until its own screen lock locks it, which can be never.
- **A lost phone is removed in Terminal at the Mac, and nowhere else.** Removing it in the app, or forgetting the Mac at the phone, leaves it trusted at the login window. `baton-loginwindow forget` or the remove script ends the trust, run at a Mac that someone has signed in to. Until then, whoever holds the phone and gets past its check can open the login window.
- **Installing needs an administrator's password and Terminal.** The app cannot do it, and says so on its card. The line runs a script from the app bundle as root, so the install is only as safe as the bundle is at that moment.
- **The phone lists the Mac twice**, once under its name and once with `(login window)`.
- **Nothing at the Mac says that a phone is looking at the login window.** The pointer moves, and that is all a person there sees.
- **The login window of a Mac that has no display attached may have nothing to capture** (reported for another product, not tried here).
- **A Wi-Fi network whose password is kept in the login keychain of the person cannot be joined at the login window** (inferred).
- **Every macOS release can change what the login window allows.** L1 and L2 are done again after an upgrade.
- **Sharing Baton for Mac with other people needs Developer ID signing and notarisation**, which is the paid program. The person's own Mac does not.
- **ADR 0017's open point after the unlock is answered** by the observation above, and by this record for what to do about it.
