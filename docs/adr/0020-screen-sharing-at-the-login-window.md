# 0020: Screen Sharing at the login window: Baton carries Apple's own screen sharing instead of capturing the screen itself

Status: proposed. Written on the person's own choice, after the two earlier ways failed. Nothing in it is built. Whether Screen Sharing's own port answers at the full login window, checked for the first time here (V1, V2 below), decides whether the rest is worth building.

## Context

[ADR 0019](0019-baton-at-the-login-window.md) chose a small Baton of its own, a program that would capture the login window's screen and post the phone's taps and keys into it. Its own two unproven points, L1 (events) and L2 (capture), were tried on the person's Mac (macOS 27.2, 2026-11-11) and both failed: the window system answered that the program "is not permitted to connect to or launch Window Server before login", and posting input needs a private entitlement that nothing the person can sign with carries. ADR 0019's own "If the two unproven points fail" named what would be left if this happened: "the plug-in of the authorisation, which ADR 0013 turned down for what a faulty one does... and which gets a record of its own before anyone builds it." This is not that record, because the plug-in did not reach the point of needing one either.

An authorization plug-in (a `.bundle` in `/Library/Security/SecurityAgentPlugins`, loaded into the chain of mechanisms that macOS runs for the `system.login.console` right) was the person's next choice. A throwaway plug-in was built and tried in a lab virtual machine, never on the person's own Mac, with three shapes: putting a name and a password into the chain's shared context before the stock mechanism that shows the window runs, doing that and then asking the engine to deactivate the mechanisms after it and start again (`RequestInterrupt`), and replacing the stock mechanism outright with one that only sets the context. None of the three signed the account in without typing; the window this project is trying to get past stayed up and waited every time. Something in Apple's chain checks a password where it is not reading the values that these mechanisms set, and no public source read for this project says what. The plug-in also only ran inside the login window's own process because the lab machine's own protections are looser than a normal Mac's; getting it to run there on a real Mac logged a rejection from the operating system's library-validation check (AMFI), which exists to keep exactly this kind of code out of exactly that process, since that process is also where a password is typed. Working around that check is not attempted here, whether or not it would have helped: the sign-in did not work even where the plug-in loaded.

Four ways were found and put to the person on 2026-11-11: carrying Apple's own screen sharing to the login window, the plug-in above, turning FileVault off (which the person's own rule refuses, since it gives up the disk's protection), and signing in by hand, with no remote part at all. The other ways that ADR 0019 had already ruled out for itself (an authenticated restart, which only covers a restart that the Mac starts and still stops at the login window; device management, for which no command that signs a person in was found; and the Mac App Store, closed to a sandboxed app that must write outside its sandbox) are ruled out here for the same reasons. The person chose to carry Apple's own screen sharing.

What is known about it, and how well:

- Apple's Screen Sharing, turned on in System Settings under General and Sharing, runs a VNC server. Two people who posted about it online report that it was unavailable at the full login window on a FileVault Mac until someone signed in, on recent macOS; one of the two says turning FileVault off fixed it. Neither post is about the exact macOS version or Mac in front of this project, and neither was checked here. Against that, ADR 0019's own Context has the person's phone reaching the Mac's SSH door, over the network, while the Mac sat at that same login window for about three minutes after a restart (observed once, 2026-11-11): the network was up there, at least for that one Mac on that one try, and at least for port 22. Whether Screen Sharing's own port is up at the same moment is a different question, since one program answering does not mean another does, and that is what V1 and V2 below check, rather than something nobody has seen.
- Screen Sharing, on a Mac that is already running, can ask for either of two things before it shows anything: the name and password of an account on the Mac that System Settings allows to connect, or a separate VNC password kept in its own settings and good for any viewer. Nothing read for this project says which, if either, it asks for before anyone has signed in, or whether it shows the login window straight away with neither. V2 looks.
- Screen Sharing, once turned on, listens for a connection on port 5900. Reported, not checked here: it listens on every network interface unless something on the Mac stops it, which would let any device on the same network as the Mac try to reach it, not only a device that goes through Baton.

## Decision

**Baton carries the connection; it does not speak the screen sharing protocol itself, and the phone does.** A program of its own (keeping the name `baton-loginwindow`) runs before anyone signs in, the same way [ADR 0019](0019-baton-at-the-login-window.md)'s did, but its job is different: instead of capturing a screen and posting input, it opens a plain connection to `127.0.0.1:5900`, where Apple's own screen sharing is listening, the moment a paired phone asks to start a session, and from then on carries bytes between that phone's connection and the local one, both ways, reading none of them and changing none of them. It is Baton's own session that is asked for and granted, in the shape [ADR 0010](0010-sessions-that-the-viewer-starts.md) already decided: the phone sends `Start`, the program answers, and only then does it open the local connection at all, so that nothing is reached on the Mac's side before a paired phone has asked. What is carried after that is Apple's own protocol, opaque to Baton, so a change to it on either side needs no change to Baton's code.

**The device and the pairing are ADR 0019's, unchanged.** Its own key, its own list of paired devices in a folder that only its owner can read, pairing done in Terminal at the Mac with the person typing the six digits that the phone shows, printing nothing else that a device sent with its question and not its name, ending the trust of a phone only with `baton-loginwindow forget` or the remove script, run at a Mac that someone has signed in to, and installed by the person with an administrator's password as plain files, checked against the same certificate as the app. None of that depended on capturing a screen, so none of it needs to change. [ADR 0019](0019-baton-at-the-login-window.md)'s Consequences about this shape (a program that answers a stranger before anyone signs in, and what a flaw in that code would give up) apply again here and are not repeated.

**It may not need to run as root.** ADR 0019's program had to run as an agent for the `LoginWindow` session type because only that gave it the login window's own window-server session to capture and post into, and launchd only honours a dedicated user for a daemon, not an agent, which is why it ran as root. This program touches no window server: it only dials a local port and speaks Baton's own protocol on the network, which need no special privilege on macOS. So it may be possible to run it as a plain launch daemon, under a user made for it alone, and keep it off the account that root's processes run as; whether a daemon is in fact up and able to reach `127.0.0.1:5900` before anyone has signed in, or needs something that is only ready after a session exists, is not known and is V3 below. If it is not possible, the program runs as root, as ADR 0019's did, and the same caution applies.

**Screen Sharing is kept from being reached except through this program.** Turning it on opens a door on the Mac that was not open before, the same cost ADR 0019 already named for this alternative when it considered it. Apple's own Application Firewall, in System Settings, allows or refuses a program and says nothing about a port or an address, so it cannot do this; `pf`, the packet filter macOS also ships with no System Settings page of its own, can, with one rule for each of IPv4 and IPv6 that refuses an incoming connection to port 5900 from anywhere but the Mac itself (`127.0.0.1` over IPv4, `::1` over IPv6), loaded at boot so that it is in place before the login window that needs it is. The program above, which dials that address from the Mac's own side, still reaches it; a device on the same network that tries the Mac's address directly gets nothing; and a device that reaches Baton's own program still has to pair with it first, the same door every other part of Baton has. Whether the rule can be loaded before the first restart that needs it and survives one, and whether Screen Sharing still answers over loopback once it is in place, is V4. The install script adds the rule and turns Screen Sharing on; the remove script takes the rule back out and turns Screen Sharing off again too, or tells the person to, since it was this program that had a reason to turn it on in the first place.

**The phone asks for the person's face before it opens this, exactly as before any other screen.** Nothing in Apple's protocol checks who is holding the phone; that check is the app's own, on the phone, for every session it starts ("Checking the person at a phone before it asks for a screen" in [security.md](../security.md)), and it runs here the same way, before the `Start` is even sent, because the rule is the phone's and does not depend on what is being carried.

**What this view does not have, until it ends.** A session that carries Apple's own protocol has none of Baton's own rules once it is open: not the private session's dark screen and held keyboard, not the guard that locks the Mac if the app dies, not the limit to one shared window, nothing of [ADR 0009](0009-window-streaming.md) or [ADR 0011](0011-privacy-mode.md). ADR 0019 already judged this acceptable for the login window itself, for the same reason this record relies on again: nothing private is shown there, since nobody has signed in yet, so there is nothing for a cover to protect. That reasoning stops being true the instant the account signs in, which is also the instant this view is looking at a real desktop with none of Baton's safeguards around it. ADR 0019 named the same gap for its own design and left closing it for a later change. Here the gap is reached through a view that a person could leave open by not closing it, rather than through a session that ends by itself when the login window goes away, so the program closes the connection to `127.0.0.1:5900` itself the moment it sees the login window close, rather than leaving that to the person or to a later change. The same signal keeps a new one from opening: the program answers a `Start` only while the Mac is showing its login window, and refuses it at every other time, including the moment right after a sign-in. That is not enough where the login window shows while an account stays signed in, which these Macs do (Fast User Switching: the app's own `AccountPlace.hidden`, in `BatonInput.swift`, is an account that is logged in with the login window on the screen): the login window is up and never closes, so the signal never comes. The program therefore also looks for a signed-in account, the way the app does, and refuses a `Start` for as long as there is one, whether or not the login window is up, so that nothing of Apple's screen sharing on a signed-in desktop can be reached through it at all. Closing the connection is what shortens the gap, and the refusal is what keeps a new one from opening; neither closes it. Closing it for good is still the later change ADR 0019 named: a program that takes the Mac over, dark and held, from the sign-in until the phone's own session starts.

**Nothing is built before V1 answers.** One observation (ADR 0019's own, port 22, once) says the network is up at the full login window; two reports found online say Screen Sharing specifically is not, until someone signs in. Both could be true together, since they are not about the same port. If V1 finds that nothing answers on this Mac this time, or that only port 22 ever does and port 5900 does not, nothing above can be reached regardless of what Baton does, and this record is replaced the way ADR 0019's capture-and-post idea was.

## Alternatives considered

- **Baton's own capture-and-post program**, ADR 0019 as first written. L1 and L2 failed on the person's Mac.
- **An authorization plug-in.** A spike found that none of three ways made the account sign in without typing, described under Context, and taking it further would mean working around a protection of the operating system that is there to keep code out of exactly the process this record also has to get code into. Not built, and not reconsidered unless V1 and V2 both fail and this whole record is replaced.
- **Turning FileVault off, with automatic sign-in.** Gives up the disk's own protection, which the person's rule keeps.
- **Signing in by hand.** No remote part at all, and the fallback until the rest of this record is built or found not to work.
- **A client of Baton's own streaming protocol instead of Apple's.** Would keep every one of Baton's own rules through the sign-in, with no gap at all, but needs the capture or the plug-in that the two records before this one each found could not be built. Not possible until one of them is.
- **Apple Remote Desktop, in place of a client of Baton's own on the phone.** It is a paid administration application that runs on a Mac, and there is none for a phone, so it could not be the phone's viewer. It controls a Mac's screen through the same service of the Mac that this record carries (inferred: it also uses port 5900; not checked here), so it would not change what V1 and V2 find at the login window, whoever wrote the client.

## Consequences

- **Screen Sharing is one more thing listening on the Mac.** It did not run before, and this record turns it on and keeps it answering only the Mac itself (`127.0.0.1` and `::1`), not any address that another device on the network could reach, with a firewall rule for it. Nothing in the system holds that rule in place once it is wrong or once a later change on the Mac removes it, the same caveat ADR 0019 made about the code that answers a stranger: the list here is what the install script sets out to do, not a limit that something else enforces.
- **The gap after sign-in, which ADR 0019 already named, is now reached through a view with none of Baton's own cover, hold or relock**, for whatever time passes between the account signing in and the program closing the connection (V6 measures it). ADR 0019 left its own fix, a program that takes the Mac over dark and held from the sign-in to the phone's next session, for a later change; it is still that, and it is now a closer one, since the view that reaches the gap has less of its own protection than ADR 0019's capture-based one would have had.
- **A client of a protocol Baton did not write before now runs in the phone app**, reading bytes a paired Mac sends. The sender is a device the phone already trusts for other things, so this is not a new way for a stranger to reach the phone, but it is new code with its own chance of bugs in reading what it is given, the same kind of care the rest of Baton takes with what a peer sends (see "Strict message decoding" in [security.md](../security.md)), applied now to a protocol that is not Baton's own and was not written by this project.
- **Everything ADR 0019 said about the device and the pairing applies again**, since the shape is reused: a program that runs on the network before anyone signs in, what a flaw in the code that answers a stranger would give up, and a lost phone removed only with `baton-loginwindow forget` or the remove script, at a Mac that someone has signed in to.
- **Every macOS release can change what Screen Sharing allows at the login window.** V1 and V2 are checked again after an upgrade, the way ADR 0019 said L1 and L2 would be.
- **If V1 or V2 fails, signing in by hand is what is left**, until this record is replaced the way ADR 0019's was.

## How it will be measured

On the person's own Mac, since nothing here can be tried without Apple hardware:

- **V1. The network at the full login window, again, and for Screen Sharing too.** Restart the Mac, unlock it with the phone over SSH as before, and once it is sitting at the ordinary login window (account tiles or a name field, not the disk password screen), from another device on the same network check whether anything answers at its address at all: port 22, which ADR 0019's own observation already found open at this same screen once, and port 5900, which has not been checked at all. If neither answers this time, that observation does not hold generally and nothing below can be reached; this record is then replaced.
- **V2. Screen Sharing answers there.** With Screen Sharing turned on beforehand and V1 showing that something answers, does port 5900 take a connection at that same screen, and does opening `vnc://` at the Mac's address from another Mac show the real login window? Does it ask for anything of its own first, or show the window straight away?
- **V3. The program's own privilege.** Can `baton-loginwindow`, built as a plain launch daemon under a user made for it, reach `127.0.0.1:5900` and listen on Baton's own network before anyone has signed in, the way launchd starts other daemons at boot? If not, it runs as root, as ADR 0019's did.
- **V4. Kept off the network.** With the firewall rule in place, does a port scan of 5900 from another device on the same network get nothing, while the Mac's own program still reaches it over `127.0.0.1`? Does the rule take effect before the first login window that needs it, and does it survive a restart?
- **V5. Signing in through it.** From the phone's new screen-sharing client, does typing the account's password sign the account in, the way typing at the Mac's own keyboard would? How does it look and feel next to one of Baton's own sessions: the delay, the picture, whether the person can tell which one they are in?
- **V6. The gap at sign-in.** From the moment the account signs in to the moment the program closes the connection to `127.0.0.1:5900`, how long, measured the way L6 of ADR 0019 measured its own gap? Does the person see anything of the signed-in desktop in that view before it closes? Sent right after the sign-in, and again at the login window that shows while an account stays signed in (Fast User Switching), is a `Start` refused both times, the way the Decision says it should be?
- **V7. Away from home.** V1 and V2 again, reached through the route of [ADR 0017](0017-away-from-home.md) instead of the home network, since reaching this from away is the whole point of building it.
